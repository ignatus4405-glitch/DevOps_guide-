# Как Terraform строит план: граф, провайдеры, state

Terraform кажется магией: вы описываете ресурсы, а он «делает правильно».
На самом деле это граф зависимостей, сопоставление с state и вызовы провайдеров.

## Граф зависимостей

Terraform строит DAG из ссылок между ресурсами:

```hcl
resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
```

`aws_subnet.app` зависит от `aws_vpc.main`, потому что ссылается на `.id`.
Порядок выполнения определяется графом, а не порядком в файле. Параллельность
ограничена `-parallelism` (по умолчанию 10).

Явные зависимости: `depends_on`, когда связь не выражается ссылкой.

## Цикл plan

1. **Refresh** (или `-refresh=false`) — прочитать реальные объекты.
2. **Diff** — сравнить конфигурацию, state и реальность.
3. **Plan** — список действий: create/update/replace/destroy.

`-replace` помечает ресурс на пересоздание. `-target` сужает план, но опасен:
можно пропустить зависимые изменения.

## Провайдеры

Провайдер — плагин с API-схемой ресурсов. Он переводит HCL в вызовы облака и
обратно. Версии провайдеров фиксируются в lock-файле (`.terraform.lock.hcl`),
чтобы у всех был одинаковый результат.

`terraform init` скачивает провайдеров; `terraform providers` показывает
источники. Без lock-файла сборка невоспроизводима.

## State — не кэш, а контракт

State хранит соответствие адреса ресурса и реального ID, а также атрибуты,
которые нельзя получить из API (например, вычисленные значения).

Поэтому:

- state нельзя терять — Terraform перестанет узнавать ресурсы;
- state нельзя хранить в Git — там секреты и конфликты;
- state нужно блокировать при apply.

`terraform import` добавляет существующий ресурс в state, но не создаёт
конфигурацию — её нужно написать вручную.

## Дрейф

Кто-то изменил ресурс в консоли — state и реальность разошлись. `plan` покажет
diff и попытается вернуть код. Чтобы ловить раньше:

```bash
terraform plan -detailed-exitcode   # 2 = есть изменения
```

Запускайте по расписанию и отправляйте отчёт владельцу.

## Почему plan врёт

- провайдер не видит изменений (eventual consistency);
- `ignore_changes` скрывает поле;
- computed-поля меняются при каждом плане;
- разные версии провайдера;
- ручные изменения после refresh.

Если план «мигает» без изменений кода — ищите причину в computed-полях и
ignore_changes, а не в «Terraform сломался».

## Модули и композиция

Модуль — папка с переменными, ресурсами и выходами. Хороший модуль:

- имеет один смысл (VPC, кластер, база);
- не создаёт провайдеров внутри;
- версионируется semver;
- документирует inputs/outputs.

Композиция — корневой модуль, который вызывает дочерние. Не делайте «один
модуль на всё»: его невозможно переиспользовать.

## Как проверить себя

1. Как Terraform определяет порядок ресурсов?
2. Что делает refresh в plan?
3. Почему state нельзя хранить в Git?
4. Что означает `-detailed-exitcode` = 2?
5. Почему план может «мигать» без изменений?

!!! tip "Практика"
    Задача «Разбор плана» в практикуме: объяснить replace и порядок.

## Подробный разбор темы

Terraform строит граф зависимостей по ссылкам на ресурсы и выражениям; граф определяет порядок создания и уничтожения. Явный `depends_on` нужен только когда зависимость не видна через значение, иначе он может излишне сериализовать работу. Provider переводит декларативные ресурсы в вызовы API, поэтому версия provider влияет на схему, поведение и миграции.

State связывает адрес ресурса и remote ID; `moved` block помогает менять адрес без пересоздания, а import связывает уже существующий объект. Разделяйте plan на понятные изменения и проверяйте, почему ресурс собирается заменить себя: это может быть ForceNew-атрибут, изменение ключа или drift. Сохранённый plan binary чувствителен: он может содержать значения и должен защищаться как state.
