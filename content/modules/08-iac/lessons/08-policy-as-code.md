# Policy as Code: guardrails вместо запретов

Правила «не создавай публичный бакет» работают, пока о них помнят. Policy as
Code превращает договорённости в проверяемые автоматически условия.

## Где применять

- **CI** — проверить Terraform plan до apply;
- **admission** — отклонить опасный манифест в кластере;
- **cloud** — SCP/organization policies;
- **registry** — политики подписи и сканирования.

Чем раньше проверка, тем дешевле исправление.

## OPA и Rego

Open Policy Agent — универсальный движок политик. Пример: запретить тег latest.

```rego
package kubernetes.admission

deny contains msg if {
  input.request.kind.kind == "Pod"
  image := input.request.object.spec.containers[_].image
  endswith(image, ":latest")
  msg := sprintf("образ %s использует latest", [image])
}
```

Conftest проверяет YAML/JSON в CI тем же языком.

## Kyverno

Kyverno — политики на YAML, без отдельного языка:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: require-labels}
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-owner
      match: {resources: {kinds: [Deployment]}}
      validate:
        message: "нужен label owner"
        pattern:
          metadata:
            labels:
              owner: "?*"
```

Плюс: читается без изучения Rego. Минус: сложные условия всё равно требуют
выразительности.

## Terraform

- `tflint` — ошибки провайдера;
- `checkov`/`tfsec` — безопасность;
- `conftest` — свои правила по plan JSON;
- Sentinel (Terraform Cloud) — политики в платформе.

```bash
terraform show -json plan.out > plan.json
conftest test plan.json --policy policy/ --namespace terraform
```

Для правила с `package kubernetes.admission` задайте соответствующий namespace:
`conftest test manifest.yaml --policy policy/ --namespace kubernetes.admission`.
Используйте Rego v1 (`deny contains ... if { ... }`) либо явно закрепите старый
режим; не смешивайте синтаксис и namespace.

## Как внедрять

1. Начните с аудита (warn), не с блокировки.
2. Соберите нарушения, объясните командам.
3. Включите enforce для критичных правил.
4. Дайте исключения с владельцем и сроком.
5. Удаляйте правила, которые не работают.

Политика без объяснения воспринимается как препятствие. Сообщение об ошибке
должно говорить, что делать, а не только «denied».

## Антипаттерны

- сотни правил «на всякий случай»;
- блокировка без пути обхода (break-glass);
- политики вне Git;
- отсутствие тестов на политики.

## Как проверить себя

1. Где можно применять policy as code?
2. Чем Rego отличается от Kyverno?
3. Почему начинать с audit?
4. Что должно быть в сообщении об отказе?
5. Зачем тестировать политики?

## Подробный разбор темы

Policy должна описывать риск и область действия: например, запрет публичного ingress для production, но не для локального тестового окружения. У правила должен быть понятный текст отказа и ссылка на безопасный путь. Если сообщение говорит только «deny», разработчик будет просить исключение вместо исправления конфигурации.

Разделяйте обязательный guardrail и рекомендацию; жёсткий блокирующий запрет используйте для недопустимого риска, мягкий результат — для качества и стоимости. Тестируйте fixtures на типичных объектах, пограничных случаях и отсутствии поля. Версионируйте policy как код и предусмотрите audited exception с владельцем и сроком, чтобы исключение не превращалось в постоянный обход.

## Пошаговый сценарий

![Порядок действий: Policy as Code: guardrails вместо запретов](assets/img/howto/08-iac--08-policy-as-code.svg)

1. Запишите требование как проверяемое правило и обозначьте исключения.
2. Подготовьте допустимые и запрещённые fixture-примеры.
3. Запустите policy на plan или manifest в CI с понятными сообщениями.
4. Проверьте процесс согласования, срока действия и аудита исключений.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Перепишите требование как короткое правило: например, «у каждой VM есть encryption».

**Как проверить.** Правило можно проверить автоматически на конфигурации, а исключение описывается отдельно.

### Шаг 2

**Что сделать.** Создайте два маленьких fixture: один разрешённый manifest и один заведомо запрещённый.

**Как проверить.** Тесты доказывают и что хорошее проходит, и что плохое блокируется.

### Шаг 3

**Что сделать.** Запустите policy на Terraform plan/manifest в CI и выведите файл и строку ошибки.

**Как проверить.** Автор изменения понимает, что исправить; запрет не содержит секрета или неясного текста.

### Шаг 4

**Что сделать.** Для исключения укажите владельца, причину, срок окончания и компенсирующую защиту.

**Как проверить.** Исключение можно пересмотреть и оно не действует бесконечно без контроля.
