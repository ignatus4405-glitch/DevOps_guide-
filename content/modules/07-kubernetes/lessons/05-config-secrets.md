# Конфигурация: ConfigMap, Secret, внешние хранилища

Приложение должно быть одинаковым во всех окружениях, а различаться только
конфигурацией. В Kubernetes для этого есть ConfigMap и Secret, но у них есть
границы, которые важно понимать заранее.

## ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: info
  APP_MODE: production
  nginx.conf: |
    server {
      listen 8080;
      location / { return 200 'ok'; }
    }
```

Использование:

```yaml
containers:
  - name: app
    envFrom:
      - configMapRef:
          name: app-config
    volumeMounts:
      - name: config
        mountPath: /etc/nginx
volumes:
  - name: config
    configMap:
      name: app-config
```

Разница: `envFrom` читает переменные один раз при старте; volume обновляется
автоматически (с задержкой до минуты), но приложение должно перечитывать файл.

## Secret

```bash
kubectl create secret generic db-creds \
  --from-literal=username=app \
  --from-literal=password='s3cr3t'
```

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-creds
        key: password
```

Важно: Secret по умолчанию хранится в etcd в base64 — это **не шифрование**.
Нужно:

- включить encryption at rest в etcd;
- ограничить RBAC на чтение секретов;
- использовать внешнее хранилище (Vault, External Secrets, CSI driver).

```bash
kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 -d
```

Любой, у кого есть `get secrets` в namespace, прочитает значение. Поэтому
`secrets` — привилегированный ресурс.

## Внешние хранилища

| Решение | Как работает |
| --- | --- |
| External Secrets Operator | синхронизирует секреты из Vault/AWS SM в Kubernetes Secret |
| Secrets Store CSI | монтирует секреты напрямую в под |
| Vault Agent Injector | sidecar/init-контейнер достаёт секрет |
| SOPS + GitOps | зашифрованные секреты в git |

Для продакшена предпочтительнее внешнее хранилище: секреты не лежат в etcd и
централизованно ротируются.

## Обновление конфигурации

Два подхода:

1. **Hot reload** — приложение следит за файлом или получает SIGHUP.
2. **Recreate pods** — конфигурация читается только при старте.

Во втором случае нужно менять аннотацию в pod template, чтобы rollout
перезапустил поды:

```yaml
spec:
  template:
    metadata:
      annotations:
        config/hash: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

Helm делает это через checksum/config. Без этого ConfigMap обновится, а поды
продолжат работать со старыми значениями.

## Проверка и типичные ошибки

```bash
kubectl get configmap app-config -o yaml
kubectl exec deploy/app -- env | grep LOG_LEVEL
kubectl exec deploy/app -- cat /etc/nginx/nginx.conf
```

| Ошибка | Симптом |
| --- | --- |
| ConfigMap не существует | Pod в `CreateContainerConfigError` |
| неверный ключ | `couldn't find key` |
| Secret в другом namespace | не находится |
| пробелы/переводы строк в Secret | приложение не может подключиться |

## Практика безопасности

- не храните секреты в ConfigMap;
- не выводите env в логи;
- ограничьте RBAC (`get secrets` — только нужным SA);
- используйте `automountServiceAccountToken: false`, если токен не нужен;
- ротируйте секреты и перезапускайте поды.

## Подробный разбор темы

ConfigMap предназначен для несекретной конфигурации; Secret — объект с данными, которые всё равно требуют шифрования в etcd, RBAC и контроля доступа. Base64 в manifest — кодирование, не защита. Не коммитьте открытый secret; используйте внешнее хранилище и синхронизацию с короткоживущими credentials, если это поддерживается платформой.

Переменная окружения считывается приложением при старте, а смонтированный файл может обновляться — поведение зависит от способа подключения и самого приложения. Изменение ConfigMap не гарантирует автоматический reload процесса. Зафиксируйте, как конфигурация версионируется, как валидируется и как раскатывается без рассинхронизации между replica. Не вставляйте секреты в командную строку, где они могут попасть в history или process list.

## Пошаговый сценарий

![Порядок действий: Конфигурация: ConfigMap, Secret, внешние хранилища](assets/img/howto/07-kubernetes--05-config-secrets.svg)

1. Разделите несекретную конфигурацию и чувствительные значения.
2. Проверьте RBAC, шифрование etcd и источник выдачи credentials.
3. Смонтируйте версионированную конфигурацию в тестовый Pod.
4. Проверьте reload приложения и отсутствие секрета в логах.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Разложите настройки по двум группам: обычные значения и пароли/ключи.

**Как проверить.** Секрет не записан в ConfigMap или в открытый git-файл.

### Шаг 2

**Что сделать.** Проверьте, кто может читать Secret, включено ли encryption at rest и откуда workload получает identity.

**Как проверить.** Доступ разрешён только конкретному service account, а не всем пользователям кластера.

### Шаг 3

**Что сделать.** Подключите тестовую версию ConfigMap/Secret к одноразовому Pod; реальные пароли не вставляйте в чат или логи.

**Как проверить.** Приложение читает нужное значение, а команда `kubectl describe` не печатает секрет в отчёт.

### Шаг 4

**Что сделать.** Измените тестовую настройку и проверьте, перечитало ли её приложение или нужен rollout.

**Как проверить.** Изменение применяется предсказуемо; в логах нет секрета.
