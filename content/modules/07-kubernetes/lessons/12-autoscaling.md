# Автомасштабирование: HPA, VPA, KEDA и кластер

Автомасштабирование звучит как «добавить подов, когда нагрузка выросла». На
деле это несколько независимых контуров, и они конфликтуют, если их не
согласовать.

## HPA: горизонтальное

HorizontalPodAutoscaler меняет число реплик по метрике:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: api}
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 60}}
```

HPA сравнивает текущее значение с целевым и меняет реплики. Важно:

- метрика должна быть доступна через metrics-server/adapters;
- requests должны быть реалистичными (utilization считается от requests);
- есть задержка: поды стартуют не мгновенно.

## Проблема холодного старта

HPA видит нагрузку, когда она уже пришла. Пока поды стартуют, пользователи
ждут. Лечение:

- minReplicas с запасом;
- predictive scaling (KEDA/облако);
- быстрый старт (меньше образ, readiness);
- queue-based scaling.

## VPA: вертикальное

VerticalPodAutoscaler подбирает requests/limits по фактическому потреблению.
Режимы: Off (рекомендации), Initial, Auto.

VPA и HPA по CPU конфликтуют: один меняет requests, другой — replicas. Не
включайте оба на одну метрику.

## KEDA: масштабирование по событиям

KEDA добавляет scaler'ы: длина очереди, lag Kafka, число сообщений в RabbitMQ.

```yaml
triggers:
  - type: kafka
    metadata:
      topic: orders
      lagThreshold: "100"
```

Это точнее CPU: очередь растёт раньше, чем процессор.

## Cluster Autoscaler / Karpenter

HPA создаёт поды, но им нужны узлы. Cluster Autoscaler добавляет узлы в group,
Karpenter подбирает инстансы напрямую.

Важно:

- requests должны соответствовать реальности, иначе узлы неэффиктивны;
- taints/tolerations и affinity влияют на размещение;
- scale-down может убить поды с локальными данными.

## Метрики и стабильность

HPA умеет `behavior`:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
```

Без стабилизации число реплик «дёргается». Для latency-критичных сервисов
масштабируйтесь по p95/очереди, а не по CPU.

## Стоимость

Автомасштабирование не бесплатно: минимумы, простой, перерасход на пиках.
Считайте unit-экономику: стоимость запроса при разной нагрузке.

## Как проверить себя

1. От чего HPA считает utilization?
2. Почему HPA запаздывает?
3. Чем KEDA лучше HPA для очередей?
4. Почему VPA и HPA конфликтуют?
5. Зачем `stabilizationWindowSeconds`?

!!! tip "Практика"
    Задача «HPA и очередь» в практикуме: выбрать метрику и границы.

## Подробный разбор темы

HPA меняет число реплик, VPA рекомендует или меняет requests, KEDA масштабирует по внешним событиям, а cluster autoscaler добавляет узлы при нехватке места. Эти уровни должны быть согласованы: если HPA требует новые Pod, но узлы не растут, проверьте requests, quota, ограничения node pool и скорость запуска образа.

Метрики масштабирования должны отражать перегрузку и иметь разумные окна усреднения. Если requests не заданы, CPU utilization может быть бессмысленным; для очереди полезнее длина backlog или возраст самого старого сообщения. Настройте stabilization window и scale-down policy, чтобы исключить колебания. Проверяйте стоимость пиков и минимальный запас, а не только реакцию на нагрузочном тесте.

## Пошаговый сценарий

![Порядок действий: Автомасштабирование: HPA, VPA, KEDA и кластер](assets/img/howto/07-kubernetes--12-autoscaling.svg)

1. Проверьте requests и метрику, на которой основано масштабирование.
2. Настройте HPA/KEDA и доступный node pool для новых Pod.
3. Сымитируйте рост нагрузки и наблюдайте scale-up и задержку очереди.
4. Проверьте scale-down, стоимость и отсутствие резких колебаний.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Проверьте `kubectl top pods` и requests: горизонтальный autoscaler сравнивает загрузку с запросом ресурсов.

**Как проверить.** Метрика существует и units понятны; HPA не работает на нулевых или отсутствующих данных.

### Шаг 2

**Что сделать.** Задайте min/max replicas и цель масштабирования в тестовом namespace.

**Как проверить.** Количество реплик ограничено безопасным диапазоном и node pool может их разместить.

### Шаг 3

**Что сделать.** Подайте небольшую синтетическую нагрузку и наблюдайте `kubectl get hpa -w`.

**Как проверить.** Число replicas растёт вслед за метрикой, а очередь/задержка снижается.

### Шаг 4

**Что сделать.** Уберите нагрузку и проверьте постепенное уменьшение реплик и стоимость ресурсов.

**Как проверить.** Масштабирование вниз не прерывает активные запросы и не колеблется резко.
