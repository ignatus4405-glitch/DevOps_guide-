# Планировщик, контроллеры и операторы

Kubernetes — это набор циклов согласования вокруг API-сервера. Понимание этих
циклов объясняет, почему под «висит в Pending», почему Deployment не всегда
перезапускает под и зачем нужны операторы.

## Желаемое и фактическое

Почти всё в Kubernetes работает по одной схеме:

```text
watch → сравнить desired и actual → действие → обновить status → повтор
```

Контроллер не выполняет команды «сейчас», он приводит состояние к желаемому.
Если pod удалён — ReplicaSet создаст новый. Если узел пропал — контроллер
увидит это и пересоздаст поды.

## etcd и API-сервер

etcd — консистентное хранилище ключ-значение, источник истины. API-сервер —
единственная точка записи, он валидирует объекты, применяет admission-политики
и рассылает watch-события.

Следствия:

- `kubectl` не общается с kubelet напрямую;
- запись в etcd — это quorum, поэтому кластер чувствителен к latency диска;
- кэш API-сервера может отдавать слегка устаревшие данные.

## Планировщик

Когда создаётся под без `nodeName`, kube-scheduler выбирает узел в два этапа:

1. **Filter (predicates)** — какие узлы вообще подходят:
   ресурсы (requests), taints/tolerations, affinity, nodeSelector,
   topology spread, volume zones.
2. **Score** — какой из подходящих лучше: баланс ресурсов, близость,
   anti-affinity.

Если под не проходит фильтр, он остаётся `Pending`, а в событиях будет причина.
`kubectl describe pod` — первый инструмент, а не перезапуск.

Частые причины Pending:

- не хватает CPU/RAM с учётом requests;
- taint без toleration;
- nodeSelector/affinity не совпадает;
- PVC в зоне, где нет узлов;
- превышена PodDisruptionBudget при вытеснении.

## Requests, limits и планирование

Планировщик смотрит только на **requests**. Limits не учитываются при
размещении. Поэтому:

- заниженные requests — узел перегружен по факту;
- завышенные — деньги на ветер и пустые узлы.

Правило: requests ≈ p95 потребления, limits — потолок с запасом. Для памяти
limits важен из-за OOM; для CPU limit приводит к throttling.

## QoS-классы

| Класс | Условие | При вытеснении |
| --- | --- | --- |
| Guaranteed | requests == limits | уходят последними |
| Burstable | requests < limits | средний приоритет |
| BestEffort | нет requests/limits | уходят первыми |

## Операторы и CRD

CRD расширяет API новым типом объекта. Оператор — контроллер, который умеет
с ним работать и знает предметную область.

Пример: `kind: PostgresCluster` вместо набора StatefulSet, Service, Secret,
Job для бэкапа. Оператор создаёт всё это и следит за состоянием.

Оператор нужен, когда:

- есть сложная логика жизненного цикла;
- нужны действия «наружу» кластера (бэкап, failover, DNS);
- хочется один декларативный объект вместо десяти.

Не нужен, когда хватает Deployment и ConfigMap.

## Владение и сборка мусора

`ownerReferences` связывают объекты. Удаляете Deployment — ReplicaSet и podы
удаляются каскадно. `kubectl delete --cascade=orphan` оставляет потомков.

Финализаторы (`finalizers`) блокируют удаление, пока контроллер не завершит
внешние действия: удалит диск, запись DNS, бакет.

## Отладка контроллеров

```bash
kubectl get events --sort-by=.lastTimestamp
kubectl describe deploy api
kubectl get rs,pods -l app=api
kubectl logs -n kube-system deploy/cluster-autoscaler
```

Если «ничего не происходит», проверьте:

1. существует ли контроллер и жив ли он;
2. совпадают ли labels/selectors;
3. не блокирует ли finalizer;
4. не отвергает ли admission-политика;
5. видит ли контроллер события (RBAC).

## Как проверить себя

1. Что делает контроллер при расхождении desired и actual?
2. Какие два этапа проходит планировщик?
3. Почему limits не влияют на размещение?
4. Когда оператор оправдан, а когда нет?
5. Зачем нужны finalizers?
