# Планировщики: cron, systemd timers и идемпотентность

Регулярные задачи — бэкапы, ротация, синхронизация, отчёты — должны запускаться
без человека. Но «поставил в cron» ещё не значит «сделал надёжно»: нужны логи,
защита от наложений и понятное поведение при сбое.

## cron: синтаксис и подводные камни

```
# ┌ минута (0-59)
# │ ┌ час (0-23)
# │ │ ┌ день месяца (1-31)
# │ │ │ ┌ месяц (1-12)
# │ │ │ │ ┌ день недели (0-7, 0 и 7 — воскресенье)
# │ │ │ │ │
  30 3 * * *  /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

Важные детали:

- cron запускает задачу с **минимальным окружением**: `PATH=/usr/bin:/bin`,
  нет ваших переменных из `.bashrc`. Абсолютные пути обязательны.
- `%` в команде означает перевод строки — экранируйте `\%`.
- `>> log 2>&1` нужен, иначе вывод уйдёт в почту (или потеряется).
- `MAILTO=""` отключает почту, если она не настроена и создаёт мусор.

Проверка пользовательских заданий:

```bash
crontab -l
crontab -e
sudo ls -l /etc/cron.d/ /etc/cron.daily/
```

## Наложения и блокировки

Если задача выполняется дольше интервала, запуски накладываются: два бэкапа
одновременно пишут в один файл. Лечится блокировкой:

```bash
exec 9>/var/lock/backup.lock
flock -n 9 || { echo "уже выполняется"; exit 0; }
```

`flock -n` не ждёт, а сразу выходит, если лок занят. Это стандартный приём в cron-
скриптах. В systemd есть готовая альтернатива — `Type=oneshot` + юнит не запустится
повторно, пока предыдущий активен.

## systemd timers: лучше cron

| Возможность | cron | systemd timer |
| --- | --- | --- |
| Логи | вручную | journalctl автоматически |
| Пропущенный запуск | теряется | `Persistent=true` догоняет |
| Зависимости | нет | `After=`, `Requires=` |
| Разброс нагрузки | вручную | `RandomizedDelaySec` |
| Лимиты ресурсов | нет | `MemoryMax`, `CPUQuota` |
| Секреты в окружении | файл crontab | `EnvironmentFile` с правами 600 |

Пример пары юнитов:

```ini
# backup.service
[Unit]
Description=Ночной бэкап
[Service]
Type=oneshot
ExecStart=/opt/scripts/backup.sh
```

```ini
# backup.timer
[Unit]
Description=Запуск бэкапа в 03:30
[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true
RandomizedDelaySec=600
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable --now backup.timer
systemctl list-timers --all
```

`OnCalendar` можно проверить без ожидания: `systemd-analyze calendar "*-*-* 03:30:00"`
покажет следующие запуски.

## Идемпотентность и наблюдаемость

Регулярная задача должна:

1. **Быть безопасной при повторном запуске** — не дублировать данные, не падать
   на существующих файлах.
2. **Оставлять след** — лог, метрику, запись в журнал. Иначе «бэкап есть» —
   утверждение без доказательств.
3. **Проверяться** — раз в месяц запускать восстановление из бэкапа, а не только
   создание.
4. **Иметь таймаут** — зависший процесс не должен блокировать следующие запуски:
   `timeout 3600 /opt/scripts/backup.sh`.

## Проверка, что бэкап работает

```bash
# создать
/opt/scripts/backup.sh
# проверить целостность
tar -tzf /backup/app-$(date +%F).tar.gz > /dev/null && echo OK
# восстановить в тестовый каталог
mkdir -p /tmp/restore && tar -xzf /backup/app-latest.tar.gz -C /tmp/restore
```

Бэкап, из которого ни разу не восстанавливали, — это надежда, а не резервная
копия. Включите проверку восстановления в тот же таймер раз в неделю.

## Подробный разбор темы

Cron запускает задачу в минимальном окружении: не рассчитывайте на интерактивный `PATH`, профиль пользователя или текущую директорию. Указывайте абсолютные пути, перенаправляйте вывод в журнал и задавайте временную зону осознанно. Systemd timer удобен, когда важны зависимости, журналирование, контроль пропущенного запуска (`Persistent=true`) и единое управление службой.

Планировщик может запустить новый экземпляр, пока предыдущий ещё работает. Используйте lock или другой механизм координации и проектируйте задачу идемпотентно: повторный запуск не должен дублировать платёж, удалять лишнее или портить данные. Зафиксируйте длительность и результат выполнения, настройте сигнал при пропуске ожидаемого запуска и предусмотрите ручной безопасный повтор.
