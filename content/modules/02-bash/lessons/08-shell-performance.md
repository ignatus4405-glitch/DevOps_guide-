# Производительность shell: процессы, циклы, потоки

Скрипт, который «работает», может выполняться часами. Обычно причина не в
bash, а в лишних процессах и неправильной обработке данных.

## Стоимость fork/exec

Каждая внешняя команда — это `fork` + `exec` + загрузка бинарника. В цикле на
100 000 итераций это миллионы операций. Встроенные команды (`[[ ]]`, `printf`,
`read`, арифметика) дешевле внешних (`grep`, `sed`, `expr`).

```bash
# медленно
for f in *.log; do
  lines=$(wc -l < "$f")
  echo "$f $lines"
done

# быстрее: один awk
awk 'FNR==1{if(NR>1)print name, count; name=FILENAME; count=0} {count++} END{print name, count}' *.log
```

## `cat` и конвейеры

`cat file | grep x` создаёт лишний процесс. `grep x file` делает то же самое.
Но `cat` уместен для склейки или когда инструмент не умеет файлы.

Конвейер из пяти команд на миллионе строк дороже одной awk-программы, но
читается лучше. Выбор — баланс.

## Циклы против потоков

Bash плохо подходит для построчной обработки больших файлов:

```bash
while IFS= read -r line; do
  process "$line"
done < big.txt
```

Это может быть приемлемо, но `awk`/`perl`/`python` будут на порядки быстрее.
Если нужен именно shell — минимизируйте работу в теле цикла.

## Параллельность

```bash
printf '%s\n' "${hosts[@]}" | xargs -P 8 -I{} ssh {} uptime
```

`xargs -P` запускает параллельно. Ограничивайте параллелизм: 100 одновременных
ssh положат и клиент, и сеть.

GNU `parallel` даёт больше контроля (retries, grouping, вывод), но требует
установки.

## Буферизация и пайпы

Вывод в терминал медленный. Перенаправление в файл и `stdbuf -oL` помогают,
но меняют поведение. Для логов используйте `tee`, если нужен и экран, и файл.

## Профилирование

```bash
time ./script.sh
bash -x ./script.sh 2>trace.log
```

`time` показывает real/user/sys. Если real >> user+sys — скрипт ждёт I/O или
процессы. `-x` показывает каждый шаг, но замедляет.

Для поиска «горячих» мест вставляйте `date +%s%N` вокруг подозрительных блоков
или используйте `PS4` с временем.

## Практические правила

1. Меньше процессов в цикле.
2. Один проход по данным вместо трёх.
3. Ограниченный параллелизм.
4. Не читайте файл целиком, если нужна первая строка.
5. Проверяйте на реальном объёме, а не на 10 строках.

## Как проверить себя

1. Почему внешняя команда в цикле дорога?
2. Чем `grep file` лучше `cat file | grep`?
3. Когда `while read` оправдан?
4. Как ограничить параллелизм `xargs`?
5. Что означает real ≫ user+sys?

!!! tip "Практика"
    Задача «Ускорить скрипт» в практикуме: убрать лишние процессы.

## Подробный разбор темы

Самая частая причина медленного shell-скрипта — запуск внешней программы на каждой строке. Сначала измерьте `time` на репрезентативном объёме, затем замените повторные вызовы на пакетную обработку или встроенные операции Bash, если это не ухудшает читаемость. Сравнивайте одинаковые входы и учитывайте стоимость чтения диска, сортировки и создания временных файлов.

Параллельный запуск ускоряет независимые задачи, но требует ограничения числа workers, корректного сбора exit codes и безопасной записи результатов. Не распараллеливайте операции, которые меняют один и тот же файл или общий state без блокировки. На очень больших данных переход на Python/Go может быть лучше, чем сложный набор shell-трюков: критерии выбора — объём, поддерживаемость и возможности тестирования.

## Пошаговый сценарий

1. Измерьте время на репрезентативном объёме данных.
2. Найдите повторные внешние процессы и лишние временные файлы.
3. Обрабатывайте данные пакетно и ограничивайте параллелизм.
4. Сравните скорость и корректность на одинаковом входе.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Подготовьте фиксированный тестовый файл и измерьте начальное время командой `time ./script.sh input.txt`.

**Как проверить.** Зафиксированы размер входа, машина и время; без этого нельзя честно сравнить оптимизацию.

### Шаг 2

**Что сделать.** Посмотрите, не запускает ли цикл `grep`/`awk` отдельный процесс для каждой строки; это часто лишние затраты.

**Как проверить.** Вы нашли конкретный повторяющийся запуск или временный файл, а не оптимизируете «на глаз».

### Шаг 3

**Что сделать.** Сравните обработку в цикле с одним вызовом `awk` или ограниченным `xargs -P`; не запускайте неограниченную параллельность.

**Как проверить.** Новая версия обрабатывает тот же вход и не превышает безопасный предел процессов.

### Шаг 4

**Что сделать.** Повторите `time` на том же файле и сравните контрольную сумму результата `sha256sum`.

**Как проверить.** Время улучшилось, а результат остался побайтно или логически тем же.
