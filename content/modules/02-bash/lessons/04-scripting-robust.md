# Надёжные скрипты: аргументы, ошибки, trap

Скрипт, который «работает», и скрипт, которому можно доверить продакшен, — разные
вещи. Надёжный скрипт падает громко и рано, не оставляет мусора и умеет
откатываться.

## Строгий режим

Первые строки любого серьёзного скрипта:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
IFS=$'\n\t'
```

| Опция | Что делает |
| --- | --- |
| `-e` | выход при ненулевом коде команды |
| `-u` | ошибка при использовании необъявленной переменной |
| `-o pipefail` | падение конвейера, если упала любая его часть |
| `-E` | наследование ERR-trap в функциях и подстановках |
| `IFS` | разделители: без пробелов и переводов строк безопаснее |

Без `pipefail` команда `false | true` считается успешной — типичная причина
«скрипт прошёл, а ничего не сделал».

Важно: `set -e` не срабатывает в условиях `if`, `while`, после `&&`/`||` и в
подстановках, если это не последняя команда. Это не баг, а правила языка.

## Аргументы

```bash
usage() {
  cat <<'USAGE'
Использование: deploy.sh -e <env> -v <version> [-n]
  -e  окружение: staging | prod
  -v  версия артефакта
  -n  dry-run
USAGE
}

while getopts ":e:v:nh" opt; do
  case "$opt" in
    e) ENV="$OPTARG" ;;
    v) VERSION="$OPTARG" ;;
    n) DRY_RUN=1 ;;
    h) usage; exit 0 ;;
    \?) echo "Неизвестная опция: -$OPTARG" >&2; usage >&2; exit 2 ;;
    :) echo "Опция -$OPTARG требует значения" >&2; exit 2 ;;
  esac
done

: "${ENV:?не задано окружение (-e)}"
: "${VERSION:?не задана версия (-v)}"
```

Конструкция `: "${VAR:?сообщение}"` — короткий способ проверить обязательную
переменную и вывести понятную ошибку. `${VAR:-default}` подставляет значение по
умолчанию, `${VAR:?}` — падает с сообщением.

## Функции и локальные переменные

```bash
log() { printf '[%s] %s\n' "$(date -Is)" "$*" >&2; }

retry() {
  local attempts=$1 delay=$2
  shift 2
  local i=1
  until "$@"; do
    (( i >= attempts )) && return 1
    log "попытка $i не удалась, повтор через ${delay}s"
    sleep "$delay"
    ((i++))
  done
}

retry 3 5 curl -fsS https://api.example.com/health
```

`local` обязателен: без него переменные функции живут в глобальной области и
ломают соседнюю логику. Логи пишем в stderr (`>&2`), чтобы stdout оставался
чистым для данных.

## trap: уборка и откат

```bash
TMPDIR=$(mktemp -d)
cleanup() { rm -rf "$TMPDIR"; }
trap cleanup EXIT

trap 'echo "Ошибка в строке $LINENO" >&2' ERR
```

`trap ... EXIT` выполняется всегда — и при успехе, и при ошибке, и при Ctrl+C
(если добавить `INT TERM`). Это правильный способ удалить временные файлы.

Для деплоя — откат при сбое:

```bash
ROLLBACK=0
trap 'if (( ROLLBACK )); then kubectl rollout undo deployment/app; fi' EXIT
kubectl set image deployment/app app="$IMAGE"
kubectl rollout status deployment/app --timeout=120s || { ROLLBACK=1; exit 1; }
```

## Опасные места

- **`rm -rf $DIR/`** — если `DIR` пуста, удалит `/`. Всегда `${DIR:?}` и кавычки.
- **Неэкранированные переменные** — путь с пробелом развалится: `"$file"`, не `$file`.
- **`cd` без проверки** — `cd "$dir" || exit 1`, иначе скрипт продолжит работу
  в неверном каталоге.
- **Пароли в командной строке** — видны в `ps`. Используйте `--password-file` или
  переменные окружения.
- **Секреты в `set -x`** — трассировка печатает всё; отключайте на время работы с
  токенами: `set +x` / `set -x`.

## Идемпотентность

Скрипт должен давать один и тот же результат при повторном запуске. Вместо
«создать пользователя» — «создать, если нет»:

```bash
id -u "$USER_NAME" >/dev/null 2>&1 || useradd -m "$USER_NAME"
mkdir -p /srv/app
ln -sfn /srv/app/releases/"$VERSION" /srv/app/current
```

`ln -sfn` атомарно переключает ссылку, `mkdir -p` не падает, если каталог есть.
Идемпотентность — обязательное свойство скриптов, которые запускает CI или Ansible.

## Логирование в скрипте

Скрипт без логов невозможно разобрать ночью. Минимальный набор:

```bash
log() {
  printf '%s [%s] %s\n' "$(date -Is)" "$1" "$2" >&2
}
log INFO "старт резервного копирования"
log ERROR "нет доступа к $BACKUP_DIR"
```

Правила:

- **всё диагностическое — в stderr**, чтобы stdout оставался данными;
- **уровни** info/warn/error, без «printf везде»;
- **никаких секретов** в логах: пароли, токены, содержимое `.env`;
- **код возврата** должен соответствовать результату.

## Параллельность без сюрпризов

```bash
for host in "${HOSTS[@]}"; do
  ssh "$host" 'uptime' &
done
wait
```

Фоновые процессы дают скорость, но ломают порядок вывода и усложняют
обработку ошибок. Для критичных операций лучше `xargs -P` с явным списком
и проверкой кодов возврата.

## Подробный разбор темы

Надёжный CLI-скрипт валидирует аргументы до побочных эффектов: число параметров, наличие файла, формат значения и допустимые режимы. Сообщение об ошибке должно объяснять ожидаемый синтаксис и возвращать ненулевой код. Для временных файлов и фоновых процессов используйте `trap` на `EXIT`, `INT` и `TERM`, чтобы корректно очищать ресурсы при штатной ошибке или остановке.

`set -e` не означает «любая ошибка немедленно завершит программу» во всех конструкциях: команды в `if`, `&&`, `||` и подстановках имеют особые правила. Поэтому важные операции лучше проверять явно и добавлять контекст к сообщению. Перед запуском в проде проверьте повторное выполнение, частичный отказ и остановку во время операции; именно эти случаи отличают надёжный сценарий от удачного демо.

## Пошаговый сценарий

![Порядок действий: Надёжные скрипты: аргументы, ошибки, trap](assets/img/howto/02-bash--04-scripting-robust.svg)

1. Разберите аргументы и проверьте типы и пути до побочных эффектов.
2. Определите коды ошибок для каждого критичного шага.
3. Добавьте trap для временных файлов и фоновых процессов.
4. Смоделируйте ошибку, сигнал остановки и повторный запуск.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Разберите параметры в начале программы и проверьте, что обязательные пути существуют до записи файлов.

**Как проверить.** Если пользователь забыл аргумент, скрипт сообщает это сразу и не меняет систему.

### Шаг 2

**Что сделать.** Назначьте разные коды завершения для разных ошибок и выводите понятное сообщение в stderr.

**Как проверить.** При ошибке оператор понимает, что именно сломалось, а CI видит ненулевой exit code.

### Шаг 3

**Что сделать.** Через `trap` удаляйте только свой временный файл и корректно завершайте созданный вами фоновый процесс.

**Как проверить.** После успешного запуска, ошибки или Ctrl+C не остаются временные файлы и дочерние процессы.

### Шаг 4

**Что сделать.** Прогоните успешный сценарий, затем искусственно передайте отсутствующий файл и остановите тест через Ctrl+C.

**Как проверить.** Во всех трёх случаях результат предсказуем, очистка срабатывает, повторный запуск не повреждает данные.
