# Как проверять скрипты: shellcheck, bats и дымовые тесты

Скрипт без проверки — это код без тестов, только ошибки в нём дороже: он работает
с файлами, правами и продакшеном. Минимальный набор инструментов доступен в любом
CI.

## shellcheck: статический анализ

```bash
shellcheck deploy.sh
shellcheck -x -s bash scripts/*.sh
```

Типичные находки:

| Код | Проблема | Пример |
| --- | --- | --- |
| SC2086 | неэкранированная переменная | `rm $file` → `rm "$file"` |
| SC2046 | неэкранированная подстановка | `for i in $(ls)` |
| SC2181 | проверка `$?` вместо `if` | `cmd; if [ $? -ne 0 ]` |
| SC2155 | объявление и присвоение одной строкой | `local x=$(cmd)` → две строки |
| SC2016 | одинарные кавычки скрывают переменные | `'$HOME'` |

Запускать shellcheck нужно в CI на каждый pull request. Это самый дешёвый способ
поймать опечатку, которая иначе проявится в три часа ночи.

## Форматирование и стиль

- `shfmt -i 2 -ci` — единое форматирование, меньше шума в диффах;
- `bash -n script.sh` — проверка синтаксиса без выполнения;
- `set -x` в отладке и `PS4` с номером строки:

```bash
PS4='+${BASH_SOURCE}:${LINENO}: '
set -x
```

## bats: тесты для скриптов

`bats` (Bash Automated Testing System) даёт структуру describe/test и ассерты.

```bash
#!/usr/bin/env bats

setup() {
  TMPDIR=$(mktemp -d)
  source ./lib.sh
}

teardown() {
  rm -rf "$TMPDIR"
}

@test "parse_version извлекает номер" {
  run parse_version "v1.2.3"
  [ "$status" -eq 0 ]
  [ "$output" = "1.2.3" ]
}

@test "parse_version падает на мусоре" {
  run parse_version "not-a-version"
  [ "$status" -ne 0 ]
}
```

Запуск: `bats tests/`. В CI устанавливается одной командой
(`apt install bats` или `npm i -g bats`).

## Что тестировать в скриптах

1. **Аргументы**: пустые, неверные, лишние. Скрипт должен падать с кодом 2 и
   понятным сообщением.
2. **Граничные случаи**: пустой каталог, отсутствующий файл, пробел в пути.
3. **Идемпотентность**: второй запуск не ломает результат.
4. **Побочные эффекты**: создаются ли нужные файлы, не остаётся ли мусор.
5. **Коды возврата**: CI должен отличать успех от предупреждения.

## Дымовой тест в контейнере

Самый практичный способ проверить скрипт, который меняет систему, — прогнать его
в одноразовом контейнере:

```bash
docker run --rm -v "$PWD":/work -w /work ubuntu:24.04 bash -c './install.sh && ./verify.sh'
```

Это ловит отсутствующие зависимости и предположения о среде («у меня есть jq»).
Для Terraform/Ansible существуют свои аналоги: `terraform validate`, `ansible-lint`,
`molecule test`.

## Проверка в CI

Минимальный job для bash-скриптов:

```yaml
- name: Проверить скрипты
  run: |
    sudo apt-get install -y shellcheck
    shellcheck -x scripts/*.sh
    bash -n scripts/*.sh
```

Дальше добавляются bats-тесты. Даже эти две команды отсекают большинство ошибок,
которые иначе обнаруживаются в продакшене.

## Антипаттерны проверки

- **Тестировать только happy path.** Ошибка чаще в пустом значении, чем в
  правильном.
- **Проверять `echo`, а не эффект.** Убедитесь, что файл действительно создан.
- **Игнорировать stderr.** Скрипт может вернуть 0 и при этом ругаться в лог.
- **Полагаться на окружение разработчика.** В CI другой пользователь, другие
  версии утилит, нет доступа к сети.

## Подробный разбор темы

Разделяйте статический анализ и поведенческие тесты. ShellCheck находит типовые ошибки quoting и неиспользуемые переменные, но не доказывает корректность бизнес-логики. Bats запускает сценарий с контролируемыми входами и проверяет stdout, stderr и exit code. Изолируйте тест от реальных путей: подменяйте временный каталог и бинарные команды через `PATH`, чтобы случайно не затронуть систему.

Минимальный набор проверок включает нормальный ввод, пустые данные, отсутствующий файл, отказ доступа и повторный запуск. Для shell-функций проверяйте не только «что команда завершилась с 0», но и побочный эффект: появился ли ожидаемый артефакт, остались ли временные файлы. Дымовой тест полезен после сборки, но он дополняет, а не заменяет точечные тесты.

## Пошаговый сценарий

![Порядок действий: Как проверять скрипты: shellcheck, bats и дымовые тесты](assets/img/howto/02-bash--05-testing-shell.svg)

1. Запустите ShellCheck и исправьте предупреждения о quoting и переменных.
2. Изолируйте файлы и команды внутри временного test environment.
3. Проверьте успех, ошибку, пустой ввод и повторный запуск через Bats.
4. Сверьте exit code, вывод и ожидаемые побочные эффекты.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Установите ShellCheck и запустите `shellcheck script.sh`; читайте каждое предупреждение перед исправлением.

**Как проверить.** Ошибки quoting и переменных устранены, а оставшееся исключение объяснено, а не просто скрыто.

### Шаг 2

**Что сделать.** В тестах направляйте файлы в `$BATS_TEST_TMPDIR` и подменяйте внешнюю команду безопасной заглушкой.

**Как проверить.** Тест не пишет в реальные каталоги и не вызывает настоящий production-сервис.

### Шаг 3

**Что сделать.** Добавьте отдельные Bats-тесты на правильный ввод, отсутствующий файл, пустой ввод и повторный запуск.

**Как проверить.** Каждый ожидаемый сценарий получает явную проверку, а не один общий «тест прошёл».

### Шаг 4

**Что сделать.** Сравните код завершения, stdout/stderr и созданные файлы с ожиданиями теста.

**Как проверить.** Тест ловит как неверное сообщение, так и нежелательный побочный эффект.
