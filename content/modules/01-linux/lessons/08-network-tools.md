# Сеть на сервере: ip, ss, tcpdump, mtr

На собеседовании и в инциденте проверяют не знание теории OSI, а умение ответить
на вопрос «почему сервис недоступен» за пять минут. Для этого нужен небольшой
набор команд и порядок их применения.

## Порядок диагностики

Всегда идём от нижнего уровня к верхнему, иначе можно час искать проблему в
приложении, когда не настроен маршрут.

1. Есть ли адрес и линк? `ip -br addr`
2. Есть ли маршрут по умолчанию? `ip route`
3. Резолвится ли имя? `dig +short example.com`
4. Открыт ли порт? `ss -lntp`
5. Доходит ли пакет? `ping`, `mtr`
6. Отвечает ли приложение? `curl -v`

## ip вместо ifconfig

```bash
ip -br addr                 # кратко: интерфейс, состояние, адреса
ip route                    # таблица маршрутов
ip route get 8.8.8.8        # каким маршрутом пойдёт пакет
ip neigh                    # ARP-таблица
```

`ip route get` — недооценённая команда: она сразу показывает интерфейс и источник
адреса для конкретного получателя. Если маршрута нет, вы увидите это до того, как
начнёте проверять firewall.

## ss вместо netstat

```bash
ss -lntp                    # слушающие TCP-порты и процессы
ss -tnp state established   # установленные соединения
ss -s                       # сводка по сокетам
```

Если приложение «не запускается», а в логах пусто, `ss -lntp` покажет, занят ли
порт и кто его держит. `Address already in use` — почти всегда старый процесс,
который не завершился.

Типичная картина: сервис слушает `127.0.0.1:8080`, а балансировщик ходит на
`<ip>:8080`. Изнутри всё работает, снаружи — connection refused. Слушать нужно
`0.0.0.0` (или конкретный внешний адрес), а не loopback.

## DNS: dig и getent

```bash
dig +short api.example.com
dig api.example.com A +noall +answer
dig @1.1.1.1 api.example.com
getent hosts api.example.com
```

Разница `dig` и `getent` важна: `dig` идёт напрямую в DNS, `getent` использует
системный резолвер (`/etc/nsswitch.conf`, `/etc/hosts`). Если `dig` отвечает, а
приложение не может подключиться, проблема в `/etc/hosts`, `resolv.conf` или
NSS — а не в DNS-сервере.

`dig +trace` показывает всю цепочку от корня. Полезно, когда непонятно, кто
отвечает неправильно.

## Проверка доступности: ping, mtr, nc

```bash
ping -c 4 10.0.0.5
mtr -rw -c 20 api.example.com
nc -zv 10.0.0.5 5432
```

`ping` проверяет ICMP, но многие сети его блокируют — неудачный ping не доказывает,
что TCP недоступен. `nc -zv` проверяет конкретный порт. `mtr` combines ping и
traceroute: показывает потери на каждом хопе, что помогает отличить проблему
приложения от проблемы сети.

## tcpdump: смотреть на пакеты

```bash
sudo tcpdump -i any -n port 5432 -c 20
sudo tcpdump -i eth0 -n -A 'tcp port 80 and host 10.0.0.5'
sudo tcpdump -i any -n 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'
```

Читать вывод нужно уметь:

- SYN без SYN-ACK — пакет не дошёл или порт закрыт firewall;
- SYN, затем RST — порт закрыт, но хост доступен;
- повторные ретрансмиссии — потери в сети;
- `Flags [P.]` — данные с подтверждением, нормальный обмен.

`-w file.pcap` сохраняет дамп для анализа в Wireshark. На продакшене сначала
ограничивайте захват фильтром и количеством пакетов: `tcpdump` без фильтра на
нагруженном интерфейсе может заметно нагрузить CPU.

## curl как инструмент диагностики

```bash
curl -v https://api.example.com/health
curl -I --http2 https://example.com
curl -w '\n%{http_code} %{time_connect} %{time_total}\n' -o /dev/null -s https://example.com
curl --resolve api.example.com:443:10.0.0.5 https://api.example.com/
```

- `-v` показывает TLS-рукопожатие, заголовки и версию HTTP;
- `--resolve` позволяет обратиться к конкретному IP, не меняя DNS, — идеально,
  чтобы проверить новую ноду до переключения балансировщика;
- `-w` даёт тайминги: `time_connect` (TCP), `time_appconnect` (TLS),
  `time_total`. По ним видно, где именно медленно.

## Мини-разбор: «сервис недоступен снаружи»

1. `ss -lntp` — сервис слушает `127.0.0.1:8080` → причина найдена.
2. Если слушает `0.0.0.0`, проверяем `iptables -S` / `nft list ruleset`.
3. `curl` с самого хоста работает, снаружи — нет: смотрим security group / firewall.
4. `mtr` показывает потери на последнем хопе — сеть провайдера, а не приложение.

## Что происходит в ядре

Пакет проходит цепочки netfilter: PREROUTING, INPUT, FORWARD, OUTPUT,
POSTROUTING. Правила iptables/nftables решают, принять, отбросить или
преобразовать адрес.

`conntrack` хранит состояние соединений. Без него NAT не знал бы, какому
внутреннему хосту вернуть ответ. Таблица имеет лимит:

```bash
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
conntrack -S
```

Переполнение — типичная причина «пакетов нет, а сеть жива» под высокой
нагрузкой. Лечение: увеличить лимит, сократить время жизни, убрать лишний NAT.

### NAT и порты

SNAT меняет источник, DNAT — назначение. Для каждого соединения нужен порт в
таблице. При тысячах коротких соединений портов не хватает, и новые подключения
получают таймаут.

### Очереди и потери

`ss -lnt` показывает `Recv-Q`/`Send-Q`. Растущая очередь приёма — приложение не
успевает читать; переполнение — потери. `netstat -s`/`nstat` дают счётчики
retransmit, drops, listen overflows.

### MTU и фрагментация

Если MTU на пути меньше, чем думает отправитель, большие пакеты теряются, а
`curl` «висит» на TLS handshake. Проверка:

```bash
ping -M do -s 1472 host
```

1472 + 28 = 1500. Меньший рабочий размер указывает на туннель/VPN.

## Подробный разбор темы

Комбинируйте инструменты по вопросу. `ip addr` показывает адреса интерфейсов, `ip route get <адрес>` — выбранный ядром путь, `ss -lntp` — локальные слушающие сокеты. `tcpdump` помогает увидеть SYN, ответ и повторные передачи; начните с узкого фильтра по адресу и порту и не сохраняйте лишний пользовательский трафик. `mtr` показывает потери и задержки по маршруту, но промежуточный узел может ограничивать ICMP, не теряя трафик приложения.

Сопоставляйте захват на обеих сторонах: если SYN ушёл, но ответа нет, ищите фильтр или обратный маршрут; если handshake состоялся, переходите к TLS и HTTP. В контейнерной среде проверяйте сеть в том же namespace, где работает сервис: вывод `ss` на хосте может не отражать его сокеты.

## Проверьте себя

1. Чем `ss` лучше `netstat` и что показывает флаг `-p`?
2. Почему `dig` может работать, а приложение — нет?
3. Что означает SYN без SYN-ACK в tcpdump?
4. Зачем нужен `curl --resolve`?
