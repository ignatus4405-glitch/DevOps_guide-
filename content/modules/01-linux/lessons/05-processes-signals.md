# Процессы, сигналы и лимиты ресурсов

Linux запускает не «программы», а процессы. Понимание того, как процесс появляется,
чем отличается от дочернего и как им управлять, отличает инженера, который
перезапускает сервис «на удачу», от того, кто понимает, что произойдёт.

## Как появляется процесс

Последовательность всегда одна: `fork()` создаёт копию текущего процесса,
`execve()` заменяет её образ другой программой. Отсюда важное следствие: у любого
процесса есть родитель (PPID). Если родитель умер, процесс усыновляется PID 1 —
в современных системах это systemd.

```bash
ps -o pid,ppid,stat,cmd -p $$
# PID  PPID STAT CMD
# 4211  4199 S    bash
```

Поле `STAT` — состояние процесса. Основные значения:

| Код | Состояние | Что значит |
| --- | --- | --- |
| R | running/runnable | выполняется или ждёт CPU |
| S | sleeping | ждёт события (сеть, диск, таймер) |
| D | uninterruptible sleep | ждёт ввода-вывода, сигналы не доставляются |
| Z | zombie | завершился, но родитель не забрал код возврата |
| T | stopped | остановлен сигналом (Ctrl+Z) |

Много процессов в `D` — почти всегда проблема с диском или сетевой ФС, а не с CPU.
Зомби не потребляют память, но их накопление означает, что родитель не вызывает
`wait()`.

## Сигналы: как правильно останавливать

Сигнал — асинхронное уведомление. Их немного, но путаница между ними приводит к
потере данных.

| Сигнал | Номер | Смысл |
| --- | --- | --- |
| SIGHUP | 1 | «перечитай конфигурацию» (у демонов) |
| SIGINT | 2 | Ctrl+C, запрос прерывания |
| SIGKILL | 9 | немедленно убить, нельзя перехватить |
| SIGTERM | 15 | вежливая просьба завершиться |
| SIGSTOP | 19 | остановить, нельзя перехватить |

Правильный порядок остановки сервиса:

```bash
kill -TERM 4211     # приложение закрывает соединения и завершает работу
sleep 5
kill -KILL 4211     # только если не завершилось
```

`SIGKILL` не даёт приложению сохранить состояние и закрыть соединения — клиенты
увидят обрыв. Поэтому Kubernetes при удалении пода сначала шлёт SIGTERM и ждёт
`terminationGracePeriodSeconds`, и только потом KILL. Если приложение игнорирует
SIGTERM, поды будут умирать по таймауту.

## Приоритеты и лимиты

`nice` меняет приоритет планировщика (от -20 до 19, меньше — важнее). Обычный
пользователь может только понижать приоритет (увеличивать nice), root — повышать.

```bash
nice -n 10 tar -czf backup.tar.gz /var/lib/app     # не мешать продакшену
renice -n 5 -p 4211
```

Лимиты задаются в двух местах: `ulimit` для оболочки и systemd-юнита для сервиса.
Проверить:

```bash
ulimit -n                 # максимум открытых файлов
cat /proc/4211/limits | grep -E "open files|processes"
```

Типичная ошибка: приложение получает `Too many open files`, а `ulimit -n` в
интерактивной оболочке показывает 1024, хотя сервис запущен systemd с другим
значением. Смотреть нужно лимиты **конкретного процесса**, а не своей сессии.

## Где смотреть, что процесс делает

`/proc` — виртуальная ФС с состоянием ядра. Самые полезные файлы:

| Путь | Содержимое |
| --- | --- |
| `/proc/<pid>/cmdline` | аргументы запуска (разделены `\0`) |
| `/proc/<pid>/environ` | переменные окружения |
| `/proc/<pid>/fd/` | открытые файловые дескрипторы |
| `/proc/<pid>/cwd` | текущий каталог |
| `/proc/<pid>/status` | память, потоки, владелец |

```bash
tr '\0' ' ' < /proc/4211/cmdline; echo
ls -l /proc/4211/fd | head
```

Последняя команда показывает, куда процесс пишет и какие сокеты держит. Часто так
находят «забытый» лог-файл, который занимает диск.

## cgroups: лимиты на уровне ядра

Ограничения CPU и памяти в контейнерах — это cgroups v2. Посмотреть лимиты
контейнера можно прямо на хосте:

```bash
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/cpu.max
```

Если приложение убито с кодом 137 (128 + 9), это SIGKILL — чаще всего OOM killer
из-за `memory.max`. Именно поэтому `kubectl describe pod` показывает `OOMKilled`,
а не ошибку приложения.

## Практический разбор: сервис не завершается

Симптом: `systemctl stop app` висит 90 секунд, потом процесс убивается.

1. `systemctl status app` — показывает, что stop job идёт.
2. `ps -o pid,stat,cmd -C app` — процесс в состоянии `S`, значит ждёт.
3. `cat /proc/<pid>/status | grep SigIgn` — проверяем, не игнорируется ли SIGTERM.
4. `strace -p <pid> -e trace=network` — видно, что процесс ждёт ответа от базы.

Причина: приложение закрывает соединения синхронно и ждёт таймаут. Решение —
асинхронное завершение или уменьшение таймаута, а не увеличение
`TimeoutStopSec`.

## Подробный разбор темы

Процесс — это не только команда, но и набор ресурсов и отношений: PID, родитель, открытые файловые дескрипторы, переменные окружения и лимиты. `SIGTERM` просит программу завершиться штатно; `SIGKILL` немедленно прекращает её и не оставляет времени на очистку. Для службы сначала используйте менеджер (`systemctl stop`), а ручной сигнал отправляйте только после проверки PID и владельца процесса.

Когда приложение упирается в число открытых файлов или процессов, сравните лимиты процесса (`/proc/<pid>/limits`) с лимитами пользователя и cgroup. Изменять `ulimit` в интерактивной оболочке недостаточно, если службу запускает systemd: там свой контекст. Перед повышением лимита выясните причину роста — утечка дескрипторов не исчезнет от увеличения потолка.

3. Где смотреть лимит открытых файлов у работающего сервиса, а не у своей оболочки?
