# Процессы, systemd, пакеты и логи

Сервер живёт не файлами, а **процессами**. DevOps-инженер должен уметь ответить на
три вопроса: какой процесс ест ресурсы, кто его запустил, и почему он перезапустился.

## Процессы: наблюдение и управление

```bash
ps aux                      # все процессы с CPU/памятью
ps aux --sort=-%mem | head  # топ по памяти
top / htop                  # интерактивный монитор (htop удобнее)
pgrep -a nginx              # PID процессов по имени
pidof nginx                 # только PID
pstree -p                   # дерево процессов
kill -15 1234               # вежливое завершение (SIGTERM)
kill -9 1234                # жёсткое убийство (SIGKILL, без уборки ресурсов)
```

| Сигнал | Номер | Когда использовать |
| --- | --- | --- |
| SIGTERM | 15 | По умолчанию: процесс завершится корректно |
| SIGKILL | 9 | Процесс завис и не реагирует на 15 |
| SIGHUP | 1 | Перечитать конфигурацию (nginx, sshd) |
| SIGINT | 2 | Как Ctrl+C в терминале |

!!! warning "Важно"
    `kill -9` не даёт процессу закрыть соединения и сохранить данные. Если приложение
    не завершается по `SIGTERM` — это баг приложения: правильный обработчик должен
    закрывать пул соединений и только потом выходить. В Kubernetes такое поведение
    приводит к обрывам запросов при деплое.

## systemd: управление сервисами

`systemd` — система инициализации: именно она запускает сервисы при старте системы
и следит за ними. Юнит-файл описывает, что запускать:

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=MyApp API
After=network-online.target

[Service]
User=appsvc
WorkingDirectory=/opt/app
EnvironmentFile=/etc/myapp/myapp.env
ExecStart=/opt/app/venv/bin/python -m myapp
Restart=on-failure
RestartSec=3
# Ограничения — залог безопасности
NoNewPrivileges=true
ProtectSystem=strict

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload        # после правки юнит-файла
sudo systemctl enable --now myapp   # автозапуск при загрузке + старт сейчас
systemctl status myapp              # состояние, PID, последние строки лога
sudo systemctl restart myapp        # перезапуск
sudo systemctl stop myapp
systemctl list-units --type=service --state=running
systemctl list-unit-files --state=enabled | wc -l
journalctl -u myapp -f              # следить за логом сервиса
journalctl -u myapp --since "1 hour ago" --no-pager
journalctl -p err -b                # ошибки текущей загрузки
journalctl --disk-usage             # сколько занимает журнал
```

!!! tip "Совет"
    `systemctl status` показывает не только «active», но и время запуска, PID и
    последние 10 строк лога — этого обычно достаточно для первой диагностики.
    Если сервис «падает по кругу», смотрите `journalctl -u <сервис> -n 100`.

## Пакеты: apt и dnf

| Действие | Debian/Ubuntu | RHEL/CentOS/Fedora |
| --- | --- | --- |
| Обновить индекс | `sudo apt update` | `sudo dnf check-update` |
| Установить | `sudo apt install nginx` | `sudo dnf install nginx` |
| Обновить всё | `sudo apt upgrade -y` | `sudo dnf update -y` |
| Удалить | `sudo apt remove nginx` | `sudo dnf remove nginx` |
| Найти пакет | `apt search nginx` | `dnf search nginx` |
| Показать файлы пакета | `dpkg -L nginx` | `rpm -ql nginx` |
| Какому пакету принадлежит файл | `dpkg -S /usr/sbin/nginx` | `rpm -qf /usr/sbin/nginx` |
| Показать зависимости | `apt-cache depends nginx` | `dnf repoquery --requires nginx` |

Обновления безопасности — регулярная задача. На десятках серверов её автоматизируют
(Ansible, unattended-upgrades), но **никогда не применяют на прод без staging**:
обновление ядра может потребовать перезагрузки, а новая версия nginx — правки конфига.

## Ресурсы: диск, память, нагрузка

```bash
df -h                          # место на ФС
du -sh /var/log/*              # кто занимает место
find / -xdev -size +1G -type f 2>/dev/null   # большие файлы (без сетевых ФС)
lsof +L1                       # удалённые файлы, удерживаемые процессом (частая причина «диск полон»)
free -h                        # память и swap
vmstat 1 5                     # нагрузка, контексты, swap на лету
uptime                         # load average за 1/5/15 мин
iostat -xz 1 3                 # утилизация дисков (пакет sysstat)
ss -tulpn                      # кто слушает какие порты
```

**Load average** — среднее число процессов в очереди на CPU и в ожидании диска.
Важно сравнивать его с количеством ядер (`nproc`): load 8 на 4 ядрах — перегрузка.

!!! note "Частый инцидент: «диск полон, но du не находит файлов»"
    Классика: приложение удалило лог, но процесс продолжает писать в открытый файл —
    место не освобождается. `lsof +L1` покажет такой файл. Лечение: `truncate -s 0 /proc/<pid>/fd/<fd>`
    или корректный reload приложения. Постоянное решение — ротация логов (logrotate).

## Логи: где смотреть и что искать

| Источник | Где лежит | Как читать |
| --- | --- | --- |
| Systemd-сервисы | journald | `journalctl -u svc -f` |
| Syslog | `/var/log/syslog` (Debian) | `less`, `grep` |
| Приложение | `/var/log/<app>/` | `tail -f`, `grep` |
| Краш-логи ядра | `/var/log/kern.log`, `dmesg` | `dmesg -T \| tail` |
| Аудит | `/var/log/auth.log` | `grep "Failed password"` |

```bash
journalctl -u myapp --since "10 min ago" | grep -i error | tail -50
tail -F /var/log/nginx/error.log          # -F следит даже за пересозданным файлом
zgrep "500 " /var/log/nginx/access.log.*.gz   # поиск в архивах rotation
```

## Реальный сценарий диагностики

> Пользователи жалуются: сайт не открывается. Действия по шагам.

```bash
# 1. Сервис вообще запущен?
systemctl status nginx

# 2. Если упал — почему? Читаем лог.
journalctl -u nginx -n 50 --no-pager

# 3. Слушает ли порт?
ss -tulpn | grep ':80\|:443'

# 4. Что на файловой системе? Иногда «диск полон» ломает запись логов.
df -h /var

# 5. Есть ли конфликт на порту (другой процесс занял 80)?
sudo lsof -i :80

# 6. Ошибки конфигурации проверяем ДО рестарта:
sudo nginx -t && sudo systemctl reload nginx
```

Порядок важен: **сначала факты, потом гипотезы**. Опытные инженеры не рестартуют
сервис «на всякий случай» — рестарт уничтожает улики.

## Пакеты: чем отличаются менеджеры

| Система | Установка | Поиск | Обновление |
| --- | --- | --- | --- |
| Debian/Ubuntu | `apt install pkg` | `apt search pkg` | `apt update && apt upgrade` |
| RHEL/Fedora | `dnf install pkg` | `dnf search pkg` | `dnf upgrade` |
| Alpine | `apk add pkg` | `apk search pkg` | `apk upgrade` |

Проверка, из какого пакета файл:

```bash
dpkg -S /usr/bin/ss        # Debian
rpm -qf /usr/bin/ss        # RHEL
```

Это первое действие, когда нужно понять, что за бинарник в системе и обновляется
ли он пакетным менеджером. Файлы, установленные вручную в `/usr/local`, не
обновляются и часто становятся источником уязвимостей.

## Логи: где что искать

| Источник | Команда | Когда использовать |
| --- | --- | --- |
| systemd journal | `journalctl -u app` | сервисы под systemd |
| Файлы приложения | `/var/log/app/*.log` | приложение пишет само |
| Ядро | `dmesg -T` | OOM, диск, сеть |
| Аутентификация | `/var/log/auth.log` | входы, sudo |
| Пакеты | `/var/log/apt/history.log` | что установили |

`dmesg -T` с человеческим временем обязателен: без `-T` вы увидите секунды с
загрузки и не сопоставите событие с инцидентом.

## Ротация логов

Логи без ротации заполняют диск. `logrotate` делает это по расписанию:

```
# /etc/logrotate.d/app
/var/log/app/*.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}
```

`copytruncate` нужен, если приложение не реагирует на `SIGHUP` и держит файл
открытым. Минус — возможная потеря нескольких строк в момент копирования.
Идеальный вариант — приложение само переоткрывает лог по сигналу.

Проверить конфигурацию без ожидания расписания:

```bash
sudo logrotate -d /etc/logrotate.d/app    # debug, ничего не меняет
sudo logrotate -f /etc/logrotate.d/app    # принудительно
```

## Короткое резюме

- Процессы управляются сигналами: `SIGTERM` корректно, `SIGKILL` — принудительно.
- `systemd` запускает сервисы и хранит их логи в journald.
- Пакеты ставятся через `apt`/`dnf`, обновления не применяют на прод без staging.
- Диагностика идёт по порядку: сервис → лог → порт → диск → конфликты.

## Как ядро выбирает процесс

Планировщик Linux (CFS, а с 6.6 — EEVDF) распределяет CPU между задачами,
стремясь к справедливости с учётом приоритетов (nice). Потоки — единица
планирования, процесс — единица ресурсов.

`load average` показывает не загрузку CPU, а среднее число задач в состоянии
runnable **и** uninterruptible sleep за 1/5/15 минут. Поэтому:

- load 8 на 4 ядрах — очередь на CPU;
- load 8 при простое CPU — часто ожидание диска (D-state).

Проверяйте `vmstat`: колонки `r` (runnable) и `b` (blocked) объясняют, что
именно происходит.

### Context switch

Переключение контекста стоит денег: сохранить регистры, сменить адресное
пространство, прогреться кэшам. Тысячи переключений в секунду — норма для
сетевого сервиса, десятки тысяч — повод посмотреть на блокировки и размер
пулов потоков.

### Приоритеты и nice

`nice` от −20 до 19 влияет на долю CPU. `renice` меняет на ходу. `ionice`
задаёт класс I/O. Это инструменты точечной настройки, а не замена архитектуре:
если сервис конкурирует сам с собой, приоритеты не спасут.

### Signals

SIGTERM — просьба завершиться, SIGKILL — безусловное убийство, SIGHUP —
перечитать конфигурацию (по договорённости), SIGSTOP/SIGCONT — пауза.
Приложение должно обрабатывать SIGTERM: закрыть соединения, дождаться запросов,
выйти с кодом 0. Иначе оркестратор дождётся таймаута и убьёт процесс.

## Подробный разбор темы

Различайте пакет, процесс и службу: пакет доставляет файлы программы, процесс — конкретный запуск с PID, unit systemd описывает желаемое состояние и способ управления. «Пакет установлен» не означает, что приложение запущено; «процесс существует» не означает, что он принимает запросы. Проверяйте всю цепочку: `dpkg -l` или `rpm -q`, `systemctl status`, `ps`, порт через `ss`, затем журнал через `journalctl -u имя-службы`.

Сравнивайте время ошибки с журналами и недавними изменениями. Если служба рестартует, изучите `Main PID`, код выхода и последние сообщения, а не запускайте её снова вслепую. Для установки или обновления в production фиксируйте версию пакета и источник репозитория: это делает откат и воспроизведение поведения возможными.

## Пошаговый сценарий

![Порядок действий: Процессы, systemd, пакеты и логи](assets/img/howto/01-linux--03-processes-packets.svg)

1. Уточните установленную версию пакета и источник репозитория.
2. Проверьте состояние unit и найдите PID фактического процесса.
3. Сверьте listening port с журналом службы за время ошибки.
4. После исправления подтвердите готовность запроса и стабильность процесса.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Запишите имя пакета и посмотрите его версию через менеджер вашей системы: `dpkg -s пакет` или `rpm -q пакет`.

**Как проверить.** Вы знаете установленную версию и можете определить, из какого репозитория она пришла.

### Шаг 2

**Что сделать.** Для службы используйте `systemctl status имя-службы`; найдите строку с состоянием и PID процесса.

**Как проверить.** Служба действительно запущена, а найденный PID относится к нужной программе.

### Шаг 3

**Что сделать.** Выполните `ss -lntp`, чтобы увидеть TCP-порты, и `journalctl -u имя-службы --since "10 minutes ago"`, чтобы открыть свежие записи.

**Как проверить.** Есть совпадение между портом, процессом и временем ошибки; не смотрите только на старые сообщения.

### Шаг 4

**Что сделать.** Если есть тестовая точка проверки, выполните запрос к ней и сразу проверьте `systemctl is-active имя-службы`.

**Как проверить.** Запрос получает ожидаемый ответ, служба остаётся активной и в журнале нет новой ошибки.
