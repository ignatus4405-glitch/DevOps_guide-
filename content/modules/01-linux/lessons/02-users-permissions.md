# Пользователи, права и владельцы файлов

Модель прав Linux отвечает на один вопрос: **кто может что делать с этим файлом**.
Для DevOps это критично: 90 % проблем «сервис не стартует» или «не читается файл»
— это именно права.

![Права доступа](assets/img/linux-permissions.svg)

## Модель прав: три категории по три бита

Права есть у трёх категорий: **владелец (u), группа (g), остальные (o)**.
Для каждой — три бита: **читать (r=4), писать (w=2), исполнять (x=1)**.

```
-rwxr-xr--  1 deploy devs  1200 Oct 12 10:00 run.sh
│└┬┘└┬┘└┬┘     │      │
│ │  │  └── остальные: r--  = 4  (только чтение)
│ │  └───── группа:    r-x  = 5  (чтение и запуск)
│ └──────── владелец:  rwx  = 7  (полный доступ)
└────────── тип: - файл, d каталог, l симлинк
```

Числовая запись складывается: `rwxr-xr--` → `754`. Именно так читаются команды
`chmod 644 файл` и `chmod 600 ключ.pem`.

| Права | Типичное применение |
| --- | --- |
| `600` | приватный SSH-ключ, `.env` с секретами |
| `644` | обычный конфиг или страница сайта (владелец пишет, остальные читают) |
| `700` | приватный каталог (например, `~/.ssh`) |
| `755` | каталог или исполняемый скрипт |
| `750` | каталог, доступный владельцу и группе (частый вариант для веб-корня) |

!!! warning "Важно"
    `chmod 777` не «решает проблему прав», а создаёт дыру: любой процесс (в том
    числе скомпрометированный) сможет изменить файл. Правильное решение —
    определить владельца и группу, например `chown -R www-data:www-data /var/www`.

## Смена владельца и прав

```bash
chown deploy:devs /opt/app/config.yml     # владелец и группа
chown -R nginx:nginx /var/www/html        # рекурсивно (-R) — только осознанно
chmod 640 /etc/app/secrets.env            # владелец rw, группа r, остальные —
chmod +x deploy.sh                        # добавить бит исполнения
umask 027                                 # маска для новых файлов: 640/750
```

**umask** задаёт, какие биты *снимать* при создании файла: файл создаётся как `666 & ~umask`,
каталог — `777 & ~umask`. При `umask 022` файлы получают `644`, каталоги `755`.

## пользователи, группы, sudo

```bash
id                          # кто я и в каких группах
id deploy                   # группы конкретного пользователя
sudo adduser appuser         # создать пользователя
sudo usermod -aG docker appuser   # добавить в группу (нужен релогин!)
groups appuser              # проверить членство в группах
sudo -l                     # что мне разрешено без пароля
sudo -u www-data whoami     # выполнить команду от другого пользователя
```

!!! danger "Осторожно"
    `usermod -aG` без флага `-a` **перезатрёт** список групп пользователя. Команда
    `usermod -G docker deploy` оставит deploy только в группе docker и выкинет
    его из sudo-группы. Всегда используйте `-aG`.

Правила гигиены:

1. Работать под обычным пользователем, `sudo` — точечно.
2. Для сервисов создавать **отдельного** пользователя без права входа в систему:
   `adduser --system --no-create-home --group appsvc`.
3. `sudoers` править только через `visudo` — он проверяет синтаксис (ошибка в файле
   может лишить вас sudo навсегда).
4. Root-вход по SSH отключать, разрешать вход по ключу.

## SSH: как DevOps реально попадает на серверы

```bash
ssh-keygen -t ed25519 -C "deploy@laptop"        # создать ключ (сохраните парольную фразу)
ssh-copy-id deploy@10.0.0.15                    # установить публичный ключ на сервер
ssh deploy@10.0.0.15                            # вход
ssh -i ~/.ssh/id_deploy -p 2222 deploy@host     # указать ключ и порт
ssh-copy-id -i ~/.ssh/id_deploy.pub user@host   # скопировать конкретный ключ
```

Файл `~/.ssh/config` экономит кучу времени:

```ini
Host prod-web
    HostName 10.0.0.15
    User deploy
    IdentityFile ~/.ssh/id_deploy
    Port 2222
```

Теперь достаточно `ssh prod-web`. Для переноса файлов — `scp` или `rsync`:

```bash
rsync -avz --delete ./build/ deploy@prod-web:/opt/app/build/   # синхронизация каталогов
scp file.tar.gz prod-web:/tmp/                                 # разовая копия
```

!!! tip "Совет"
    `rsync --delete` удаляет на приёмнике всё, чего нет в источнике. Проверяйте путь
    **во второй раз после знака `:`** — классическая ошибка приводит к удалению
    каталога на сервере.

## Права на уровне сервисов: ACL и capability

Иногда групп недостаточно: нужен доступ одному пользователю к чужому каталогу.

```bash
setfacl -m u:deploy:r-x /var/www/site        # точечное разрешение (ACL)
getfacl /var/www/site                        # посмотреть ACL
sudo setcap cap_net_bind_service=+ep /usr/local/bin/app   # разрешить порт 80 без root
getcap /usr/local/bin/app
```

ACL полезны в shared-инфраструктуре, capabilities — вместо запуска от root ради
привилегированного порта.

## Короткое резюме

- Права = три категории (владелец, группа, остальные) × три бита (r, w, x).
- `chmod` меняет биты, `chown` — владельца, `umask` — маску новых файлов.
- Для сервисов создают отдельного системного пользователя, `sudo` — по необходимости.
- SSH с ключами и `~/.ssh/config` — базовый инструмент работы с серверами.
