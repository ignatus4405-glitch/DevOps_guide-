# Базовая сетевая диагностика на Linux-сервере

Сетевые проблемы — самая частая причина инцидентов. Здесь разбираем **практический
порядок диагностики** на сервере; теория сетей (TCP/IP, DNS, TLS) — в модуле 4.

## Карта интерфейсов и маршрутов

```bash
ip a                     # адреса и интерфейсы (современная замена ifconfig)
ip -br a                 # кратко: интерфейс, состояние, адрес
ip r                     # таблица маршрутизации (default gateway)
ip n                     # ARP/neighbour-таблица
resolvectl status        # какие DNS-серверы настроены (systemd-resolved)
cat /etc/resolv.conf     # классический конфиг DNS
```

Типовые признаки неполадок: интерфейс в состоянии `DOWN`, отсутствует `default via`,
адрес из диапазона `169.254.x.x` (значит DHCP не ответил).

## Порты: кто слушает и достижим ли

```bash
ss -tulpn                      # все слушающие сокеты с процессами
ss -tulpn | grep ':443'        # конкретный порт
ss -tn state established '( dport = :5432 )'   # установленные соединения к БД
nc -vz db.internal 5432        # проверка доступности порта (netcat)
timeout 3 bash -c "</dev/tcp/db.internal/5432" && echo open  # без extra-пакетов
```

!!! tip "Совет"
    Различайте «слушает ли порт локально» (`ss`) и «доступен ли он с другого хоста»
    (`nc`). Сервис может прекрасно слушать `127.0.0.1:8080`, но быть недоступным извне —
    это самая частая ошибка при деплое: приложение биндится на localhost, а
    прокси/балансировщик не может до него дотянуться.

## DNS: сначала имя, потом всё остальное

```bash
dig api.example.com +short                 # A-запись
dig api.example.com @8.8.8.8 +short        # спросить у конкретного DNS
dig +trace api.example.com                 # пройти всю цепочку от корня
dig -x 10.0.0.15 +short                    # обратная запись (PTR)
getent hosts api.example.com               # как резолвит сама система (учитывает /etc/hosts)
nslookup api.example.com                   # простой вариант
```

Порядок разрешения имён в Linux задаёт `/etc/nsswitch.conf`:
сначала `files` (`/etc/hosts`), затем `dns`. Именно поэтому «у меня работает» —
это часто результат старой записи в `/etc/hosts`.

## HTTP/TLS из терминала

```bash
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com   # код и время
curl -v https://example.com                                                    # полный диалог с TLS
curl -I https://example.com                                                    # только заголовки
curl --resolve api.example.com:443:10.0.0.15 https://api.example.com/health    # проверка до DNS-переключения
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null | openssl x509 -noout -dates
```

Последняя команда показывает срок действия сертификата — быстрый способ проверить
«а не истёк ли сертификат» без открытия браузера. Истечение сертификата — классическая
авария, которую должна предотвращать автоматика (certbot/ACME + алерт за 14 дней).

## Разбор по слоям: пошаговый чек-лист

| Шаг | Команда | Что проверяем |
| --- | --- | --- |
| 1. Имя резолвится? | `dig +short host` | DNS отвечает и верный ли IP |
| 2. Хост доступен? | `ping -c2 host` | есть ли маршрут (ICMP может быть закрыт!) |
| 3. Порт открыт? | `nc -vz host 443` | слушает ли сервис и пускает ли firewall |
| 4. TLS в порядке? | `openssl s_client -connect host:443` | сертификат, цепочка, срок |
| 5. Приложение отвечает? | `curl -v http://host/health` | код ответа, заголовки, тело |
| 6. Что в логах? | `journalctl -u svc -n 100` | причина на стороне приложения |

!!! warning "Важно"
    `ping` не доказательство: ICMP часто блокируют в облаках, а сервис при этом
    работает. И наоборот — `ping` проходит, а `443` закрыт файрволом. Проверяйте
    **тот протокол и порт, который использует приложение**.

## Файрвол и правила доступа

```bash
sudo ufw status verbose          # Ubuntu: активен ли, какие правила
sudo ufw allow 443/tcp           # разрешить порт
sudo firewall-cmd --list-all     # RHEL-семейство
sudo iptables -L -n -v | head -30   # низкоуровневые правила
sudo nft list ruleset | head -40    # современный nftables
```

В облаке к этому добавляются **security groups** — правила на уровне сети провайдера.
Классическая ловушка: приложение поднято, `ufw` настроен, а пользователи не проходят
потому что в security group не открыт порт 443.

## Трассировка и служебные утилиты

```bash
traceroute -n api.example.com     # маршрут до цели (mtr информативнее)
mtr --report -c 20 api.example.com
tcpdump -i any -n port 443 -c 20   # первые 20 пакетов на порту
sudo tcpdump -i any -n -w /tmp/dump.pcap 'tcp port 8080'  # запись для анализа в Wireshark
ss -s                             # сводка по сокетам (сколько всего открыто)
```

`tcpdump` — тяжёлая артиллерия: включайте фильтры и ограничение по количеству пакетов,
иначе легко положить производительность сервера.

## Короткое резюме

- Диагностика идёт снизу вверх: интерфейс → маршрут → DNS → порт → TLS → приложение → логи.
- `ss` показывает локальные сокеты, `nc`/`curl` — реальную достижимость.
- `openssl s_client` проверяет сертификат, `dig` — DNS, `tcpdump` — трафик.
- В облаке учитывайте security groups: они вне хоста, но могут блокировать всё.
