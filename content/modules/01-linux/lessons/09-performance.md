# Диагностика производительности: CPU, память, диск

«Сервер тормозит» — не диагноз. Задача инженера — за несколько минут определить,
какой ресурс стал узким местом, и подтвердить это цифрами. Разберём метод и
команды, которые действительно нужны.

## Метод USE

Для каждого ресурса проверяют три величины:

- **Utilization** — насколько ресурс занят (0–100 %);
- **Saturation** — есть ли очередь к ресурсу;
- **Errors** — есть ли ошибки.

| Ресурс | Utilization | Saturation | Errors |
| --- | --- | --- | --- |
| CPU | `top`, `mpstat` | load average, `runq-sz` | machine check |
| Память | `free`, `vmstat` | swap in/out, OOM | dmesg |
| Диск | `iostat -x` | `aqu-sz`, `await` | dmesg, smartctl |
| Сеть | `sar -n DEV` | retransmits, drops | `ip -s link` |

Если utilization низкая, а saturation высокая — ресурс перегружен очередью, что
хуже, чем просто высокая загрузка.

## CPU: load average не равен загрузке

```bash
uptime
# load average: 4.12, 3.80, 3.10
nproc
```

Load average — среднее число процессов в состоянии R и D. На 4-ядерной машине
значение 4 близко к пределу, но **в load входят и процессы, ждущие диск**. Поэтому
load 8 при CPU 20 % означает проблему с вводом-выводом, а не с процессором.

```bash
top -b -n1 | head -15
mpstat -P ALL 1 5
pidstat -u 1 5
```

Смотреть нужно на:

- `%us` — пользовательский код; высокий — приложение считает;
- `%sy` — ядро; высокий — много системных вызовов, часто сеть или файлы;
- `%wa` — ожидание ввода-вывода; высокий — диск;
- `%st` — steal; в виртуализации означает, что CPU забрал гипервизор.

`%st` выше 5–10 % — повод жаловаться провайдеру или переезжать, а не
оптимизировать приложение.

## Память: кэш — это хорошо

```bash
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           15Gi        6.2Gi       1.1Gi       200Mi        8.4Gi        8.9Gi
```

Главная колонка — **available**, а не free. Linux использует свободную память под
кэш файлов и отдаёт её при необходимости. «Мало free» — нормальная картина.

Реальные признаки нехватки:

- `si`/`so` в `vmstat` стабильно больше нуля — активный swap;
- OOM killer в `dmesg`;
- рост `pgmajfault` — страницы читаются с диска.

```bash
vmstat 1 10
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
```

Память процесса:

```bash
ps -eo pid,rss,vsz,comm --sort=-rss | head
pmap -x <pid> | tail -1
```

`RSS` — реально занятая физическая память, `VSZ` — виртуальное адресное
пространство (обычно намного больше и само по себе не проблема).

## Диск: iostat и очередь

```bash
iostat -xz 1 5
df -h
```

Ключевые колонки:

| Колонка | Смысл | Тревожное значение |
| --- | --- | --- |
| `%util` | доля времени, когда диск занят | > 80 % |
| `await` | среднее время ожидания I/O, мс | > 20 мс для SSD |
| `aqu-sz` | средняя длина очереди | > 2–3 |
| `r/s`, `w/s` | операций в секунду | зависит от диска |

Высокий `await` при низком `%util` бывает на сетевых ФС и облачных дисках с
лимитом IOPS. Проверяйте лимиты провайдера: иногда «медленный диск» — это
исчерпанная квота.

Кто именно грузит диск:

```bash
iotop -oPa
pidstat -d 1 5
```

## Сеть

```bash
sar -n DEV 1 5
ip -s link show eth0
ss -s
```

Растущие `dropped`/`overrun` на интерфейсе — переполнение очередей. `retrans`
в `ss -ti` — потери или таймауты. На контейнерных хостах часты проблемы с
conntrack: `dmesg | grep conntrack`.

## Инструмент на все случаи: perf

```bash
perf top
perf stat -p <pid> sleep 5
perf record -F 99 -p <pid> -- sleep 10
perf report
```

`perf` показывает, в каких функциях ядро и приложение проводят время. Это
следующий шаг после того, как вы поняли, что узкое место — CPU. Для интерпретации
нужны символы (debug symbols) и базовое понимание стека.

## Последовательность разбора

1. `uptime` и `nproc` — есть ли вообще нагрузка.
2. `vmstat 1` — CPU, память, swap, I/O одним взглядом.
3. `iostat -xz`, `iotop` — если `%wa` или `b` высокие.
4. `pidstat`/`top` — какой процесс.
5. `perf` или логи приложения — почему именно он.

Фиксируйте цифры до и после изменения. «Стало быстрее» без замера — не результат,
а впечатление.

## Метод, а не догадки

Порядок диагностики производительности:

1. **Симптом** — что именно медленно и для кого.
2. **Метрика** — latency, throughput, ошибки; смотрим на график, а не на один
   замер.
3. **Ресурс** — CPU, память, диск, сеть: какой из них на пределе.
4. **Процесс** — кто именно потребляет и почему.
5. **Проверка гипотезы** — изменение и повторный замер.

Правило: не оптимизируйте то, что не измерили. «Кажется, тормозит диск» —
не гипотеза, пока `iostat` не покажет очередь.

## Что смотреть в первую очередь

| Симптом | Инструмент | Что искать |
| --- | --- | --- |
| высокая load average | `uptime`, `vmstat` | runnable vs blocked |
| память | `free -m`, `vmstat` | swap, page faults |
| диск | `iostat -x 1` | await, %util |
| сеть | `ss -s`, `sar -n DEV` | retransmits |

`load average` выше числа ядер не всегда означает CPU: в очереди могут стоять
процессы, ждущие диск.

## Когда виноват не сервер

Частая ошибка — искать проблему в приложении, когда её нет. Проверьте DNS,
балансировщик, клиент и сеть до того, как перезапускать сервисы. Перезапуск
стирает следы и делает разбор невозможным.

## Подробный разбор темы

Сначала определите симптом и интервал: растёт latency, очередь запросов или просто средняя загрузка? Снимите базовую картину `uptime`, `top`, `vmstat 1`, `iostat -xz 1` и `pidstat`; затем сравните с нормальным периодом и отметьте конкретный ресурс. Высокий load average сам по себе не означает перегруженный CPU: в Linux в него входят процессы, ожидающие диск.

Разделяйте наблюдение и причину. Большой `%iowait` указывает на ожидание ввода-вывода, но не говорит, какой запрос создал очередь; высокий RSS не доказывает утечку, пока не посмотрена динамика. Ищите корреляцию с деплоем, задачей или ростом трафика. Меняйте один параметр за раз, фиксируйте результат и не увеличивайте ресурсы до понимания, что именно ограничивает пропускную способность.

## Проверьте себя

1. Почему load average может быть высоким при низкой загрузке CPU?
2. Какую колонку `free -h` нужно смотреть и почему?
3. Что означает высокий `await` при низком `%util`?
4. В каком порядке вы будете искать причину «сервер тормозит»?
