# Хуки и локальные проверки до push

Ошибку дешевле поймать на ноутбуке, чем в CI за 10 минут и ещё дешевле, чем в
продакшене. Git-хуки — механизм, который запускает проверки автоматически в
нужный момент.

## Что такое хук

Хук — исполняемый файл в `.git/hooks/`. Git вызывает его на определённых событиях.
Основные:

| Хук | Когда | Типичное применение |
| --- | --- | --- |
| `pre-commit` | до создания коммита | линтер, форматтер, секреты |
| `commit-msg` | проверка сообщения | Conventional Commits, номер задачи |
| `pre-push` | перед отправкой | быстрые тесты |
| `post-merge` | после merge | обновить зависимости |

Важно: `.git/hooks` **не версионируется**. Командные хуки распространяют через
`core.hooksPath` или фреймворк `pre-commit`.

## Простейший pre-commit

```bash
#!/usr/bin/env bash
set -euo pipefail
changed=$(git diff --cached --name-only --diff-filter=ACM | grep -E '\.(py|sh)$' || true)
[ -z "$changed" ] && exit 0
ruff check $changed
shellcheck $changed
```

Установка:

```bash
cp .githooks/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Минус: `$changed` развалится на путях с пробелами — для надёжности используйте
`xargs -0` и `-z`.

## pre-commit framework

Стандарт де-факто для команд — `pre-commit` (Python). Конфигурация версионируется
и подтягивает готовые хуки.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: detect-private-key
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
      - id: ruff-format
  - repo: https://github.com/shellcheck-py/shellcheck-py
    rev: v0.10.0.1
    hooks:
      - id: shellcheck
```

```bash
pre-commit install
pre-commit run --all-files
pre-commit autoupdate
```

Плюсы: единая версия для всех, кэш окружений, легко обновлять. Именно так делают
большинство зрелых репозиториев.

## Защита от секретов

`detect-private-key`, `gitleaks`, `trufflehog` на pre-commit ловят ключи до того,
как они попадут в историю. Это важно: удалить секрет из истории сложно, а из
форков GitHub — невозможно.

```bash
gitleaks protect --staged --redact
```

Если секрет уже попал в коммит:

1. Немедленно отозвать ключ (ротация) — это первое действие.
2. Вычистить историю (`git filter-repo`), если секрет был в публичном репозитории.
3. Уведомить команду и проверить использование ключа.

Ротация важнее чистки: пока ключ действителен, он уже скомпрометирован.

## Хуки в CI vs локально

| Локальные хуки | CI |
| --- | --- |
| быстрая обратная связь | авторитетная проверка |
| можно обойти `--no-verify` | обойти нельзя |
| требуют установки | работает всегда |
| экономят минуты CI | защищают main |

Хуки — удобство, а не защита. Обязательные проверки должны быть в CI и в branch
protection, иначе кто-то однажды сделает `git push --no-verify`.

## commit-msg: порядок в истории

```bash
#!/usr/bin/env bash
pattern='^(feat|fix|docs|chore|ci|refactor|test)(\(.+\))?: .{5,}'
grep -qE "$pattern" "$1" || {
  echo "Сообщение не по Conventional Commits: $pattern" >&2
  exit 1
}
```

Такой хук делает changelog автоматическим: из сообщений извлекаются типы
изменений и версия поднимается по правилам semver.

## Хуки и CI: кто за что отвечает

Локальные хуки экономят время, серверные — защищают общую ветку. Разумное
разделение:

| Проверка | Локально | В CI |
| --- | --- | --- |
| форматирование | да (быстро) | да (как gate) |
| линтер | да | да |
| unit-тесты | по желанию | да |
| интеграционные | нет | да |
| сканер секретов | да | да |

Локальные хуки легко обойти (`--no-verify`), поэтому они не могут быть
единственной защитой. Обязательные проверки должны жить в CI и в правилах
защиты ветки.

Хороший `pre-commit` занимает секунды. Если он длится минуту, разработчики
начнут его отключать — и потеряется даже та польза, что была.

## Подробный разбор темы

Hook — удобный быстрый фильтр, но он выполняется в локальной среде разработчика, поэтому его нельзя считать единственной границей безопасности. Настройте одинаковые команды в CI и сделайте локальный hook лёгким: форматирование, lint, быстрые тесты. Длительные интеграционные проверки обычно должны оставаться в pipeline, иначе разработчики будут отключать hook ради скорости.

Зафиксируйте конфигурацию через управляемый инструмент (`pre-commit`, npm scripts или репозиторный bootstrap), а не через неотслеживаемый `.git/hooks`. Покажите ясную ошибку и команду для исправления. Не используйте `--no-verify` как нормальный путь; если есть обоснованное исключение, задокументируйте его и обеспечьте обязательную проверку на сервере.

## Пошаговый сценарий

![Порядок действий: Хуки и локальные проверки до push](assets/img/howto/03-git--05-hooks.svg)

1. Выберите быстрые проверки, которые полезно запускать до commit.
2. Зафиксируйте hook-конфигурацию вместе с репозиторием.
3. Покажите точную команду исправления; не обходите hook без документированного экстренного основания.
4. В любом случае дождитесь обязательных серверных проверок CI.
