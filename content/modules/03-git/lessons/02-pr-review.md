# Pull request, ревью и защита main

Pull request (PR) — это не «просьба разрешить», а **точка контроля качества и
обмена знаниями**. Для DevOps-инженера PR — основной способ менять пайплайны и
инфраструктуру безопасно: изменения проходят ревью и автоматические проверки до main.

## Как выглядит хороший PR

| Элемент | Плохо | Хорошо |
| --- | --- | --- |
| Размер | 2000 строк «всё сразу» | < 400 строк, один смысл |
| Заголовок | «фикс» | `fix(ci): кэшировать pip, сборка с 8 до 3 минут` |
| Описание | пусто | что, зачем, как проверить, риск отката |
| Тесты | «проверю на проде» | новые тесты + зелёный пайплайн |
| Скриншоты | — | для UI/дашбордов приложены |
| Миграции | «потом» | обратно совместимые, порядок выката описан |

Шаблон описания, который стоит скопировать в репозиторий:

```markdown
## Что сделано
Кэширование зависимостей в пайплайне сборки.

## Зачем
Сборка длилась 8 минут, стала 3. Меньше ожидания в PR.

## Как проверял
- локально: прогон тестов,
- в CI: два push, шаг cache hit,
- сравнение времени сборки (ссылки).

## Риск и откат
Кэш может устареть: ключ включает hash requirements.txt. Откат — revert PR.
```

## Ревью: как давать и как получать

**Давая ревью**, отвечайте на вопросы: изменение корректно? безопасно? сопровождаемо?
не ломает ли обратную совместимость? Есть ли тесты? Что будет при отказе зависимости?

Приёмы эффективного ревью:

1. **Сначала машина, потом человек.** Линтеры, тесты, сканеры должны отсеять банальности до ревьюера.
2. **Комментарии разных уровней.** `nit:` — мелочь, `question:` — уточнение, `blocker:` — без этого нельзя мержить.
3. **Спрашивайте про эксплуатацию.** «Как поймём, что сломалось?», «Что в логах при ошибке?».
4. **Не переписывайте чужие решения молча** — предложите и объясните.

**Получая ревью**, не спорьте о вкусах, а уточняйте критерии: «какие требования у
этого решения?». Отвечайте на каждый комментарий (даже «исправил») — так видно, что
ничего не потерялось.

## Защита ветки main

Branch protection (GitHub → Settings → Branches) включает правила:

| Правило | Зачем |
| --- | --- |
| Require pull request before merging | нет прямых пушей в main |
| Require approvals (1–2) | обязательное ревью |
| Require status checks (CI) | не мержим красный пайплайн |
| Require linear history | понятная история без верёвок |
| Require signed commits (в строгих компаниях) | подтверждение авторства |
| Require conversation resolution | все замечания закрыты |
| Restrict force-push | защита от перезаписи истории |

## Теги и версии

```bash
git tag -a v1.4.0 -m "Релиз 1.4.0: health endpoint, кэш сборки"
git push origin v1.4.0
git tag -l "v1.*" --sort=-v:refname | head -5
```

Версионирование по семантике (semver): **MAJOR** — несовместимые изменения,
**MINOR** — новая функциональность, **PATCH** — исправления. Теги — триггер для
сборки релиза: именно на них будет работать GitHub Actions в этом курсе.

```gitignore
# секреты и окружение

```

!!! danger "Осторожно"
    Если секрет всё же попал в историю — недостаточно удалить файл новым коммитом:
    он останется в истории и в форках. Действия: **немедленно отозвать ключ/токен**,
    затем почистить историю (`git filter-repo`, BFG) и сообщить команде. Отзыв ключа —
    обязателен, потому что утечку уже могли увидеть.

## Короткое резюме

- PR — механизм контроля качества: маленький размер, понятное описание, зелёный CI.
- Ревью автоматизируется линтерами, человеческое ревью смотрит на смысл и эксплуатацию.
- Branch protection защищает main: PR, approvals, status checks, запрет force-push.
- Теги — точка отсчёта релиза; семантика версий определяет ожидания потребителей.
