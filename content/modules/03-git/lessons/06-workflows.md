# Ветвление: trunk-based, GitFlow и релизные ветки

Выбор модели ветвления — не вкусовщина, а следствие того, как команда выпускает
изменения. Одна и та же схема может ускорять поставку и мешать ей.

## GitFlow: когда он уместен

Классическая схема: `main`, `develop`, `feature/*`, `release/*`, `hotfix/*`.

```
main ─────●──────────────●─────────
           \            /
release/1.4 \──●──●────/
             \        /
develop ──●───●──●───●──●──
```

Плюсы: явные релизы, поддержка нескольких версий, понятный hotfix.
Минусы: много ветвей, долгие merge, «develop» отстаёт от продакшена.

Уместен для продуктов с версионированными релизами (десктоп, библиотеки,
on-premise), где нужно поддерживать 1.x и 2.x одновременно.

## Trunk-based development

Все работают в коротких ветках (до 2 дней) и часто сливаются в `main`. Релиз —
тег на `main`, а не отдельная ветка.

Правила:

1. Ветка живёт не дольше 1–2 дней.
2. Незаконченное скрывается за feature flag.
3. `main` всегда готов к деплою.
4. CI на каждый коммит, CD — автоматически.

Почему это работает: маленькие изменения проще ревьюить, быстрее тестировать и
безопаснее откатывать. Google, Netflix и большинство SaaS-компаний работают так.

## Release-ветки и hotfix

Даже в trunk-based бывают периоды стабилизации:

```
main ──●──●──●──●──●──●──
        \           \
release/1.4 ──●──────●──── (только фиксы)
```

Hotfix:

```bash
git switch -c hotfix/payment-timeout release/1.4
# фикс
git commit -m 'fix: таймаут платежного шлюза'
git switch release/1.4 && git merge --no-ff hotfix/payment-timeout
git tag -a v1.4.1 -m 'hotfix 1.4.1'
git push origin release/1.4 --tags
git switch main && git cherry-pick <fix-sha>   # не забыть про main!
```

Самая частая ошибка — забыть перенести фикс в `main`. Тогда следующий релиз
снова содержит баг. Автоматизируйте проверку или используйте один источник правды.

## Feature flags вместо долгих веток

```python
if flags.enabled("new_checkout", user_id=user.id):
    return new_checkout(cart)
return old_checkout(cart)
```

Код попадает в `main` сразу, но включается по флагу. Это позволяет:

- мержить чаще и мелкими порциями;
- включать функциональность для 1 % пользователей;
- мгновенно выключать при инциденте, не делая деплой.

Требования: флаг должен иметь владельца и срок жизни. «Временные» флаги живут
годами и превращают код в лабиринт.

## Защита main

Обязательный минимум:

- нельзя push напрямую;
- обязательный review (хотя бы один);
- зелёный CI;
- запрет force-push;
- подпись коммитов (опционально);
- линейная история или squash (по договорённости).

```bash
gh api -X PUT repos/{owner}/{repo}/branches/main/protection \
  -F enforce_admins=true \
  -F required_pull_request_reviews.required_approving_review_count=1
```

Защита без зелёного CI бессмысленна: она не даёт сломать main, но не мешает
смержить непроверенный код.

## Как выбрать

| Признак | Рекомендация |
| --- | --- |
| SaaS, деплой несколько раз в день | trunk-based |
| Несколько поддерживаемых версий | release-ветки |
| Регулярные релизы раз в квартал | GitFlow или release-ветки |
| Маленькая команда, один продукт | trunk-based с короткими ветками |
| Регулируемая отрасль, аудит изменений | trunk-based + подписанные теги |

Модель можно менять: главное — не тащить ритуалы GitFlow в команду, которая
деплоит каждый час.

## Практика: как выбрать модель ветвления

Модель нужна не для красоты, а чтобы ответить на три вопроса:

1. Как часто выкатываем?
2. Кто и как проверяет изменение?
3. Как откатываем?

Если релизы ежедневные — trunk-based с короткоживущими ветками и feature flags.
Если релизы редкие и версии поддерживаются параллельно — release-ветки.
GitFlow оправдан в редких случаях, когда есть долгие параллельные версии, но
для веб-сервиса он добавляет церемонии без пользы.

Признак неверной модели: ветка живёт неделями и конфликтует при каждом merge.
В этом случае проблема не в Git, а в размере изменений.

## Что ломается на практике

| Проблема | Причина | Лечение |
| --- | --- | --- |
| долгие merge-конфликты | долгоживущие ветки | дробить изменения |
| «кто-то сломал main» | нет защиты ветки | required checks |
| непонятные релизы | нет тегов | semver + автогенерация |
| откат невозможен | деплой из ветки | деплой по тегу/образу |

Git — инструмент договорённостей. Если договорённости нет, никакая модель не
поможет.

## Подробный разбор темы

Trunk-based development сокращает время жизни веток и поощряет маленькие интеграции; feature flags помогают отделить выкладку кода от включения функции. GitFlow может быть оправдан, если продукт поддерживает несколько версий и длительные релизные циклы, но добавляет правила слияния и синхронизации. Выбирайте модель по времени обратной связи, размеру команды и способу поставки.

Проверьте процесс на реальном изменении: где запускается CI, как создаётся release candidate, что происходит с hotfix и как изменения возвращаются в основную ветку. Если приходится регулярно вручную синхронизировать несколько долгоживущих веток, это стоимость модели, которую нужно явно принять. Наличие ветки `develop` само по себе не делает релиз надёжнее.
