# История как инструмент: reflog, cherry-pick, bisect

Git хранит не «текущую версию», а граф изменений. Это даёт три суперспособности:
восстановить потерянное, перенести отдельный коммит и найти коммит, который всё
сломал. Без них работа с Git превращается в осторожное переписывание файлов.

## reflog: страховка от любой ошибки

`reflog` — журнал перемещений HEAD. Он хранит записи даже для «потерянных» коммитов
после `reset --hard` или неудачного rebase.

```bash
git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# 9f8e7d6 HEAD@{1}: commit: feat: add retry
git reset --hard HEAD@{1}      # вернуть коммит
```

Ключевое: коммит не удаляется сразу, пока на него ссылается reflog (по умолчанию
90 дней для достижимых, 30 для недостижимых). Поэтому `reset --hard` почти всегда
обратим — пока вы не сделали `git gc --prune=now`.

## reset, revert, checkout: что выбрать

| Команда | Что делает | Когда |
| --- | --- | --- |
| `git reset --soft HEAD~1` | убирает коммит, изменения в индексе | переделать сообщение/состав |
| `git reset --mixed HEAD~1` | убирает коммит и из индекса | пересобрать коммит |
| `git reset --hard HEAD~1` | убирает и изменения | только локально и осознанно |
| `git revert <sha>` | создаёт обратный коммит | отмена в общей ветке |
| `git checkout <sha> -- file` | достаёт файл из истории | вернуть отдельный файл |

В общих ветках (`main`, `develop`) используют `revert`: он не переписывает
историю у коллег. `reset` — инструмент локальной правки.

## cherry-pick: перенести один коммит

Нужен, когда фикс сделан в `main`, а релизная ветка должна получить только его.

```bash
git switch release/1.4
git cherry-pick 4f2a1c9
# конфликт:
git status
# правим файлы
git add .
git cherry-pick --continue
# или отменить
git cherry-pick --abort
```

Осторожно с повторным применением: cherry-pick создаёт **новый** коммит с другим
SHA. Если потом ветки сольются, Git может применить изменение дважды. После
переноса в релизную ветку обычно нужен и merge обратно в `main`, чтобы история
сошлась.

## bisect: найти сломавший коммит

Есть 200 коммитов и непонятно, какой внёс регрессию. Вместо чтения — бинарный
поиск.

```bash
git bisect start
git bisect bad                 # текущий сломан
git bisect good v1.3.0         # этот работал
# Git переключает на середину, вы проверяете
npm test                       # или ручная проверка
git bisect good                # или bad
# ... 7–8 шагов для 200 коммитов
git bisect reset
```

Автоматизация:

```bash
git bisect start HEAD v1.3.0
git bisect run pytest tests/test_payments.py -q
```

`bisect run` сам прогоняет команду и находит первый плохой коммит. Это самый
быстрый способ ответить на вопрос «когда это сломалось».

## blame и log: кто и когда

```bash
git blame -L 40,60 src/app.py
git log --oneline -- src/app.py
git log -S 'retry_count' --oneline     # когда появилась/исчезла строка
git log --since='2 weeks ago' --author='Anna' --oneline
```

`-S` (pickaxe) ищет коммиты, где изменилось количество вхождений строки. Это
незаменимо при расследовании: «кто добавил этот флаг и зачем».

`git blame` показывает последнего автора строки, а не автора логики. Полезнее
смотреть на коммит целиком: `git show <sha>`.

## Работа с тегами

```bash
git tag -a v1.4.0 -m 'release 1.4.0'
git push origin v1.4.0
git describe --tags --always
```

Аннотированный тег хранит автора, дату и сообщение. Легковесный (`git tag v1.4.0`)
— просто указатель. Для релизов используют аннотированные: по ним строят changelog
и проверяют артефакты.
