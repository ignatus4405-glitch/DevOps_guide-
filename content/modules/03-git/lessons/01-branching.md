# Ветки, merge и rebase

Git хранит историю как граф коммитов. **Ветка — это просто указатель на коммит**,
поэтому она бесплатна: создать ветку = записать один хеш.

![Ветвление и pull request](assets/img/git-branching.svg)

## Ежедневный цикл

```bash
git switch -c feature/health-check     # новая ветка от текущей
git status                              # что изменено
git add -p                              # выбрать изменения по кускам (аккуратный коммит)
git commit -m "feat(api): health endpoint"   # conventional commits
git push -u origin feature/health-check
# после ревью и merge ветку удаляем
git switch main && git pull --ff-only
git branch -d feature/health-check
```

| Команда | Что делает | Когда нужна |
| --- | --- | --- |
| `git switch -c name` | создать и переключиться | начали задачу |
| `git switch -` | вернуться на предыдущую ветку | быстро переключиться |
| `git fetch --prune` | обновить данные и убрать исчезнувшие ветки | ежедневно |
| `git log --oneline --graph --decorate -15` | понять историю | перед merge |
| `git diff main...HEAD` | что изменит ваша ветка в main | перед PR |
| `git blame -L 40,60 file` | кто и когда менял строки | при разборе бага |

## Merge vs rebase: в чём разница

```
merge:   main  A---B-------M        (M — merge-коммит, история ветвится)
                 \         /
        feature   C---D---E

rebase:  main  A---B---C'---D'---E' (линейная история, ветка «переехала»)
```

| Стратегия | Плюсы | Минусы | Где применять |
| --- | --- | --- | --- |
| `merge` | сохраняет реальную историю, безопасен | «шумные» merge-коммиты | merge PR в main |
| `squash merge` | один коммит на задачу, чистая main | теряются промежуточные коммиты | большинство команд |
| `rebase` | линейная история, удобно читать | переписывает хеши (нельзя для опубликованных веток) | обновление локальной ветки перед PR |

```bash
git switch feature/x
git rebase main                  # перенести свои коммиты поверх свежего main
# если конфликт: правим файл, затем
git add file && git rebase --continue     # или: git rebase --abort
git push --force-with-lease      # безопасный force: не затрёт чужие коммиты
```

!!! warning "Важно"
    Никогда не делайте `rebase` (и уж точно `push --force`) в `main`: коллеги получат
    расхождение истории и потеряют работу. Правило: **переписываем только свои
    локальные ветки**, а для чужих изменений используем `revert`.

## Разрешение конфликтов

Конфликт возникает, когда два коммита меняют один и тот же кусок. Git оставляет маркеры:

```
<<<<<<< HEAD                  (ваша версия — то, что в текущей ветке)
timeout = 30
=======
timeout = 60                  (входящая версия)
>>>>>>> feature/timeouts
```

Порядок действий:

```bash
git status                     # список конфликтных файлов
# редактируем файл: выбираем нужное, маркеры <<< === >>> удаляем
git add conflict_file.conf
git commit                     # при merge; при rebase — git rebase --continue
```

Практика: сначала разберитесь, *почему* изменились обе стороны (часто нужен не
выбор, а объединение), затем проверьте результат тестами. Конфликты в generated-файлах
и lock-файлах стоит решать регенерацией, а не руками.

## Переписывание истории аккуратно

```bash
git commit --amend                # исправить последний коммит (сообщение/файлы)
git rebase -i HEAD~3              # переставить, объединить (squash) три последних коммита
git reset --soft HEAD~1           # расформировать коммит, оставив изменения в индексе
git stash push -m "wip"           # отложить грязь, чтобы переключиться
git stash pop
```

## Conventional commits и зачем это DevOps-инженеру

```
feat(api): добавить /health
fix(ci): не запускать пайплайн дважды на один push
chore(deps): обновить base image до python:3.12-slim
docs(readme): описать переменные окружения
```

Формат `type(scope): описание` даёт машиночитаемую историю: из неё генерируются
changelog, автоматически определяется версия (semantic-release) и понятно, что
попадёт в релиз. В этом курсе сообщения коммитов используются генератором релизов.

## Служба спасения

```bash
git reflog                        # все перемещения HEAD — здесь находятся «потерянные» коммиты
git checkout <hash>               # посмотреть на старый коммит (detached HEAD)
git switch -c rescue <hash>       # сделать из него ветку
git restore --staged file         # убрать из индекса
git restore file                  # отменить изменения в файле
git revert <hash>                 # безопасный «анти-коммит» — отмена в main
git clean -nd                     # что будет удалено (-n — примерка, без -n удалит!)
```

!!! tip "Совет"
    `git revert` предпочтительнее «ручной отмены»: он оставляет след в истории,
    объясняющий откат. А `git reflog` спасает почти всегда — коммиты в Git не
    исчезают мгновенно после отмены.

## Анатомия ветки и коммита

Ветка в Git — это просто указатель на коммит (40-символьный SHA). HEAD — указатель
на текущую ветку. Отсюда всё поведение:

```bash
cat .git/HEAD                 # ref: refs/heads/main
git rev-parse main            # SHA коммита
git cat-file -p HEAD          # содержимое: tree, parent, author, message
```

Коммит состоит из снимка дерева (tree), ссылки на родителя (или двух при merge),
автора и сообщения. Изменения вычисляются как разница деревьев — Git не хранит
«дельты по файлам» в том смысле, в котором их обычно представляют.

## Fast-forward, three-way и squash

| Тип merge | Что происходит | Когда |
| --- | --- | --- |
| fast-forward | указатель просто сдвигается | ветка не расходилась с main |
| three-way | создаётся merge-коммит с двумя родителями | обе ветки имели коммиты |
| squash | все коммиты ветки становятся одним | feature-PR в main |
| rebase | коммиты переносятся на новую базу | локальная уборка истории |

```bash
git merge --ff-only feature      # откажется, если нужен merge-коммит
git merge --no-ff feature        # всегда создавать merge-коммит
git merge --squash feature       # подготовить один коммит
```

`--ff-only` полезен в CI: он проверяет, что ветка актуальна и не потребует
неожиданного merge.

## Что делать с «грязной» историей

Перед PR полезно привести коммиты в порядок:

```bash
git rebase -i HEAD~5
# pick   a1b2c3d feat: add endpoint
# squash 9f8e7d6 fix typo
# reword 7c6b5a4 feat: add tests
```

В интерактивном rebase доступны `pick`, `reword`, `edit`, `squash`, `fixup`,
`drop`. Правило: переписывать историю можно только в своей ветке, которую никто
не забирал.

## Полезные настройки

```bash
git config --global pull.rebase true          # pull через rebase, а не merge
git config --global fetch.prune true          # удалять исчезнувшие remote-ветки
git config --global rerere.enabled true       # запоминать разрешения конфликтов
git config --global core.autocrlf input       # нормальные переводы строк
git config --global init.defaultBranch main
```

`pull.rebase true` убирает «поезда» merge-коммитов при обновлении ветки, но требует
понимания конфликтов. В командах с общими ветками чаще используют merge.

## Короткое резюме

- Ветка — указатель на коммит; короткие ветки уменьшают конфликты.
- `merge` сохраняет историю, `rebase` делает линейной; force — только со `--force-with-lease` и только в своих ветках.
- Конфликт — это про смысл, а не про синтаксис: сначала понять, потом объединять.
- Conventional commits и `revert` вместо переписывания — правила взрослого репозитория.
