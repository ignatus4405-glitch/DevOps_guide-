# Монорепозиторий: преимущества, цена, инструменты

Один репозиторий на все сервисы упрощает изменения «сквозь» код, но требует
дисциплины и инструментов. Выбор между mono и poly — не религия, а компромисс.

## Плюсы

- атомарные изменения: API и клиент в одном PR;
- единые стандарты и зависимости;
- проще рефакторинг и поиск;
- один CI-конфиг и версионирование.

## Минусы

- CI становится сложным: нельзя собирать всё на каждый коммит;
- права доступа грубее;
- большой checkout;
- конфликты и шум в истории.

## Инструменты

- **Bazel** — граф зависимостей и кэш;
- **Nx** — affected-проекты;
- **Turborepo** — кэш задач;
- **Git sparse-checkout** — частичный checkout;
- **Git LFS** — большие файлы.

Идея affected: собрать и протестировать только то, что затронуто изменением.

```bash
npx nx affected -t test --base=origin/main
```

## Версионирование

Монорепо не означает «одна версия». Сервисы версионируются независимо, но
общие библиотеки — отдельно. Важно не создать «библиотеку всего».

## CI в монорепо

1. Определить затронутые проекты.
2. Запустить их тесты параллельно.
3. Собрать только изменённые артефакты.
4. Опубликовать с независимыми тегами.

Кэш и remote execution критичны: без них CI станет узким местом.

## Polyrepo

Плюсы: изоляция, свои права, маленький checkout. Минусы: сквозные изменения
через несколько PR, рассинхрон версий, дублирование пайплайнов.

## Гибрид

Часто работает лучше всего: монорепо для тесно связанных сервисов, отдельные
репозитории для общих библиотек/инфраструктуры.

## Культура и масштаб

Монорепо не спасает от плохих границ: если все модули зависят от всех,
affected-сборка будет собирать всё. Дисциплина важнее инструмента:

- явные границы пакетов и правила импорта;
- код-ревью с владельцами областей (CODEOWNERS);
- запрет циклических зависимостей;
- маленькие PR и быстрый main.

При росте до тысяч проектов появляются свои проблемы: время checkout, размер
истории, стоимость хранения. Тогда помогает частичный checkout и вынос
тяжёлых артефактов в LFS или отдельные репозитории.
