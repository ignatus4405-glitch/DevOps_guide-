# Монорепозиторий: преимущества, цена, инструменты

Один репозиторий на все сервисы упрощает изменения «сквозь» код, но требует
дисциплины и инструментов. Выбор между mono и poly — не религия, а компромисс.

## Плюсы

- атомарные изменения: API и клиент в одном PR;
- единые стандарты и зависимости;
- проще рефакторинг и поиск;
- один CI-конфиг и версионирование.

## Минусы

- CI становится сложным: нельзя собирать всё на каждый коммит;
- права доступа грубее;
- большой checkout;
- конфликты и шум в истории.

## Инструменты

- **Bazel** — граф зависимостей и кэш;
- **Nx** — affected-проекты;
- **Turborepo** — кэш задач;
- **Git sparse-checkout** — частичный checkout;
- **Git LFS** — большие файлы.

Идея affected: собрать и протестировать только то, что затронуто изменением.

```bash
npx nx affected -t test --base=origin/main
```

## Версионирование

Монорепо не означает «одна версия». Сервисы версионируются независимо, но
общие библиотеки — отдельно. Важно не создать «библиотеку всего».

## CI в монорепо

1. Определить затронутые проекты.
2. Запустить их тесты параллельно.
3. Собрать только изменённые артефакты.
4. Опубликовать с независимыми тегами.

Кэш и remote execution критичны: без них CI станет узким местом.

## Polyrepo

Плюсы: изоляция, свои права, маленький checkout. Минусы: сквозные изменения
через несколько PR, рассинхрон версий, дублирование пайплайнов.

## Гибрид

Часто работает лучше всего: монорепо для тесно связанных сервисов, отдельные
репозитории для общих библиотек/инфраструктуры.

## Культура и масштаб

Монорепо не спасает от плохих границ: если все модули зависят от всех,
affected-сборка будет собирать всё. Дисциплина важнее инструмента:

- явные границы пакетов и правила импорта;
- код-ревью с владельцами областей (CODEOWNERS);
- запрет циклических зависимостей;
- маленькие PR и быстрый main.

При росте до тысяч проектов появляются свои проблемы: время checkout, размер
истории, стоимость хранения. Тогда помогает частичный checkout и вынос
тяжёлых артефактов в LFS или отдельные репозитории.

## Подробный разбор темы

Монорепозиторий экономит координацию для сквозных изменений, но требует карты зависимостей и быстрых выборочных проверок. Изменение общей библиотеки должно запускать тесты её потребителей; изменение документации не обязано пересобирать все сервисы. Для этого CI использует граф целей, path filters и кэш, но фильтры нужно тестировать: пропущенный тест хуже медленного теста.

Разделяйте репозиторий логическими владельцами, CODEOWNERS и понятными контрактами между компонентами. Отслеживайте размер клона, время checkout/build, частоту конфликтов и количество команд, затронутых одним изменением. Монорепозиторий не устраняет архитектурную связанность — он делает её видимой и позволяет управлять ею инструментами.

## Пошаговый сценарий

![Порядок действий: Монорепозиторий: преимущества, цена, инструменты](assets/img/howto/03-git--07-monorepo.svg)

1. Нарисуйте зависимости между приложениями, библиотеками и общими файлами.
2. Настройте выборочные проверки для изменённых узлов графа.
3. Назначьте владельцев компонентов и правила совместимости.
4. Проверьте, что изменение общей библиотеки запускает тесты потребителей.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Нарисуйте, какие приложения используют каждую библиотеку и какие папки общие.

**Как проверить.** У каждой общей папки есть список потребителей; видны потенциальные затронутые проекты.

### Шаг 2

**Что сделать.** Настройте CI так, чтобы изменение приложения запускало его тесты, а изменение общей библиотеки — тесты всех её потребителей.

**Как проверить.** Изменение не пропускает нужную проверку и не запускает без причины весь огромный набор тестов.

### Шаг 3

**Что сделать.** Запишите владельца каждой области и правила изменения общих API или версий.

**Как проверить.** Автор PR знает, кого позвать на ревью и какой контракт нельзя случайно сломать.

### Шаг 4

**Что сделать.** Измените общую библиотеку в тестовой ветке и убедитесь, что CI подхватил один простой и один реальный consumer.

**Как проверить.** Проверки поймали несовместимое изменение до merge.
