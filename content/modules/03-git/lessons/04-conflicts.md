# Конфликты и стратегии слияния без паники

Конфликт — не ошибка, а нормальная ситуация: две ветки изменили одно место.
Задача — разрешить его осознанно и не потерять чужие изменения.

## Откуда берётся конфликт

Git сравнивает не файлы целиком, а общий предок (merge base) с двумя сторонами.
Конфликт возникает, когда обе стороны изменили одни и те же строки или одна
удалила файл, а другая изменила.

```bash
git merge feature/login
# CONFLICT (content): Merge conflict in src/auth.py
git status --short
# UU src/auth.py
```

## Чтение маркеров

```
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature/login
```

- между `<<<<<<<` и `=======` — ваша текущая ветка (ours);
- между `=======` и `>>>>>>>` — вливается (theirs);
- нужно оставить один вариант или собрать оба, затем удалить маркеры.

Правила:

1. Не оставляйте маркеры в файле — ищите `grep -rn '<<<<<<<' .`.
2. Понимайте обе стороны: `git log --merge -p -- src/auth.py`.
3. Запускайте тесты после разрешения — конфликт мог быть логическим, не текстовым.

## Инструменты разрешения

```bash
git mergetool            # графический редактор (meld, vimdiff, VS Code)
git checkout --ours src/auth.py    # взять свою версию целиком
git checkout --theirs src/auth.py  # взять вливаемую
git add src/auth.py
git commit               # завершить merge
```

`--ours`/`--theirs` удобны для сгенерированных файлов (lock-файлы, артефакты),
но опасны для кода: можно молча выбросить чужую логику.

Отмена:

```bash
git merge --abort
git rebase --abort
git cherry-pick --abort
```

## Стратегии слияния

| Стратегия | Когда | Плюсы | Минусы |
| --- | --- | --- | --- |
| merge commit | долгоживущие ветки | полная история | «поезд» коммитов в графе |
| squash merge | feature → main | один чистый коммит | теряется детальная история |
| rebase + fast-forward | локальные ветки | линейная история | переписывает SHA |
| cherry-pick | перенос фикса | точечно | дублирование коммитов |

Правило: **rebase — только для своих, ещё не опубликованных веток**. Если ветку
уже забрали коллеги, rebase перепишет SHA и им придётся делать `reset --hard`.

## Конфликты при rebase

Rebase применяет коммиты по одному, поэтому конфликт может возникать на каждом шаге.

```bash
git rebase main
# конфликт
# правим
git add .
git rebase --continue
# если шаг не нужен
git rebase --skip
# отменить всё
git rebase --abort
```

Полезно включить `git config --global rerere.enabled true`: Git запомнит, как вы
разрешили конфликт, и применит то же решение повторно.

## Как уменьшить количество конфликтов

1. **Маленькие PR** — меньше пересечений.
2. **Частый merge/rebase main** — не копить расхождения.
3. **Договорённости о форматировании** — `.editorconfig`, prettier, единый стиль.
4. **Не коммитить сгенерированные файлы** — lock-файлы обновляет один бот.
5. **Владение файлами** — CODEOWNERS уменьшает одновременные правки.

## Разбор: конфликт в lock-файле

`package-lock.json` конфликтует почти всегда. Правильное решение — не править
вручную, а пересобрать:

```bash
git checkout --theirs package-lock.json
npm install
git add package-lock.json
```

Для Python-аналогов (`poetry.lock`, `uv.lock`) — то же самое: взять одну сторону
и пересчитать зависимости. Ручное слияние lock-файла почти гарантирует битую
зависимость.

## Как Git сливает изменения

Merge использует трёхстороннее сравнение: база (общий предок), наша версия,
их версия. Конфликт возникает, когда изменения пересекаются в одной области.

Rebase применяет коммиты по одному на новую базу — конфликты могут появляться
на каждом шаге. Это не хуже, а просто другой процесс.

### Стратегии

- `merge` — сохраняет историю, один конфликт на слияние;
- `rebase` — линейная история, конфликты по шагам;
- `ort` (по умолчанию) — улучшенный алгоритм слияния;
- `ours`/`theirs` — выбрать сторону целиком (осторожно).

### rerere

`git rerere` запоминает разрешения конфликтов и применяет их повторно:

```bash
git config --global rerere.enabled true
```

Полезно при частых rebase одной ветки.

### Как разрешать

1. Понять, что меняли обе стороны.
2. Выбрать не «мою сторону», а корректный результат.
3. Запустить тесты после разрешения.
4. `git add` и продолжить (`merge --continue`/`rebase --continue`).

### Признак проблемы

Если конфликты огромные и повторяются — проблема не в Git, а в размере
изменений и долгоживущих ветках. Дробите работу и чаще синхронизируйтесь.

## Подробный разбор темы

Конфликт означает, что Git не может автоматически выбрать итог, а не то, что одна сторона «победила». Смотрите три версии: base, ours и theirs; затем определите, какое поведение требуется после объединения. Для JSON, lock-файлов и миграций опасно просто оставить блок, который «компилируется»: итог может быть синтаксически валиден, но логически потерять часть требований.

После разрешения конфликтов проверьте `git diff --check`, список изменённых файлов и тесты для затронутой области. Не коммитьте маркеры `<<<<<<<` и `>>>>>>>`. Если одна и та же конфликтная логика повторяется, `rerere` может запомнить разрешение, но всё равно просмотрите его: Git повторяет прошлый выбор, а не проверяет его смысл.
