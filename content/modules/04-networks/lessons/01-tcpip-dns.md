# TCP/IP, порты и DNS

**Сеть в DevOps нужна не ради теории, а ради диагностики:** 80 % инцидентов
«не работает» — это DNS, порт, сертификат или балансировщик.

![Стек TCP/IP и инструменты](assets/img/networking-stack.svg)

## Путь одного запроса

```
Пользователь → DNS (получить IP) → TCP-соединение (3-way handshake)
→ TLS-рукопожатие → HTTP-запрос → обратный прокси → приложение → ответ
```

Каждый этап можно проверить отдельно — это и есть метод диагностики.

| Этап | Инструмент | Что видим |
| --- | --- | --- |
| DNS | `dig +short host` | IP-адреса записи |
| Маршрут | `traceroute host`, `mtr` | где теряются пакеты |
| Порт | `nc -vz host 443` | открыт ли порт |
| TLS | `openssl s_client -connect host:443` | сертификат, цепочка, срок |
| HTTP | `curl -v https://host/` | коды, заголовки, редиректы |
| Приложение | `journalctl -u svc` | логика сервиса |

## IP, подсети, порты

```bash
ip -br a                      # адреса интерфейсов
ip r                          # маршруты, default gateway
ss -tulpn                     # слушающие порты и процессы
ss -tnp state established     # активные соединения
```

| Понятие | Значение | Практический вывод |
| --- | --- | --- |
| `/32` | один адрес | security group на конкретный хост |
| `10.0.0.0/16` | 65 536 адресов | типовой VPC |
| `10.0.1.0/24` | 256 адресов | подсеть под AZ |
| Private-диапазоны | 10/8, 172.16/12, 192.168/16 | не маршрутизируются в интернет |

**Порты**, которые надо знать наизусть: `22` SSH, `80` HTTP, `443` HTTPS,
`5432` PostgreSQL, `3306` MySQL, `6379` Redis, `8080`/`8000` приложения,
`9090` Prometheus, `3000` Grafana, `6443` Kubernetes API.

!!! warning "Важно"
    Сервис, слушающий `127.0.0.1`, доступен только внутри хоста. Для доступа извне
    нужен `0.0.0.0` (или конкретный адрес). Проверка: `ss -tulpn` показывает
    `127.0.0.1:8080` → значит балансировщик до него не дотянется.

## NAT, файрвол, security groups

```bash
sudo ufw status numbered        # Ubuntu
sudo ufw allow from 10.0.0.0/16 to any port 5432 proto tcp   # только из VPC
sudo firewall-cmd --add-service=https --permanent && sudo firewall-cmd --reload
sudo iptables -t nat -L -n | head      # NAT-правила (Docker добавляет свои)
```

Порядок фильтрации в облаке: **security group (вне хоста) → local firewall → сервис
слушает нужный интерфейс**. Забыть любое из трёх — типовой инцидент.

Docker меняет картину: контейнерный порт публикуется правилами iptables
(`-p 8080:80`), и `ufw` в некоторых конфигурациях обходится — это известная
особенность, о которой стоит помнить при разборе жалоб на «открытый наружу порт».

## DNS: как имена превращаются в адреса

```bash
dig example.com A +short            # IPv4
dig example.com AAAA +short         # IPv6
dig www.example.com CNAME +short    # алиас
dig example.com MX +short           # почта
dig +trace example.com              # вся цепочка: корень → TLD → авторитативный
dig @1.1.1.1 example.com +short     # спросить конкретный резолвер
```

| Тип записи | Что делает | Пример использования |
| --- | --- | --- |
| A / AAAA | имя → IP | основной адрес сервиса |
| CNAME | имя → другое имя | привязка к балансировщику/CDN |
| MX / TXT | почта / проверки | SPF, DKIM, подтверждение домена |
| NS | делегирование зоны | DNS-провайдер |
| SRV | сервис и порт | service discovery |

**TTL** (время жизни записи) решает судьбу переключений: перед миграцией уменьшите
TTL до 60 секунд, тогда переключение на новый IP произойдёт быстро. Стандартный TTL
в 3600 секунд означает, что часть клиентов пойдёт на старый адрес ещё час.

!!! tip "Совет"
    `dig` по умолчанию не учитывает `/etc/hosts`, а `getent hosts` учитывает. Если
    «у меня работает, а у коллеги нет» — сравните ответы `getent hosts` на обеих
    машинах: часто причина в локальном файле hosts или в DNS-кэше.

В Kubernetes DNS — отдельная подсистема (CoreDNS): сервисы получают имена вида
`service.namespace.svc.cluster.local`. Ошибка «не резолвится имя сервиса» почти
всегда означает проблему CoreDNS или неправильное имя/namespace.

## Порты: что нужно помнить

| Диапазон | Назначение | Примеры |
| --- | --- | --- |
| 0–1023 | привилегированные | 22 SSH, 80 HTTP, 443 HTTPS |
| 1024–49151 | зарегистрированные | 5432 PostgreSQL, 6379 Redis, 8080 HTTP-alt |
| 49152–65535 | динамические | временные порты клиента |

Сервис не может слушать порт < 1024 без прав root (или capability
`CAP_NET_BIND_SERVICE`). Поэтому в контейнерах приложение слушает 8080, а
перенаправление с 80 делает ingress или `docker -p 80:8080`.

Посмотреть, кто слушает:

```bash
ss -lntp
sudo lsof -i :5432
```

## TCP против UDP

| | TCP | UDP |
| --- | --- | --- |
| Соединение | устанавливается (3-way handshake) | нет |
| Доставка | гарантирована, с повторами | не гарантирована |
| Порядок | сохраняется | не гарантируется |
| Скорость | ниже | выше |
| Применение | HTTP, SSH, БД | DNS, метрики, видео, QUIC |

DNS использует UDP для обычных запросов и TCP для больших ответов и зонных
трансферов. Потеря UDP-пакета не ретранслируется на уровне транспорта — этим
занимается приложение (или повторный запрос клиента).

## Подсети и CIDR без страха

`10.0.0.0/16` означает: первые 16 бит фиксированы, остальные 16 — адреса хостов.
Отсюда 65 536 адресов. Быстрая арифметика:

| CIDR | Адресов | Типичное использование |
| --- | --- | --- |
| /24 | 256 | подсеть в VPC |
| /16 | 65 536 | весь VPC |
| /32 | 1 | конкретный хост |
| /8 | 16 777 216 | огромная сеть (редко) |

В AWS из каждой подсети вычитаются 5 адресов (network, broadcast, router, DNS×2).
Поэтому /24 даёт 251 доступный адрес — частая причина «не хватает IP» в небольшой
подсети.

## Короткое резюме

- Путь запроса разбивается на этапы, каждый проверяется своим инструментом.
- Порты и адреса: слушает ли `0.0.0.0`, доступен ли порт снаружи.
- Фильтров три: security group, локальный firewall, привязка сервиса.
- DNS-записи и TTL определяют, куда и как быстро пойдёт трафик после изменений.

## Инкапсуляция и MTU

Данные приложения → TCP-сегмент → IP-пакет → Ethernet-кадр. На каждом уровне
добавляется заголовок. MTU Ethernet — 1500 байт; если путь проходит через
туннель, эффективный MTU меньше.

TCP умеет обнаруживать размер через MSS и Path MTU Discovery, но при
блокировке ICMP возникают «чёрные дыры»: handshake проходит, данные нет.
Отсюда классика — `ping -M do` и `curl --http1.1` для проверки.

### Управление перегрузкой

TCP регулирует скорость через congestion window. Классические алгоритмы
(cubic) реагируют на потери; BBR оценивает пропускную способность и RTT.
На каналах с потерями BBR часто даёт лучше, но может быть агрессивнее к соседям.

**Bufferbloat** — большие буферы в маршрутизаторах добавляют задержку: пакеты
не теряются, но стоят в очереди. Симптом: throughput высокий, latency растёт
под нагрузкой. Лечение — AQM (fq_codel) и разумные буферы.

### DNS-таймауты

Резолвер пробует серверы по очереди с таймаутом. Если первый DNS не отвечает,
каждый запрос ждёт секунды. Проверяйте `/etc/resolv.conf`, `options timeout`,
`ndots`, и используйте `dig +stats` для реального времени.

### NAT и keepalive

NAT-устройства забывают неактивные соединения. Долгоживущие соединения
(базы, gRPC) должны отправлять keepalive. Иначе после паузы клиент пишет в
мёртвый сокет и получает reset.

## Подробный разбор темы

Успешное соединение требует совпадения нескольких условий: клиент получил правильный IP через DNS, выбрал маршрут, дошёл до адреса и порта, прошёл фильтрацию, а процесс принял handshake. Для TCP полезно различать `connection refused` (узел ответил, но порт не слушается/отвергнут) и timeout (ответ не пришёл вовремя). Оба симптома отличаются от ошибки разрешения имени.

Порт идентифицирует endpoint на хосте, а не «сервис в интернете» сам по себе; один процесс может слушать несколько интерфейсов, а NAT меняет адреса по пути. Диагностируйте и клиентскую, и серверную стороны: локальный `ss` показывает listening socket, `getent hosts` — ответ системного resolver. Сверяйте IPv4 и IPv6: приложение может работать по одному семейству и отказывать по другому.

## Пошаговый сценарий

![Порядок действий: TCP/IP, порты и DNS](assets/img/howto/04-networks--01-tcpip-dns.svg)

1. Разрешите hostname и сравните полученный адрес с ожидаемым.
2. Проверьте маршрут, source address и доступность целевого TCP-порта.
3. Подтвердите handshake и запрос на прикладном протоколе.
4. Сопоставьте результат клиента с listening socket на сервере.
