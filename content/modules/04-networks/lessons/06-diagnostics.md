# Диагностика сети: от DNS до потерь пакетов

Сетевые инциденты пугают тем, что «не видно, что происходит». На самом деле есть
строгая последовательность проверок, которая за пять минут отделяет проблему
приложения от проблемы сети.

## Схема разбора

```
DNS → маршрут → порт → TLS → HTTP → производительность
```

На каждом шаге — своя команда и свой признак успеха. Не переходите к следующему,
пока не получили ответ на предыдущий.

### 1. DNS

```bash
dig +short api.example.com
getent hosts api.example.com
```

Нет ответа — проверяйте `/etc/resolv.conf`, `search`, доступность DNS-сервера.

### 2. Маршрут

```bash
ip route get 203.0.113.10
mtr -rw -c 20 api.example.com
```

`ip route get` показывает интерфейс и источник. `mtr` — потери по хопам: если
потери начинаются на 5-м хопе и сохраняются до конца, проблема у провайдера.

### 3. Порт

```bash
nc -zv api.example.com 443
ss -tn state established '( dport = :443 )'
```

`nc` проверяет TCP-соединение без приложения. Если порт открыт, а HTTP не работает,
проблема выше.

### 4. TLS

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null
```

Смотрите на `Verify return code`, дату и цепочку.

### 5. HTTP

```bash
curl -v https://api.example.com/health
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' -o /dev/null -s https://api.example.com/
```

Тайминги показывают, где задержка: DNS, TCP, TLS или сервер.

### 6. Производительность

```bash
mtr -rw api.example.com
iperf3 -c 10.0.0.5
ip -s link show eth0
ss -ti
```

## Чтение mtr

```
HOST: client            Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 10.0.0.1         0.0%    20    0.4   0.5   0.3   1.2   0.2
  2.|-- 192.168.1.1      0.0%    20    1.2   1.4   1.0   3.1   0.4
  3.|-- 203.0.113.1     35.0%    20   12.0  13.2  11.0  20.4   2.1
  4.|-- api.example.com  0.0%    20   12.5  13.0  11.5  19.0   1.9
```

Потери на промежуточном хопе при нулевых потерях на конечном — это ограничение
ICMP на маршрутизаторе, а не проблема. Важны потери на **последнем** хопе.

## TCP-ретрансмиссии

```bash
ss -ti | grep -A1 ':443'
# retrans:0/12 means 12 retransmits
```

Ретрансмиссии означают потери или перегрузку. На локальной сети их должно быть
близко к нулю. Причины: переполненные буферы, проблемы с MTU, нестабильный канал.

## MTU и фрагментация

```bash
ping -M do -s 1472 -c 3 api.example.com
```

1472 + 28 (IP+ICMP) = 1500. Если большие пакеты не проходят, а маленькие проходят,
MTU меньше 1500 — типично для VPN и туннелей. Симптом: TLS-рукопожатие зависает,
хотя ping работает.

## Что приложить к инциденту

Хороший отчёт содержит:

1. время и зону (UTC!);
2. команду и её вывод;
3. что ожидалось и что получено;
4. с какого хоста выполнялась проверка;
5. воспроизводится ли с другого места.

Без этого «сайт не работает» превращается в переписку на час.

## Подробный разбор темы

Диагностируйте одну попытку запроса и записывайте её временные отметки. Сначала сравните резолвинг DNS, затем TCP-connect, TLS handshake, время до первого байта и полный HTTP-ответ. `curl -w` помогает разделить эти этапы; повторите запрос из того же сетевого сегмента, что и проблемный клиент. Если DNS-ответ корректен, но TCP handshake зависает, дальнейшая проверка содержимого HTTP пока преждевременна.

Сравните успешный и неуспешный маршрут по адресу, порту, IPv4/IPv6 и исходному subnet. Потери на промежуточном хопе не обязательно означают потерю пользовательского трафика: маршрутизатор может ограничивать ответы на traceroute. Ищите потери на конечном пути и сверяйте их с application metrics. Не делайте вывод по одной пробе — повторите измерение в период инцидента.

## Пошаговый сценарий

![Порядок действий: Диагностика сети: от DNS до потерь пакетов](assets/img/howto/04-networks--06-diagnostics.svg)

1. Зафиксируйте адрес, порт, время и место запуска проблемного запроса.
2. Разделите DNS, connect, TLS, первый байт и полный HTTP-ответ.
3. Сравните успешный и неуспешный путь без смены остальных параметров.
4. Подтвердите гипотезу повторной пробой и серверными метриками.

## Проверьте себя

1. В каком порядке проверять «сервис недоступен»?
2. Что означает 35 % потерь на промежуточном хопе при 0 % на последнем?
3. Как отличить проблему MTU от проблемы приложения?
4. Какие данные нужны, чтобы инцидент можно было воспроизвести?
