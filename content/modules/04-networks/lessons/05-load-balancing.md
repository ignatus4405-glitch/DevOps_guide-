# Балансировка: L4, L7, health checks, sticky sessions

Когда один сервер не справляется или не должен быть единственной точкой отказа,
перед ним ставят балансировщик. Но «поставить nginx» — не решение: важно понимать,
на каком уровне он работает и как определяет, что бэкенд жив.

## L4 против L7

| Характеристика | L4 (TCP/UDP) | L7 (HTTP) |
| --- | --- | --- |
| Что видит | IP и порт | метод, путь, заголовки |
| Скорость | выше | ниже, но гибче |
| Маршрутизация | по адресу | по хосту, пути, cookie |
| TLS | passthrough или termination | termination + повторное шифрование |
| Примеры | AWS NLB, HAProxy TCP | nginx, ALB, Traefik, Envoy |

L4 не умеет «отправить `/api` на один сервис, а `/static` на другой» — он видит
только поток байтов. L7 умеет, но должен расшифровать TLS.

## Алгоритмы распределения

- **round robin** — по кругу; просто и предсказуемо;
- **least connections** — на сервер с меньшим числом активных соединений;
- **least response time** — учитывает задержку;
- **IP hash** — один клиент всегда на одном бэкенде;
- **random with two choices** — выбирает двух случайно и идёт к менее загруженному.

Для долгих соединений (gRPC, WebSocket) round robin может собрать всех клиентов
на одном бэкенде, если соединения долгоживущие. Тогда нужен least connections или
специальные настройки.

## Health checks

Балансировщик должен знать, что бэкенд жив. Два типа:

- **passive** — по реальным запросам: если 5 подряд ошибок, вывести из пула;
- **active** — периодический запрос `/health`.

Health-check должен проверять **готовность обслуживать**, а не факт, что процесс
запущен:

```python
@app.get("/healthz")
def healthz():
    if not db.ping():
        return Response(status_code=503)
    return {"status": "ok"}
```

Ошибки:

| Ошибка | Последствие |
| --- | --- |
| `/health` всегда 200 | трафик идёт на неработающий бэкенд |
| `/health` ходит в БД на каждый запрос | лишняя нагрузка |
| проверка зависит от внешнего сервиса | каскадный отказ: все бэкенды «больны» |
| слишком короткий интервал | ложные срабатывания |

Правило: liveness проверяет сам процесс, readiness — готовность принимать трафик,
включая зависимости. Это же разделение используется в Kubernetes.

## nginx как reverse proxy

```nginx
upstream api {
    least_conn;
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location /health {
        access_log off;
        proxy_pass http://api;
    }

    location / {
        proxy_pass http://api;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }
}
```

Без `X-Forwarded-For` приложение видит IP балансировщика, и логи/лимиты ломаются.
Без `keepalive` nginx открывает новое TCP-соединение на каждый запрос — лишняя
задержка и порты в TIME_WAIT.

## Sticky sessions и почему их избегают

Sticky (session affinity) привязывает клиента к бэкенду по cookie. Это просто, но
мешает:

- при отказе бэкенда пользователь теряет сессию;
- при деплое часть пользователей «прыгает»;
- нагрузка распределяется неравномерно.

Правильное решение — хранить состояние вне процесса: в Redis, БД или JWT. Тогда
любой бэкенд может обслужить любой запрос, и балансировщик свободен в выборе.

## Таймауты и retry

Таймауты должны быть согласованы по всей цепочке:

```
клиент 30s → балансировщик 25s → приложение 20s → БД 15s
```

Если приложение ждёт БД 60 секунд, а балансировщик рвёт соединение на 30-й, клиент
получит 502 и не увидит полезную ошибку. Правило: внутренние таймауты короче
внешних.

Retry опасен для неидемпотентных запросов (`POST`). Повторять стоит только
идемпотентные методы или запросы с `Idempotency-Key`.

## Разбор реального сценария

Сервис жалуется: «иногда 502, чаще всего утром». Что проверяем:

1. **502 означает**, что балансировщик не получил валидный ответ от бэкенда.
2. Смотрим, меняется ли картина по времени — совпадает ли с деплоем или
   прогревом.
3. Проверяем health-check: если он слишком строгий, под исключается из пула
   при первом же медленном ответе.
4. Проверяем таймауты: `proxy_read_timeout` меньше, чем p99 бэкенда, даёт
   регулярные 502 под нагрузкой.
5. Проверяем keepalive до бэкенда: без него соединения открываются заново и
   портят latency.

Типичная причина утренних 502 — холодный старт после ночного масштабирования
вниз: новые поды не успевают прогреться, а readiness уже зелёный.

## Что настроить

```nginx
upstream api {
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    keepalive 32;
}
server {
    location / {
        proxy_pass http://api;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
        proxy_next_upstream error timeout http_502;
    }
}
```

Смысл: быстро отбрасывать мёртвый бэкенд, не ждать дольше пользователя и
повторять запрос на другом узле, если ошибка инфраструктурная.

## Подробный разбор темы

L4-балансировщик распределяет соединения по адресам и портам, L7 понимает протокол и может маршрутизировать по host/path или заголовкам. Выбор влияет на видимость запроса, TLS, стоимость и количество соединений. Health check должен измерять готовность обслуживать рабочую нагрузку, а не только отвечать на TCP SYN или процессный `/health`.

Sticky sessions упрощают хранение состояния в памяти, но делают нагрузку неравномерной и мешают масштабированию. Если сессия нужна, сравните affinity с внешним session store и учтите поведение при отказе узла. При настройке балансировщика задайте таймауты согласованно с приложением, корректный draining перед выключением экземпляра и наблюдение за кодами ответов по каждому backend.
