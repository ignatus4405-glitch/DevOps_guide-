# Семантика HTTP: идемпотентность, кэш, условные запросы

HTTP — не просто «отправить JSON». Семантика методов и заголовков определяет,
как работают прокси, кэши, ретраи и браузеры. Ошибки здесь приводят к двойным
платежам и странным ответам из кэша.

## Методы и идемпотентность

| Метод | Безопасный | Идемпотентный | Тело |
| --- | --- | --- | --- |
| GET | да | да | нет |
| HEAD | да | да | нет |
| PUT | нет | да | да |
| DELETE | нет | да | нет |
| POST | нет | **нет** | да |
| PATCH | нет | нет | да |

Идемпотентность — свойство сервера: повторный PUT с тем же телом даёт тот же
результат. POST по умолчанию — нет, поэтому для платежей используют
`Idempotency-Key`.

## Коды ответов, которые важно различать

- `200/201/204` — успех;
- `301/308` — постоянный редирект (308 сохраняет метод);
- `302/307` — временный (307 сохраняет метод);
- `400` — клиентская ошибка;
- `401` — не аутентифицирован;
- `403` — аутентифицирован, но нельзя;
- `404` — нет ресурса;
- `409` — конфликт;
- `422` — валидация;
- `429` — rate limit;
- `500/502/503/504` — серверные, но причины разные.

`502` — плохой ответ upstream, `504` — таймаут upstream. Это разные диагнозы.

## Кэширование

Заголовки:

- `Cache-Control: max-age=60, public/private, no-store`;
- `ETag` — версия ресурса;
- `Last-Modified`;
- `Vary` — какие заголовки влияют на кэш.

`private` запрещает кэшировать в общем кэше (CDN), `no-store` — не хранить
вообще. `Vary: Authorization` защищает от утечки между пользователями.

## Условные запросы

Клиент присылает `If-None-Match: <etag>`. Сервер отвечает `304 Not Modified`
без тела, если версия та же. Это экономит трафик и ускоряет загрузку.

```http
GET /api/profile
If-None-Match: "v42"
→ 304
```

## Кэш и безопасность

- не кэшируйте ответы с персональными данными в общих кэшах;
- `Set-Cookie` и `Authorization` требуют аккуратного `Vary`;
- CDN должен уважать `Cache-Control`, а не кэшировать всё подряд.

## Согласование содержимого

`Accept`, `Accept-Encoding`, `Accept-Language` позволяют отдать разный формат.
`Vary` должен перечислять эти заголовки, иначе кэш отдаст не тот вариант.

## Ретраи и методы

Ретраить можно идемпотентные методы. Для POST — только с ключом идемпотентности
и ограничением попыток. Иначе повтор создаст второй заказ.

## Прокси и hop-by-hop

Заголовки `Connection`, `Keep-Alive`, `Transfer-Encoding` относятся к соединению
и не должны передаваться дальше. `X-Forwarded-For`/`Forwarded` — к клиенту,
но им нельзя доверять без проверки на границе.

## Подробный разбор темы

Идемпотентность означает, что повтор операции сохраняет конечный эффект, а не что ответ всегда одинаков. Это важно для безопасных ретраев при timeout: клиент может не знать, выполнился ли запрос до потери ответа. Для операции создания часто используют idempotency key, чтобы сервер распознал повтор. `Cache-Control`, `ETag` и `If-None-Match` уменьшают передачу данных, но кэш должен учитывать авторизацию и `Vary`.

Проверьте семантику метода вместе с бизнес-операцией: `GET` не должен менять состояние; `PUT` заменяет представление ресурса, `PATCH` меняет часть, `DELETE` может быть повторяемым на уровне конечного состояния. Обрабатывайте `429` и `Retry-After`, ограничивайте число повторов и применяйте backoff с jitter, иначе множество клиентов синхронно усилят перегрузку.

## Пошаговый сценарий

1. Опишите эффект операции и решите, безопасен ли повтор запроса.
2. Назначьте idempotency key для повторяемой операции создания.
3. Настройте Cache-Control и условные запросы с учётом авторизации.
4. Ограничьте retry числом попыток, backoff и jitter.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Опишите, что изменит запрос. Повтор `GET` обычно безопасен; повтор платежа или создания заказа может выполнить действие ещё раз.

**Как проверить.** Вы знаете, можно ли повторить операцию без второго списания или дубликата.

### Шаг 2

**Что сделать.** Для создания с возможными повторами передайте уникальный idempotency key и храните результат по этому ключу.

**Как проверить.** Повтор с тем же ключом возвращает результат первой операции, а не создаёт вторую.

### Шаг 3

**Что сделать.** Настройте кэш только для данных, которые разрешено хранить; персональные ответы обычно нельзя отдавать другому пользователю из общего кэша.

**Как проверить.** Заголовки Cache-Control соответствуют чувствительности данных и авторизации.

### Шаг 4

**Что сделать.** Повторяйте запрос лишь при временной ошибке, ограничьте число попыток и добавьте паузу с jitter.

**Как проверить.** Один сбой не превращается в шторм повторных запросов.
