# DNS изнутри: зоны, записи, резолверы

DNS — самая частая причина «сервис недоступен» после неправильных прав. При этом
он устроен просто: иерархия зон и кэширование. Понимание этих двух идей снимает
90 % загадок.

## Иерархия и делегирование

Корневые серверы знают, кто отвечает за `.com`, серверы `.com` — кто отвечает за
`example.com`, и так далее. Зона — часть пространства имён, за которую отвечает
конкретный набор серверов.

```bash
dig +trace api.example.com
```

`+trace` проходит всю цепочку: корень → TLD → авторитетные серверы. Если на
каком-то шаге ответа нет, сразу видно, где сломано делегирование.

## Типы записей

| Запись | Назначение | Пример |
| --- | --- | --- |
| A | IPv4-адрес | `api.example.com. 300 IN A 203.0.113.10` |
| AAAA | IPv6-адрес | `api.example.com. 300 IN AAAA 2001:db8::10` |
| CNAME | псевдоним | `www.example.com. IN CNAME example.com.` |
| MX | почтовый сервер | `example.com. IN MX 10 mail.example.com.` |
| TXT | текст (SPF, DKIM, верификация) | `example.com. IN TXT "v=spf1 ..."` |
| NS | делегирование зоны | `example.com. IN NS ns1.example.com.` |
| SRV | сервис + порт | `_https._tcp.example.com. IN SRV ...` |

Правила:

- CNAME нельзя ставить на корень зоны (`example.com`), потому что он конфликтует
  с NS/SOA. Для корня используют A/AAAA или ALIAS/ANAME у провайдера.
- CNAME не может сосуществовать с другими записями того же имени.
- TTL управляет кэшем. 300 секунд — гибкость, 3600 — меньше нагрузки.

## Резолвер: как имя превращается в адрес

Путь запроса в Linux:

1. `/etc/nsswitch.conf` — порядок источников (`files dns`).
2. `/etc/hosts` — локальные записи.
3. `/etc/resolv.conf` — адреса DNS-серверов, `search`-домены, `options`.
4. Резолвер (systemd-resolved, dnsmasq) или напрямую DNS-сервер.
5. Кэш: локальный, затем серверов провайдера.

Отсюда классика: `dig` идёт напрямую в DNS и отвечает, а приложение — нет, потому
что оно читает `/etc/hosts` или использует другой резолвер.

```bash
getent hosts api.example.com     # как видит система
resolvectl status                # systemd-resolved
cat /etc/resolv.conf
```

## Кэширование и TTL

Каждый ответ кэшируется на TTL. Это объясняет:

- почему после смены IP часть клиентов ходит на старый адрес;
- почему TTL снижают заранее перед миграцией (за сутки до переключения);
- почему «у меня открывается, а у коллеги нет» — не магия, а разные кэши.

Проверка с разных резолверов:

```bash
dig @8.8.8.8 api.example.com +short
dig @1.1.1.1 api.example.com +short
dig api.example.com +short +ttl
```

Если ответы различаются, вопрос не в приложении, а в распространении DNS.

## Внутренний DNS в кластере

Kubernetes создаёт DNS-имена для сервисов:

```
<service>.<namespace>.svc.cluster.local
```

```bash
kubectl run tmp --rm -it --image=busybox -- sh
nslookup api.default.svc.cluster.local
```

Частые проблемы:

- под не резолвит имя, потому что `dnsPolicy` неверный;
- CoreDNS не запущен (`kubectl -n kube-system get pods`);
- NetworkPolicy блокирует UDP 53;
- в `resolv.conf` пода `ndots:5`, из-за чего внешние имена сначала пробуются как
  внутренние — задержка на каждом запросе.

## Диагностика по шагам

```bash
dig api.example.com                      # отвечает ли DNS
dig api.example.com +short               # какой адрес
dig @<authoritative> api.example.com     # что говорит авторитетный сервер
getent hosts api.example.com             # что видит система
curl --resolve api.example.com:443:<ip> https://api.example.com/  # обход DNS
```

`--resolve` — ключевой приём: он позволяет проверить конкретный сервер, не меняя
DNS и не трогая `/etc/hosts`.

## Подробный разбор темы

Рекурсивный resolver ищет ответ за клиента и кэширует результат; authoritative-сервер отвечает за конкретную зону и не обязан обходить всю иерархию. Поэтому `dig @resolver имя` и `dig +trace имя` отвечают на разные вопросы. Запись с TTL может оставаться в кэше после изменения зоны, а negative caching сохраняет и сведения о том, что имени не существует.

При выпуске изменения проверьте serial SOA, NS и glue records, затем спросите авторитетный сервер напрямую и только после этого — несколько рекурсивных resolver. Для split-horizon DNS сравните источник запроса: внутренний и внешний клиент могут закономерно получать разные адреса. Запишите тип записи, ожидаемый TTL и время распространения, чтобы не диагностировать нормальное кэширование как случайный отказ.

## Пошаговый сценарий

![Порядок действий: DNS изнутри: зоны, записи, резолверы](assets/img/howto/04-networks--03-dns-deep.svg)

1. Спросите рекурсивный resolver и сохраните тип ответа и TTL.
2. Запросите authoritative nameserver напрямую для той же записи.
3. Сверьте SOA serial, NS и negative cache, если имя отсутствует.
4. Сравните ответы нескольких resolver после истечения старого TTL.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Запросите имя обычным системным способом `getent hosts имя`; отдельно используйте `dig имя A` и запишите TTL.

**Как проверить.** Видно, какой адрес получил пользователь и сколько времени resolver может его кэшировать.

### Шаг 2

**Что сделать.** Из ответа возьмите authoritative nameserver и спросите его напрямую через `dig @ns.example имя A`.

**Как проверить.** Понятно, что хранит сама DNS-зона, независимо от кэша промежуточного resolver.

### Шаг 3

**Что сделать.** Посмотрите `dig имя SOA` и `dig имя NS`; при отсутствии имени проверьте тип ответа и отрицательный TTL.

**Как проверить.** Вы различаете неправильную запись, старый кэш и отсутствие делегации.

### Шаг 4

**Что сделать.** Повторите запрос на нескольких resolver и дождитесь окончания TTL перед выводом, что изменение распространилось.

**Как проверить.** Сравнение записано с временем запроса; старый кэш не принят за ошибку authoritative зоны.
