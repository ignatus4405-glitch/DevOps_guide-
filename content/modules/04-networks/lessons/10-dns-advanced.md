# DNS в глубину: делегирование, DNSSEC, anycast

DNS — распределённая база данных с кэшами на каждом шаге. Понимание
делегирования и TTL объясняет, почему изменения «не применились» и почему
один регион видит один IP, а другой — другой.

## Иерархия и делегирование

```text
. → com. → example.com. → api.example.com.
```

Корневые серверы знают зоны `com`, серверы `com` — NS вашего домена, ваш
DNS-провайдер — записи. Делегирование задаётся NS-записями и glue-адресами.

Если NS у регистратора не совпадают с зоной — домен «не работает», хотя записи
в панели есть.

## Типы записей

| Тип | Назначение |
| --- | --- |
| A/AAAA | IPv4/IPv6 |
| CNAME | псевдоним имени |
| MX | почта |
| TXT | верификация, SPF/DKIM |
| SRV | сервис + порт |
| CAA | кто может выпускать сертификаты |
| NS | делегирование |

CNAME нельзя ставить на apex-домен (`example.com`) — используйте ALIAS/ANAME
у провайдера.

## TTL и кэш

TTL задаёт, как долго резолвер хранит ответ. Перед миграцией:

1. снизить TTL до 60 секунд;
2. подождать старый TTL;
3. переключить;
4. вернуть нормальный TTL.

Если этого не сделать, старый адрес будет жить в кэшах часами.

Отрицательный кэш (NXDOMAIN) тоже кэшируется — по SOA minimum.

## DNSSEC

Подписи подтверждают, что ответ не подменён. Цепочка доверия идёт от корня к
зоне. Ошибки DNSSEC приводят к SERVFAIL, а не к «просто не resolves».
Проверка:

```bash
dig +dnssec example.com
delv example.com
```

DNSSEC не шифрует запросы — для этого DoH/DoT.

## Anycast

Один IP объявлен из многих точек; маршрутизация приводит клиента к ближайшей.
Так работают корневые серверы и публичные резолверы. Плюс — устойчивость к DDoS
и низкая latency. Минус — сложнее отладка: `dig` из разных мест даёт разные
серверы.

## Split-horizon

Внутренние и внешние клиенты видят разные ответы. Полезно для приватных
сервисов, но опасно: легко получить «работает у меня, не работает в кластере».

## Отладка

```bash
dig +trace example.com
dig @8.8.8.8 example.com
dig +short TXT _dmarc.example.com
resolvectl query example.com
```

`+trace` показывает путь делегирования, `@server` — конкретный резолвер.
Сравнивайте ответы авторитативного сервера и кэша.

## Подробный разбор темы

Делегирование связывает родительскую зону с NS дочерней зоны; glue-запись нужна, когда адрес самого NS лежит внутри делегируемого домена. Ошибка в NS, glue или DS может привести к SERVFAIL, хотя отдельный авторитетный сервер отвечает. DNSSEC подтверждает подлинность цепочки подписи, но не шифрует запросы; неверно опубликованный DS нарушает валидацию и делает домен недоступным для validating resolver.

Anycast объявляет один IP из нескольких точек, поэтому запросы попадают в ближайший по маршрутизации узел, а не обязательно в географически ближайший. При анализе сравнивайте resolver и регион, очищайте локальный кэш только для теста и сверяйте TTL. Изменения DNS планируйте с учётом старого TTL: сначала уменьшите TTL, дождитесь его истечения, затем меняйте адрес или делегирование.

4. Учитывайте TTL до и после изменения адреса или делегирования.
