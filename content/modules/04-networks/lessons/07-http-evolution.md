# HTTP/1.1 → HTTP/2 → HTTP/3: что изменилось внутри

HTTP кажется неизменным: метод, путь, заголовки. Но транспорт под ним менялся
трижды, и каждая версия решала конкретную проблему производительности.

## HTTP/1.1

Модель: один запрос — одно соединение (с keep-alive соединение переиспользуется,
но запросы идут последовательно). Браузер открывает 6 соединений на хост, и это
костыль против head-of-line blocking на уровне приложения.

Проблемы:

- **HOL blocking** — медленный ответ задерживает следующие;
- дублирование заголовков в каждом запросе;
- текстовый формат — дорогой разбор;
- приоритизация почти отсутствует.

## HTTP/2

Ключевая идея — **мультиплексирование**: несколько потоков (streams) в одном
TCP-соединении. Запросы и ответы разбиваются на фреймы, каждый поток имеет id.

Что появилось:

- бинарный протокол;
- сжатие заголовков HPACK;
- приоритеты и зависимости потоков;
- server push (на практике почти отказались).

Что осталось: **TCP head-of-line blocking**. Если потерян TCP-сегмент, все
потоки ждут его повторной передачи, даже если их данные уже пришли.

## HTTP/3 и QUIC

HTTP/3 работает поверх QUIC — протокола на UDP. QUIC даёт:

- независимые потоки без блокировки на уровне TCP;
- встроенный TLS 1.3 в handshake;
- 0-RTT для повторных соединений;
- миграцию соединения при смене сети (мобильный → Wi-Fi);
- контроль перегрузки в user space.

Плата: UDP может блокироваться корпоративными сетями и старыми firewall'ами,
наблюдаемость иная, а балансировщики должны поддерживать QUIC.

## TLS 1.3

Ускорение рукопожатия: один round-trip вместо двух, меньше шифров, forward
secrecy по умолчанию. 0-RTT ускоряет повторные соединения, но подвержен replay —
не используйте его для неидемпотентных запросов.

## Что видит DevOps

| Симптом | Возможная причина |
| --- | --- |
| `curl` медленный, браузер быстрый | разные версии протокола |
| 502 после включения HTTP/2 | прокси не поддерживает h2c/h2 |
| нет HTTP/3 | UDP/443 закрыт |
| высокий p99 при потерях | TCP HOL на HTTP/2 |

Проверки:

```bash
curl -I --http2 https://example.com
curl -I --http3 https://example.com
openssl s_client -alpn h2 -connect example.com:443 </dev/null
```

## Обратная совместимость

Версия согласуется через ALPN в TLS. Сервер и клиент выбирают максимум из
поддерживаемых. Поэтому «включить HTTP/3» не ломает старых клиентов, если
оставить fallback на HTTP/1.1.

## Что это значит для дизайна

- не нужно доменно шардить ради «больше соединений» — мультиплексирование
  решает это;
- объединение файлов теряет смысл, кэширование важнее;
- при потерях пакетов HTTP/3 выигрывает сильнее;
- заголовки всё ещё стоит сокращать (HPACK не бесконечен).
