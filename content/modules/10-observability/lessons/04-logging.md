# Логи: структура, сбор, хранение

Логи отвечают на вопрос «что именно произошло». Но хаотичные текстовые логи стоят
дорого и бесполезны в инциденте. Разберём, как сделать их пригодными.

## Структурированные логи

Плохо:

```
2026-10-17 10:12:33 ERROR something failed for user 42
```

Хорошо:

```json
{"ts":"2026-10-17T10:12:33Z","level":"error","msg":"payment failed",
 "user_id":42,"order_id":"a1b2","provider":"stripe","error":"timeout",
 "trace_id":"4bf92f3577b34da6"}
```

Плюсы: парсинг без регулярных выражений, фильтры по полям, корреляция с трейсами.

## Уровни и что в них писать

| Уровень | Когда | Пример |
| --- | --- | --- |
| debug | диагностика, выключен в проде | значения переменных |
| info | значимые события | запрос обработан, деплой |
| warn | потенциальная проблема | retry, деградация |
| error | ошибка, требующая внимания | исключение, 5xx |
| fatal | падение процесса | не удалось стартовать |

Правило: **не логируйте в цикле на каждый запрос на уровне info**, если это не
нужно для аудита. Стоимость хранения растёт линейно.

## Что никогда не логировать

- пароли, токены, ключи;
- номера карт и персональные данные (GDPR);
- полные тела запросов с секретами;
- cookie и заголовки авторизации.

Маскирование на уровне приложения и на уровне сборщика. Даже «временный» лог с
токеном останется в архиве.

## Сбор

| Стек | Компоненты | Плюсы |
| --- | --- | --- |
| ELK | Elasticsearch + Logstash + Kibana | мощный поиск |
| Loki | Promtail + Loki + Grafana | дешёвый, метки как в Prometheus |
| CloudWatch | агент + сервис | без инфраструктуры |
| Vector | агент + любой backend | быстрый, гибкий |

В Kubernetes логи контейнера пишутся в stdout, агент (Fluent Bit, Promtail)
собирает их с нод.

```yaml
# promtail
scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
```

## Стоимость хранения

Логи — самая дорогая часть наблюдаемости. Стратегии:

- retention: 7 дней горячих, 30–90 дней тёплых, 1 год архив;
- семплирование debug-логов;
- агрегация: не хранить по строке на запрос, если достаточно метрики;
- сжатие и холодное хранилище (S3 + Athena).

Оценивайте: 1 ТБ логов в день — это десятки тысяч долларов в год.

## Поиск в инциденте

```bash
# Loki (LogCLI)
logcli query '{app="api"} |= "error" | json | level="error"' --since=1h

# kubectl
kubectl logs deploy/api --since=15m | grep -i error

# Elasticsearch
GET logs-*/_search
{"query":{"bool":{"filter":[{"term":{"service":"api"}},{"range":{"@timestamp":{"gte":"now-1h"}}}]}}}
```

Полезно иметь сохранённые запросы: «ошибки за час по сервису», «медленные
запросы», «5xx по endpoint».

## Корреляция

Главное — связать лог с запросом и трейсом:

- `trace_id` в каждом логе;
- `request_id` в заголовке и логах;
- единый `service.name` и `environment`.

Без этого поиск в инциденте превращается в археологию.

## Подробный разбор темы

Структурированный лог хранит timestamp, severity, service/version, event и контекст запроса как отдельные поля. Это облегчает фильтрацию и агрегацию, но схема должна быть стабильной между релизами. Не записывайте пароли, access tokens, персональные данные и весь body запроса по умолчанию; redact на источнике надёжнее, чем надеяться на последующий фильтр.

Выбирайте уровень так, чтобы `error` означал необходимое действие, а не обычный контрольный поток. Коррелируйте логи с trace ID, используйте UTC и синхронизацию времени. Оцените объём по bytes per request и retention, настройте ротацию и backpressure агента. При потере логов приложение не должно незаметно блокироваться из-за недоступного collector.

1. Задайте структурированную схему события с timestamp и trace ID.
2. Исключите токены, персональные данные и секреты до отправки.
3. Настройте retention, доступ и парсинг полей для поиска.
4. Проверьте корреляцию лога с запросом и работу при потере backend логов.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Запишите пример события в JSON с временем, уровнем, сервисом и trace ID.

**Как проверить.** Поля стабильны и подходят для машинного поиска.

### Шаг 2

**Что сделать.** Перед отправкой удалите Authorization, пароли и персональные данные.

**Как проверить.** Тестовый лог не содержит токенов и не даёт восстановить приватный запрос.

### Шаг 3

**Что сделать.** Задайте срок хранения и роли доступа, затем выполните поиск по service и request ID.

**Как проверить.** Оператор быстро находит нужный лог, а старые данные удаляются по утверждённому правилу.

### Шаг 4

**Что сделать.** Проверьте, что сервис продолжает работать при недоступности log backend.

**Как проверить.** Ошибка логирования видна, но не блокирует пользовательский запрос и не раскрывает данные.
