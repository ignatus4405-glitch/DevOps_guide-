# Моделирование угроз: STRIDE, границы доверия, zero trust

Безопасность начинается не со сканера, а с вопроса «как именно нас могут
сломать». Моделирование угроз — структурированный способ задать этот вопрос
до того, как это сделает атакующий.

## STRIDE

| Угроза | Что нарушает | Пример |
| --- | --- | --- |
| Spoofing | аутентичность | поддельный токен |
| Tampering | целостность | изменённый запрос |
| Repudiation | неотказуемость | «я не делал» |
| Information disclosure | конфиденциальность | утечка логов |
| Denial of service | доступность | флуд |
| Elevation of privilege | авторизацию | IDOR, лишняя роль |

Для каждого компонента проходим по шести категориям и записываем, что может
пойти не так.

## Границы доверия

Нарисуйте систему и отметьте, где данные переходят из одной зоны доверия в
другую:

```text
интернет → CDN → ingress → сервис → БД
         ↑ граница   ↑ граница  ↑ граница
```

На каждой границе нужны аутентификация, валидация и логирование. Внутри
«доверенной» сети тоже могут быть скомпрометированные узлы — это и есть идея
zero trust.

## Zero trust

Принципы:

1. **Не доверять сети** — проверять каждый запрос.
2. **Least privilege** — минимальные права и короткий срок.
3. **Явная проверка** — аутентификация и авторизация на каждом шаге.
4. **Микросегментация** — сетевые политики между сервисами.
5. **Логирование и обнаружение** — предполагать компрометацию.

Практика в Kubernetes: NetworkPolicy default-deny, mTLS между сервисами,
SPIFFE-идентичности, короткоживущие токены.

## Модель за 30 минут

1. Соберите схему компонентов и потоков данных.
2. Отметьте границы доверия.
3. Для каждой границы пройдитесь по STRIDE.
4. Оцените вероятность и ущерб.
5. Выберите контроль, который можно проверить.
6. Запишите владельца и дату пересмотра.

Результат — таблица, а не документ на 40 страниц.

## Пример: API заказов

| Угроза | Сценарий | Контроль |
| --- | --- | --- |
| Spoofing | украденный JWT | короткий TTL, rotation, mTLS |
| Tampering | подмена суммы | подпись, серверная валидация |
| Info disclosure | IDOR `/orders/123` | проверка владельца |
| DoS | флуд поиска | rate limit, кэш |
| Elevation | лишняя роль в SA | RBAC-ревью, `auth can-i` |

## Оценка риска

Простая матрица: вероятность × ущерб. Не все угрозы равны. Уязвимость в
админке за VPN и в публичном API — разный приоритет.

Риск без владельца не исправляется. У каждой строки должен быть человек и срок.

## Связь с процессом

- при новом сервисе — модель угроз в дизайн-ревью;
- при изменении потоков данных — обновить;
- раз в квартал — пересмотр;
- findings — в трекер, а не в wiki.

## Подробный разбор темы

Начинайте модель угроз с актива, границ доверия, участников и потоков данных. STRIDE помогает систематизировать угрозы: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege. Для каждой угрозы запишите путь атаки, предпосылки, ущерб и существующий контроль. Это превращает разговор «а вдруг взломают?» в список проверяемых сценариев.

Zero trust не означает блокировать всё без причины; это проверять identity, контекст и минимальные права на каждом переходе. Пересматривайте модель при добавлении нового внешнего API, роли или типа данных. Приоритизируйте по вероятности и влиянию, выберите обработку: уменьшить риск, принять с основанием, передать или исключить функцию.

## Пошаговый сценарий

![Порядок действий: Моделирование угроз: STRIDE, границы доверия, zero trust](assets/img/howto/11-devsecops--07-threat-modeling.svg)

1. Нарисуйте data flow и отметьте внешние границы и привилегии.
2. Перечислите активы, злоумышленников и возможные пути атаки.
3. Оцените риск и сопоставьте его с контролем и владельцем.
4. Проверьте модель после изменения архитектуры или релиза.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Нарисуйте данные и потоки между клиентом, API, очередью и хранилищем; пунктиром выделите внешние границы.

**Как проверить.** На схеме видно, где недоверенный ввод попадает в систему.

### Шаг 2

**Что сделать.** Запишите важные данные и возможные злоупотребления: кто может украсть, изменить или остановить их.

**Как проверить.** Угрозы связаны с конкретными активами и путями, а не с абстрактным словом «хакер».

### Шаг 3

**Что сделать.** Оцените вероятность и ущерб, затем выберите защиту и владельца.

**Как проверить.** У самой рискованной угрозы есть проверяемая мера и ответственный.

### Шаг 4

**Что сделать.** Пересмотрите модель после изменения API, доступа или потока данных.

**Как проверить.** Изменённая архитектура не продолжает использовать устаревшую модель угроз.
