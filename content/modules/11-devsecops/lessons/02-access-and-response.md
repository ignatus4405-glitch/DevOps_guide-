# Доступы, аудит и реагирование на инциденты безопасности

## Наименьшие привилегии на всех уровнях

| Уровень | Типовые ошибки | Как правильно |
| --- | --- | --- |
| Облако (IAM) | `*:*` в политиках, долгоживущие ключи | роли, условия, OIDC для CI |
| CI/CD | GitHub Actions с `contents: write` по умолчанию | `permissions` минимально, environment approval |
| Kubernetes | `cluster-admin` для CI, default ServiceAccount | роли по namespace, `automountServiceAccountToken: false` |
| Серверы | парольный root-вход, общий ключ на команду | только ключи, sudo по ролям, отдельные ключи |
| Базы данных | один суперпользователь для всех | отдельные роли: миграции / чтение / запись |
| Секреты | хранение в переменных CI без ограничений | доступ по окружениям, короткая жизнь |

```yaml
# Kubernetes: минимум прав для приложения
apiVersion: v1
kind: ServiceAccount
metadata: { name: api, namespace: prod }
automountServiceAccountToken: false      # токен не нужен — не монтируем
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: api-reader, namespace: prod }
rules: []                                # приложению обычно НЕ нужны права в API
```

```bash
kubectl auth can-i --list -n prod --as=system:serviceaccount:prod:api
aws iam generate-service-last-accessed-details --arn arn:aws:iam::123:role/app
# неиспользуемые права → показать и убрать
```

Регулярная «уборка прав» (access review): раз в квартал проверяем, кто и что может,
убираем лишнее, ротируем креды, закрываем неиспользуемые аккаунты.

## Аудит и мониторинг безопасности

```bash
# Что включить:
# - CloudTrail/аудит API в облаке (все регионы, immutable)
# - audit-логи Kubernetes (кто создал/удалил pod, изменил роли)
# - журнал аутентификации (SSH, sudo)
# - логи CI (кто запускал деплой, с какими правами)

sudo grep -i "failed password" /var/log/auth.log | tail -20
journalctl -u ssh -n 50
kubectl logs -n kube-system -l component=kube-apiserver | grep -i "user" | tail
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=StopInstances --max-items 10
```

Алерты, которые стоит настроить сразу: вход root/админа, изменение IAM-политик,
создание access key, отключение защиты (например, удаление public access block),
массовое удаление объектов, вход с нового IP/страны для админов.

## Supply chain: цепочка поставки

```
Коммит → CI (изолированный runner) → сборка образа → подпись → реестр → admission control → prod
```

Что защищает каждый участок: ревью и branch protection (коммит), минимальные права
токена (CI), фиксированные версии базовых образов и actions (сборка), cosign
(подпись), политики допуска (admission), запрет `latest` и неподписанных образов (prod).

```yaml
# Kyverno: не запускать образы без подписи и от root
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-images }
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-signature
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["ghcr.io/org/*"]
          attestors:
            - entries: [{ keyless: { subject: "https://github.com/org/*" } }]
    - name: require-non-root
      match: { any: [{ resources: { kinds: [Pod] } }] }
      validate:
        message: "runAsNonRoot обязателен"
        pattern:
          spec: { securityContext: { runAsNonRoot: true } }
```

## Реагирование на инцидент безопасности

Отличие от «обычной» аварии: сначала **остановить утечку и сохранить улики**, потом
восстанавливать. Не уничтожайте доказательства (не перезаписывайте образ, не
удаляйте логи).

```markdown
# Runbook: подозрение на компромисс контейнера/сервиса

1. ИЗОЛИРОВАТЬ: пометить pod/инстанс, снять из балансировки, отозвать временные креды.
2. СОХРАНИТЬ СЛЕДЫ: снапшот диска, копия логов, память (если нужно), список процессов.
3. ОЦЕНИТЬ МАСШТАБ: какие креды были доступны сервису, куда он имел доступ, есть ли lateral movement.
4. ОТОЗВАТЬ И ПЕРЕВЫПУСТИТЬ: все доступные секреты, ключи, токены (в порядке «наибольший радиус → наименьший»).
5. ВОССТАНОВИТЬ из проверенного артефакта (образ по digest, подписанный).
6. РАЗБОРКА: как попали, что позволило, какие проверки провалили; action items с владельцами.
7. РЕГУЛЯТОРНОЕ: при утечке персональных данных — уведомление по политике компании (GDPR: 72 часа).
```

!!! warning "Важно"
    «Тихий фикс» инцидента безопасности — худший вариант: вы теряете данные для
    разбора и рискуете повторить. Ведите журнал действий с таймстампами и фиксируйте
    всё, что сделали, — это и есть материалы для постмортема и (при необходимости)
    для отчётности.

## Соответствие требованиям без бюрократии

Регуляторные требования (PCI DSS, ISO 27001, GDPR) проще выполнять, когда
автоматизация уже есть: теги и аудит — для инвентаризации, IaC — для воспроизводимости,
сканирование — для контроля уязвимостей, бэкапы с проверкой — для доступности,
RBAC и MFA — для контроля доступа. То есть **безопасность и compliance
опираются на те же инженерные практики**, что и надёжность.

## Принцип наименьших привилегий в доступах

- доступ по группам, не персонально;
- временный доступ (just-in-time) вместо постоянного;
- MFA для всех, кто может менять прод;
- отдельные роли для CI;
- регулярный пересмотр (access review) раз в квартал.

```bash
aws iam get-account-authorization-details
kubectl auth can-i --list --as=system:serviceaccount:app:deployer
```

## Break-glass доступ

Иногда нужен аварийный доступ ко всему. Он должен быть:

1. Отдельной ролью с громким именем.
2. С обязательным алертом при использовании.
3. С ограничением по времени.
4. С последующим разбором.

Break-glass без алерта превращается в обычный доступ, о котором никто не знает.

## Реагирование: первые 15 минут

| Минута | Действие |
| --- | --- |
| 0–2 | подтвердить инцидент, открыть канал |
| 2–5 | изолировать: отозвать ключи, заблокировать IP/под |
| 5–10 | оценить масштаб: какие данные и сервисы |
| 10–15 | назначить ответственного и коммуникацию |

Не начинайте с поиска виноватого и не пытайтесь сразу «понять всё». Сначала
остановить ущерб.

## Модель угроз за 30 минут

Полноценный threat modeling не требует недели. Достаточно ответить на четыре
вопроса для каждого компонента:

1. **Что защищаем?** Данные, деньги, доступ, репутацию.
2. **Кто может атаковать?** Внешний пользователь, уволенный сотрудник,
   скомпрометированный сервис.
3. **Как попадёт внутрь?** Публичный API, зависимости, CI, человеческий
   фактор.
4. **Что снизит риск?** Контроль, который действительно можно проверить.

| Компонент | Угроза | Контроль |
| --- | --- | --- |
| API | подбор токена | rate limit, короткий TTL |
| CI | вредоносный PR | approval, least privilege токена |
| образ | подмена | подпись и проверка в admission |
| база | утечка | шифрование, сетевые политики |

Модель без владельца и даты пересмотра устаревает за квартал. Храните её
рядом с архитектурой и обновляйте при изменении потоков данных.

## Короткое резюме

- Наименьшие привилегии применяются на всех уровнях: IAM, CI, k8s, серверы, БД.
- Аудит и алерты на чувствительные действия обязательны в любом аккаунте.
- Цепочка поставки защищается подписями, SBOM и политиками допуска.
- В инциденте безопасности сперва изоляция и сохранение улик, затем восстановление и разбор.

## Подробный разбор темы

Доступ начинается с identity, authentication и authorization: кто именно вошёл, чем подтвердил личность и какое действие ему разрешено. Разделяйте человеко-ориентированные учётные записи и service identity; используйте MFA, короткий срок сессии и минимальную роль. Общая учётная запись лишает аудит смысла, потому что действие нельзя связать с владельцем.

При подозрении на компрометацию сначала определите scope, затем сохраните необходимые доказательства и отзовите токен/роль. Ротация ключа не должна уничтожать логи и timeline. После containment проверьте новые login и API calls, восстановите только нужные права и задокументируйте причину. Runbook должен указывать, кому сообщать об инциденте и как сохранить цепочку хранения артефактов.

## Пошаговый сценарий

![Порядок действий: Доступы, аудит и реагирование на инциденты безопасности](assets/img/howto/11-devsecops--02-access-and-response.svg)

1. Назначьте владельца и минимальную identity для каждого workload.
2. Включите audit log и быстрый поиск привилегированных действий.
3. Подготовьте проверенный план изоляции учётной записи и отзыва ключа.
4. Проведите учение и подтвердите время обнаружения и безопасного восстановления.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Для каждого сервиса укажите владельца identity и разрешённые API-действия.

**Как проверить.** Нет общего ключа, которым пользуются приложения и люди одновременно.

### Шаг 2

**Что сделать.** Включите журнал audit и найдите тестовое привилегированное действие.

**Как проверить.** Лог показывает identity, объект, время и результат действия.

### Шаг 3

**Что сделать.** Напишите инструкцию отзыва доступа: остановить identity, отозвать токен, проверить соседние сервисы.

**Как проверить.** Дежурный может пройти инструкцию в тесте, не угадывая владельца.

### Шаг 4

**Что сделать.** Проведите учебную тревогу с тестовой identity и замерьте время обнаружения/изоляции.

**Как проверить.** Доступ отозван, пользовательский impact понятен, восстановление проверено.
