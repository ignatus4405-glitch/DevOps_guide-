# SAST, DAST, SCA: что и когда запускать

Безопасность приложения проверяется разными инструментами на разных этапах. Важно
понимать, что каждый находит, а что — нет, и не превращать сканы в шум.

## Три класса проверок

| Класс | Что проверяет | Когда | Примеры |
| --- | --- | --- | --- |
| SAST | исходный код | на коммит | Semgrep, CodeQL, SonarQube |
| SCA | зависимости | на коммит и по расписанию | Dependabot, pip-audit, Trivy |
| DAST | работающее приложение | на staging | OWASP ZAP, Burp |
| Secret scanning | секреты | на коммит | gitleaks, trufflehog |
| IaC scanning | инфраструктура | на PR | checkov, tfsec, kics |

Ни один класс не заменяет другой: SAST не видит конфигурацию, DAST — код,
SCA — логические ошибки.

## SAST: как использовать

```bash
semgrep --config auto --error
codeql database create db --language=python
```

Проблемы:

- ложные срабатывания (особенно в динамических языках);
- медленность на больших репозиториях;
- «отключим, потому что шумит».

Правильный подход: начать с критичных правил (SQL-инъекции, SSRF, десериализация),
постепенно расширять. Каждое исключение — с обоснованием и сроком.

## SCA: зависимости

```bash
pip-audit
npm audit --audit-level=high
trivy fs --severity HIGH,CRITICAL .
```

Политика:

- CRITICAL с доступным фиксом — блокирует merge;
- HIGH — задача с дедлайном;
- остальное — отчёт.

Важно сканировать и образ, а не только lock-файл: в базовом образе тоже есть
пакеты.

## DAST: динамика

```bash
docker run -t owasp/zap2docker-stable zap-baseline.py -t https://staging.example.com
```

ZAP baseline находит заголовки безопасности, открытые админки, простые XSS.
Полное сканирование — дольше и агрессивнее, только на выделенном стенде.

Не запускайте DAST на проде: он может создать мусорные данные и задеть
пользователей.

## Приоритизация

| Критичность | Что делать |
| --- | --- |
| exploitable в проде | фикс немедленно, hotfix |
| critical CVE | фикс в течение 7 дней |
| high | 30 дней |
| medium/low | плановое обновление |

Ориентируйтесь на эксплуатируемость, а не только на CVSS: уязвимость в
неиспользуемом компоненте менее опасна.

## Встраивание в процесс

1. Pre-commit: секреты, линтер.
2. PR: SAST, SCA, IaC scan.
3. Merge: блокирующие гейты.
4. Ночью: полный скан и обновление баз.
5. Релиз: SBOM и подпись.
6. Прод: runtime-детект.

## Подробный разбор темы

SAST анализирует исходный код без запуска и полезен рано в разработке; SCA сопоставляет зависимости с базой уязвимостей и лицензий; DAST проверяет работающий сервис через внешние запросы. Ни один сканер не покрывает все классы проблем. Выбирайте инструмент и этап по возможному ущербу и скорости обратной связи, а не по числу отчётов.

Настройте baseline, чтобы новые критичные находки не терялись среди старых, назначьте владельцев и SLA устранения. Для ложного срабатывания сохраняйте reason и scope, а не отключайте весь rule. DAST запускайте на выделенной тестовой среде с ограниченными данными и правами; убедитесь, что тесты не выполняют опасные операции и не затрагивают production.

## Пошаговый сценарий

![Порядок действий: SAST, DAST, SCA: что и когда запускать](assets/img/howto/11-devsecops--04-appsec.svg)

1. Опишите пользовательский поток, входные данные и границы доверия.
2. Добавьте безопасные проверки кода и зависимостей в ранний CI.
3. Проведите динамический тест в изолированной тестовой среде.
4. Исправьте и проверьте finding, затем сохраните доказательства и владельца риска.
