# Карта инструментов DevOps-инженера

Инструментов в DevOps hundreds, но все они закрывают **шесть задач**. Если понимать
задачи, то выбор инструмента перестаёт быть магией: новый инструмент почти всегда
делает то же самое, но иначе.

| Задача | Что закрывает | Основные инструменты | Модуль курса |
| --- | --- | --- | --- |
| Управление кодом | версии, ревью, история | Git, GitHub/GitLab | 3 |
| Сборка и проверка | тесты, линтеры, артефакты | GitHub Actions, GitLab CI, Jenkins | 5 |
| Упаковка | одинаковое окружение везде | Docker, containerd, Buildah | 6 |
| Оркестрация | запуск и масштабирование | Kubernetes, Nomad, ECS | 7 |
| Инфраструктура | создание ресурсов кодом | Terraform, Ansible, Pulumi | 8 |
| Наблюдаемость | метрики, логи, трейсы | Prometheus, Grafana, Loki, OTel | 10 |

## Как выбирают инструмент в реальной команде

1. **Совместимость с существующим стеком.** Если в компании уже Kubernetes,
   тащить Nomad никто не будет.
2. **Стоимость владения.** Инструмент, требующий отдельного инженера на поддержку,
   проигрывает managed-сервису.
3. **Порог входа и найм.** На рынке должно быть достаточно людей, умеющих это поддерживать.
4. **Активность сообщества.** Дата последнего релиза и количество контрибьюторов —
   хороший индикатор, что проект не умрёт.
5. **Обратная совместимость.** Инструмент обновляется без боли (нынешний лидер
   IaC — Terraform и его открытый форк OpenTofu — именно за это и любят).

!!! warning "Важно"
    Не превращайте резюме в список инструментов. На собеседовании спрашивают:
    «Почему ты выбрал это решение? Что было бы, если бы нагрузка выросла в 10 раз?»
    Инструмент — следствие задачи, а не наоборот.

## Минимальный стек, с которого начинают

| Область | Учим | Почему |
| --- | --- | --- |
| ОС | Linux (Ubuntu/Debian) | 90 % production — Linux |
| Скрипты | Bash | основа автоматизации и входа в контейнеры |
| Код | Git + GitHub | без этого нет ни одной вакансии |
| Сети | TCP/IP, DNS, HTTP, TLS | 80 % инцидентов — сетевые |
| CI | GitHub Actions | бесплатен, встроен в репозиторий |
| Контейнеры | Docker + Compose | стандарт упаковки |
| Оркестрация | Kubernetes | стандарт запуска |
| IaC | Terraform | стандарт описания инфраструктуры |
| Мониторинг | Prometheus + Grafana | стандарт наблюдаемости |

Этот список — **скелет курса**: мы проходим его последовательно, и каждый модуль
опирается на предыдущий.

## Что изучать после базы

- **Расширенная автоматизация**: Ansible (конфигурация серверов), Packer (образы ВМ).
- **Секреты**: HashiCorp Vault, External Secrets Operator, sealed secrets.
- **GitOps**: Argo CD или Flux — деплой из Git без ручных команд.
- **Стоимость**: FinOps-практики, rightsizing, tagging.
- **Надёжность**: chaos engineering, нагрузочное тестирование (k6, Locust).
- **Платформы**: Backstage как каталог сервисов, self-service окружения.

## Ловушки обучения

| Ловушка | Как выглядит | Что делать |
| --- | --- | --- |
| Туториал-ад | 20 незаконченных курсов | довести один проект до прода |
| Copy-paste без понимания | команда «работает, но почему — не знаю» | объяснять каждую команду вслух |
| Прыжок в Kubernetes | «не знаю Linux, но учу k8s» | база раньше, иначе k8s непонятен |
| Кнопки вместо кода | всё в веб-консоли | переписать в Terraform/манифесты |
| Без мониторинга | «задеплоил — всё ок» | добавить метрику до релиза |

## Короткое резюме

- Все инструменты DevOps закрывают шесть задач: код, сборка, упаковка,
  оркестрация, инфраструктура, наблюдаемость.
- Выбор инструмента определяется стеком команды, стоимостью владения и наймом.
- Базовая последовательность обучения задаёт этот курс: Linux → Bash → Git →
  сети → CI/CD → Docker → Kubernetes → IaC → облако → мониторинг → DevSecOps.

## Один инструмент — одна задача

Полезно держать в голове границы: большинство «конфликтов» инструментов — это
разные задачи, которые пытаются решить одним средством.

| Задача | Инструменты | Что важно понять |
| --- | --- | --- |
| Собрать артефакт | Docker, Buildah, Nix | воспроизводимость важнее удобства |
| Описать инфраструктуру | Terraform, Pulumi, CloudFormation | состояние и plan — главное |
| Настроить сервер | Ansible, cloud-init, Ignition | идемпотентность |
| Запустить контейнеры | Kubernetes, Nomad, ECS | оркестратор не заменяет CI |
| Доставить изменения | GitHub Actions, GitLab CI, Argo CD | push или pull-модель |
| Наблюдать | Prometheus, Loki, Tempo, OTel | метрики, логи, трейсы — разное |
| Хранить секреты | Vault, SOPS, облачный KMS | секрет не должен жить в git |

## Как читать вакансии

В описании вакансии инструменты перечислены через запятую, но за ними стоят
повторяющиеся задачи. Учитесь переводить:

- «Kubernetes, Helm, Argo CD» → умеете доставлять и сопровождать сервисы в кластере;
- «Terraform, AWS, VPC» → умеете описать облачную инфраструктуру и не ломать сеть;
- «Prometheus, Grafana, SLO» → умеете отвечать за надёжность, а не только за деплой;
- «GitHub Actions, Docker, security scanning» → умеете строить конвейер с проверками.

Инструмент в резюме — это гипотеза о задачах. На собеседовании спрашивают именно
про задачи: как откатывали релиз, как искали причину инцидента, как уменьшали
время сборки.

## Чего не стоит делать новичку

- **Собирать «стек мечты»** из 20 инструментов, не доведя ни один сценарий до конца.
- **Учить Kubernetes раньше Linux**: без понимания процессов, сети и файлов ошибки
  выглядят магией.
- **Игнорировать Git**: половина реальной работы — ветки, ревью, конфликты, история.
- **Пропускать безопасность**: секреты в репозитории и контейнеры от root — самые
  частые находки аудита у начинающих.

## Подробный разбор темы

Выбирайте инструмент после формулировки задачи и ограничений. Для управления конфигурацией важны идемпотентность и область применения; для контейнеров — воспроизводимая сборка и изоляция; для наблюдаемости — возможность связать сигнал с пользовательским симптомом. Одинаковое название категории не означает одинаковое решение: агентная система может быть удобна в закрытой сети, а управляемый облачный сервис — если команда не хочет поддерживать его сама.

Разберите путь одного изменения: разработчик отправляет commit, CI проверяет и создаёт артефакт, registry хранит его, CD развёртывает, метрики подтверждают здоровье. На каждой границе зафиксируйте контракт: формат входа, владельца и критерий успеха. Это помогает не покупать набор разрозненных продуктов, а выбирать минимальный стек, который закрывает реальную проблему и не создаёт лишней операционной нагрузки.
