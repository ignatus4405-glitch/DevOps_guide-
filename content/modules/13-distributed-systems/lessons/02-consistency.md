# Консистентность: CAP, PACELC, кворумы и консенсус

![Спектр консистентности](assets/img/consistency-spectrum.svg)

Когда данные лежат на нескольких узлах, всегда есть выбор: ответить быстро и,
возможно, устаревшими данными или подождать, пока все узлы договорятся.
«Согласованность» — не одно свойство, а спектр моделей.

## CAP без упрощений

Теорема CAP утверждает: при **сетевом разделении** система не может быть
одновременно согласованной и доступной.

- **C (consistency)** — линейизуемость: чтение видит последнюю запись.
- **A (availability)** — каждый запрос получает ответ (не обязательно свежий).
- **P (partition tolerance)** — система продолжает работать при потере связи.

Ключевая тонкость: `P` — не опция. Сеть рвётся всегда, поэтому реальный выбор —
что делать **во время** разделения: отказать в части запросов (CP) или отдать
старые данные (AP). В обычное время система может быть и согласованной, и
доступной.

## PACELC: что происходит без сбоя

PACELC расширяет CAP: если разделения нет (`E`), приходится выбирать между
задержкой (`L`) и согласованностью (`C`).

| Система | При разделении | Обычно |
| --- | --- | --- |
| PostgreSQL (single primary) | CP | согласованность, задержка записи |
| Cassandra | AP | низкая задержка, eventual |
| etcd | CP | кворум, строгий порядок |
| Redis (async replica) | AP | быстро, возможна потеря |

## Модели согласованности

От самой сильной к самой слабой:

1. **Линейизуемость** — все видят один порядок, запись видна сразу после
   подтверждения.
2. **Sequential consistency** — общий порядок, но без привязки к реальному
   времени.
3. **Read-your-writes** — клиент видит свои записи.
4. **Monotonic reads** — время не «откатывается» для клиента.
5. **Eventual consistency** — при отсутствии новых записей реплики сойдутся.

Для большинства продуктов достаточно read-your-writes и eventual, а не полной
линейизуемости. Выбор влияет на UX: пользователь, только что изменивший профиль,
должен увидеть изменение — это делают чтением с primary или версионированием.

## Кворумы

В реплицированной системе с `N` репликами:

- запись считается успешной при `W` подтверждениях;
- чтение опрашивает `R` реплик;
- если `W + R > N`, чтение гарантированно пересекается с последней записью.

Пример: `N=3, W=2, R=2`. Устойчивость к отказу одного узла, запись ждёт двух.
`W=1, R=1` — быстро, но можно прочитать старое значение.

Кворум не отменяет конфликтов: нужна версия (vector clock, timestamp) и правило
разрешения. «Last write wins» по часам клиента ломается при рассинхроне времени.

## Консенсус

Когда узлам нужно договориться о порядке событий (выбор лидера, конфигурация,
блокировки), используют алгоритмы консенсуса: Raft, Paxos, Zab. Идея Raft:

1. лидер принимает записи в журнал;
2. реплицирует их на большинство;
3. только после этого подтверждает клиенту;
4. при падении лидера выбирается новый с самым полным журналом.

Консенсус дорог: каждое решение — сетевое голосование. Поэтому etcd/ZooKeeper
держат маленькие метаданные, а не пользовательские данные.

## ACID и BASE

- **ACID** — атомарность, согласованность, изоляция, долговечность. Нужен там,
  где важны транзакции: деньги, заказы, инвентарь.
- **BASE** — basically available, soft state, eventual consistency. Подходит для
  лент, счётчиков, рекомендаций.

Это не «старое против нового», а разные инструменты под разные требования.

## Уровни изоляции

| Уровень | Аномалия, которую допускает |
| --- | --- |
| Read uncommitted | грязное чтение |
| Read committed | неповторяемое чтение |
| Repeatable read | фантомы (зависит от СУБД) |
| Serializable | практически нет |

Повышение уровня стоит блокировок и ретраев. Ошибка `serialization failure` —
нормальный сигнал повторить транзакцию, а не признак бага.

## Как выбирать

1. Спросите, что произойдёт, если пользователь увидит старые данные.
2. Определите, допустима ли потеря подтверждённой записи.
3. Посчитайте бюджет задержки: консенсус — это минимум два round-trip.
4. Запишите решение и его цену в ADR.

## Как проверить себя

1. Почему `P` в CAP нельзя «выключить»?
2. Что добавляет PACELC к CAP?
3. При `N=3, W=2, R=1` гарантировано ли свежее чтение?
4. Зачем консенсусу большинство, а не все узлы?
5. Чем ACID отличается от BASE по назначению?
