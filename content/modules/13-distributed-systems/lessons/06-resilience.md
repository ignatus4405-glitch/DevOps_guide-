# Паттерны устойчивости: таймауты, ретраи, предохранители

![Паттерны устойчивости](assets/img/resilience-patterns.svg)

Распределённая система состоит из сбоев. Вопрос не «упадёт ли зависимость»,
а «как сервис поведёт себя, когда она упадёт». Паттерны ниже — базовый набор.

## Таймауты

Без таймаута запрос может ждать минуты, занимая поток и соединение. Таймаут
должен быть **меньше** бюджета запроса пользователя и учитывать хвост latency.

```text
бюджет страницы 1,5 с
→ таймаут сервиса A 600 мс
→ таймаут БД внутри A 300 мс
```

Правило: таймауты уменьшаются вглубь. Иначе внутренний вызов переживёт внешний
и продолжит тратить ресурсы впустую.

## Ретраи

Ретрай помогает при кратковременном сбое и вредит при перегрузке. Условия:

1. операция идемпотентна;
2. ошибка временная (5xx, timeout, connection reset), а не 4xx;
3. есть лимит попыток (2–3);
4. есть задержка с **jitter**;
5. есть общий бюджет ретраев на запрос.

```python
delay = min(cap, base * 2 ** attempt) * random.uniform(0.5, 1.0)
```

Без jitter все клиенты повторят одновременно и устроят вторую волну.

**Retry storm** — классическая авария: сервис замедлился, клиенты начали
повторять, нагрузка выросла, он замедлился сильнее. Поэтому ретраи обязаны
сочетаться с предохранителем и лимитами.

## Circuit breaker

Предохранитель размыкает цепь, когда доля ошибок превышает порог:

| Состояние | Поведение |
| --- | --- |
| Closed | запросы идут, ошибки считаются |
| Open | запросы сразу отклоняются |
| Half-open | пробные запросы проверяют восстановление |

Порог: например, 50 % ошибок за 10 секунд при минимуме 20 запросов. Плюс —
система не тратит ресурсы на заведомо падающую зависимость.

## Bulkhead

Изоляция ресурсов: отдельные пулы потоков/соединений для разных зависимостей.
Если один сервис завис, он не выест все потоки и остальные продолжат работать.

```yaml
pools:
  payments: {max_connections: 20}
  catalog:  {max_connections: 50}
```

В Kubernetes аналог — отдельные Deployment'ы и ResourceQuota, чтобы один сервис
не занял весь узел.

## Rate limiting

Защита от перегрузки и злоупотреблений:

- **token bucket** — запас токенов, пополняется с постоянной скоростью;
- **leaky bucket** — фиксированная скорость выхода;
- **sliding window** — точнее, дороже.

Лимиты бывают на пользователя, на IP, на API-ключ. Важно, что делать при
превышении: `429` с `Retry-After`, а не молчаливый отказ.

## Деградация

Лучше отдать усечённый ответ, чем ошибку:

- показать кэшированные данные;
- убрать рекомендации, оставить каталог;
- отключитьнекритичные проверки;
- вернуть «попробуйте позже» с понятным кодом.

Деградация должна быть **заранее спроектирована** и проверена: feature flag,
тест на отключение зависимости.

## Chaos-проверки

Регулярно ломайте систему намеренно: отключите реплику, добавьте задержку,
заблокируйте DNS. Если сервис не переживает — узнайте это в среду, а не в чёрную
пятницу.

Начните с малого: kill одного пода, затем — отказ зоны в staging.

## Как проверить себя

1. Почему таймаут внешнего вызова должен быть больше внутреннего?
2. Какие ошибки нельзя ретраить?
3. Зачем jitter в задержке ретрая?
4. Что делает half-open состояние предохранителя?
5. Чем bulkhead отличается от rate limiting?

!!! tip "Практика"
    Задача «Предохранитель» в практикуме: настроить пороги и проверить поведение.

## Подробный разбор темы

Timeout должен покрывать реалистичный бюджет latency всей цепочки и не превышать timeout вызывающего клиента. Ретрайте только временные ошибки, ограничивайте число попыток и добавляйте exponential backoff с jitter; иначе клиенты синхронно усилят нагрузку на уже перегруженный сервис. Для неидемпотентной операции используйте idempotency key или не повторяйте её автоматически.

Circuit breaker временно прекращает вызовы к явно нездоровой зависимости; bulkhead ограничивает ресурс, который она может занять. Эти паттерны работают только при корректном восстановлении half-open probe и наблюдаемости. Сымитируйте медленный ответ, отказ и частичный успех, затем проверьте, что пользователь получает понятную деградацию, а не бесконечное ожидание.

## Пошаговый сценарий

![Порядок действий: Паттерны устойчивости: таймауты, ретраи, предохранители](assets/img/howto/13-distributed-systems--06-resilience.svg)

1. Нарисуйте критические зависимости и определите режим деградации.
2. Задайте timeout, ограниченные retries с backoff/jitter и concurrency limits.
3. Изолируйте отказ circuit breaker или bulkhead без каскада на соседние запросы.
4. Проведите контролируемый failure test и проверьте автоматическое восстановление.
