# Данные: репликация, шардирование и миграции

Данные — самая сложная часть распределённой системы: их нельзя «просто
перезапустить». Ошибки здесь стоят дороже всего, а изменения требуют плана.

## Репликация

**Leader-follower**: один узел принимает записи, остальные читают. Просто,
предсказуемо, но запись ограничена одним лидером.

**Multi-leader**: несколько узлов принимают записи, нужны разрешение конфликтов
и осторожность с порядком.

**Leaderless (quorum)**: запись и чтение по кворуму, как в Cassandra.

Репликация бывает **синхронной** (подтверждение после записи на реплику) и
**асинхронной** (быстро, но возможна потеря при падении лидера). Синхронная
увеличивает latency записи, асинхронная — риск.

**Replication lag** — отставание реплики. Следствия: чтение со реплики отдаёт
старые данные. Лечение: читать критичные данные с лидера, использовать
read-your-writes, следить за метрикой lag.

## Шардирование

Когда данных больше, чем помещается на один узел, их делят по ключу:

```text
shard = hash(user_id) % N
```

Проблемы:

- **горячие шарды** — один ключ популярнее остальных;
- **перебалансировка** при изменении `N` (consistent hashing смягчает);
- **запросы через шарды** — joins и агрегаты дороги;
- **транзакции** между шардами почти всегда нельзя.

Выбор ключа важнее выбора СУБД: `tenant_id` даёт изоляцию, `created_at` —
горячую партицию «сейчас».

## Индексы и запросы

Индекс ускоряет чтение и замедляет запись. Правила:

1. Индексируйте по полям фильтрации и сортировки, а не «на всякий случай».
2. Составной индекс работает слева направо.
3. `LIKE '%text%'` индекс не использует.
4. Смотрите `EXPLAIN`, а не догадывайтесь.

## Миграции без простоя

Схема меняется на живой системе. Безопасный порядок — **expand/contract**:

1. **Expand**: добавить новое поле/таблицу, писать в оба места.
2. **Backfill**: заполнить исторические данные порциями.
3. **Switch**: переключить чтение на новое.
4. **Contract**: удалить старое после периода наблюдения.

```sql
ALTER TABLE orders ADD COLUMN status_new text;
-- backfill батчами по 1000
-- переключение чтения через feature flag
```

Никогда не делайте `ALTER TABLE ... SET NOT NULL` на большой таблице без
подготовки: это блокировка и простой.

## Бэкапы и восстановление

- **RPO** — сколько данных допустимо потерять.
- **RTO** — за сколько обязаны восстановиться.

Бэкап без проверки восстановления — не бэкап, а надежда. Раз в квартал
поднимайте копию и измеряйте время. PITR (point-in-time recovery) требует
журналов транзакций; проверьте, что они действительно есть.

## Согласованность в практике

| Сценарий | Модель |
| --- | --- |
| баланс счёта | strong, транзакции |
| лента новостей | eventual |
| счётчик просмотров | eventual, приблизительный |
| инвентарь | strong + резерв |

## Как проверить себя

1. Чем синхронная репликация хуже для latency?
2. Почему `hash % N` плохо переживает изменение числа шардов?
3. Что такое expand/contract и зачем он нужен?
4. Чем RPO отличается от RTO?
5. Почему бэкап нужно проверять восстановлением?

!!! tip "Практика"
    Задача «План миграции» в практикуме: расписать expand/contract по шагам.

## Подробный разбор темы

Репликация улучшает доступность и чтение, но требует правил выбора primary, разрешения конфликтов и допустимой задержки распространения. Шардирование распределяет объём по ключу; неравномерный ключ создаёт hot shard, а изменение схемы ключа может потребовать дорогой миграции. Выбирайте partition key по реальному паттерну чтения и роста, а не только по удобству модели данных.

Безопасная миграция обычно идёт шагами: добавить совместимое поле, писать новое и старое значение, backfill небольшими партиями, проверять расхождения, переключить чтение и удалить старое поле после окна отката. Dual write может потерять согласованность при частичном сбое; используйте outbox или другой надёжный протокол и измеряйте прогресс миграции.

## Пошаговый сценарий

![Порядок действий: Данные: репликация, шардирование и миграции](assets/img/howto/13-distributed-systems--07-data.svg)

1. Определите владельца записи, модель хранения и требования к согласованности.
2. Спроектируйте ключи, индексы, схему и путь её эволюции.
3. Проверьте backup, восстановление и совместимость читателей/писателей.
4. Испытайте миграцию на копии данных и сверяйте результаты до переключения.
