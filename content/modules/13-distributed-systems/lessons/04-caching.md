# Кэширование: стратегии, инвалидация и лавины

Кэш — самый быстрый способ ускорить систему и самый частый источник «почему
данные старые». Он обменивает свежесть на скорость, и этот обмен нужно
проектировать.

## Уровни кэша

| Уровень | Пример | Особенность |
| --- | --- | --- |
| клиент | браузер, HTTP-кэш | управляется заголовками |
| CDN | статика, API-ответы | географическая близость |
| приложение | in-memory (LRU) | быстрый, но локальный |
| распределённый | Redis/Memcached | общий, сетевой hop |
| БД | buffer pool, page cache | прозрачный |

Каждый уровень добавляет согласованность и наблюдаемость. Не начинайте с пяти
уровней: начните с измерения, где реально болит.

## Стратегии

**Cache-aside (lazy loading)** — приложение сначала читает кэш, при промахе —
БД и кладёт в кэш.

```python
value = cache.get(key)
if value is None:
    value = db.query(...)
    cache.set(key, value, ttl=60)
```

Плюс: кэшируется только нужное. Минус: первый запрос медленный, возможна
рассинхронизация.

**Read-through** — кэш сам загружает данные из БД.

**Write-through** — запись идёт в кэш и БД синхронно; медленнее, но свежее.

**Write-behind** — запись сначала в кэш, потом асинхронно в БД; риск потери.

**Refresh-ahead** — обновление до истечения TTL; сложнее, но без промаха.

## Инвалидация

Две проблемы: как понять, что данные устарели, и как не удалить слишком много.

- **TTL** — просто, но данные могут быть старыми до TTL.
- **Инвалидация по ключу** — точнее, требует дисциплины.
- **Версионирование** — ключ включает версию/хэш; старые записи истекают сами.
- **Событийная инвалидация** — сервис-источник публикует событие изменения.

Правило: источник истины — БД, кэш всегда вторичен. Если кэш потерян, система
должна работать, пусть и медленнее.

## Лавина, пробивание и протухание

- **Cache stampede** — TTL истёк у популярного ключа, сотни запросов идут в БД.
  Лечение: jitter в TTL, блокировка на пересчёт, stale-while-revalidate.
- **Cache penetration** — запросы к несуществующим ключам всегда мимо кэша.
  Лечение: кэшировать «пусто» с коротким TTL, фильтр Блума.
- **Cache avalanche** — падение всего кэша разом. Лечение: прогрев, ограничение
  параллельных запросов к БД, деградация.

```python
ttl = base_ttl + random.randint(0, 30)  # jitter
```

## Что кэшировать нельзя

- персональные данные без учёта прав доступа;
- ответы, зависящие от авторизации, в общем ключе;
- финансовые операции без строгой инвалидации;
- секреты и токены.

Ключ должен включать всё, что влияет на ответ: пользователя, локаль, версию,
параметры. Иначе один пользователь увидит данные другого — это уже инцидент
безопасности.

## Наблюдаемость кэша

Метрики: hit ratio, latency, evictions, memory, errors. Hit ratio 95 % звучит
хорошо, но если оставшиеся 5 % — дорогие запросы, БД всё равно перегружена.
Смотрите на стоимость промаха, а не только на процент.

## Как выбрать TTL

1. Насколько старые данные допустимы для продукта?
2. Как часто данные меняются?
3. Сколько стоит промах для БД?
4. Есть ли событие инвалидации?

TTL — это обещание пользователю: «данные могут быть устаревшими не дольше N».
Записывайте это в контракт.

## Как проверить себя

1. Чем cache-aside отличается от write-through?
2. Что такое cache stampede и как его предотвратить?
3. Почему кэш не должен быть источником истины?
4. Какой ключ кэша считается корректным?
5. Почему hit ratio сам по себе недостаточен?

## Подробный разбор темы

Cache-aside читает из кэша, при промахе обращается к источнику и записывает результат; write-through обновляет кэш вместе с записью, но усложняет путь операции. Для каждого ключа определите TTL, поведение при промахе и максимальный размер. TTL ограничивает длительность устаревания, но не гарантирует мгновенную консистентность после изменения данных.

Stampede возникает, когда множество запросов одновременно вычисляют один истёкший объект; single-flight, jitter и предварительное обновление уменьшают всплеск. Cache poisoning требует валидации входных параметров и границ кэшируемого ответа. Метрики hit ratio полезны только вместе с latency, backend load и долей устаревших данных: высокий hit rate не всегда означает хороший пользовательский результат.

## Пошаговый сценарий

![Порядок действий: Кэширование: стратегии, инвалидация и лавины](assets/img/howto/13-distributed-systems--04-caching.svg)

1. Определите ключ, владельца данных и допустимый срок устаревания.
2. Настройте TTL, invalidation и защиту от stampede.
3. Проверьте cache hit/miss и поведение при пустом или недоступном кеше.
4. Сверьте корректность после обновления исходных данных и конкурентных запросов.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Опишите, что кэшируется, для кого данные и сколько секунд старые данные ещё допустимы.

**Как проверить.** Для ключа учтены пользователь/язык/права, а время устаревания согласовано с владельцем данных.

### Шаг 2

**Что сделать.** Настройте TTL и правило очистки; добавьте защиту от одновременного запроса тысяч клиентов после истечения TTL.

**Как проверить.** Просроченное значение обновляется, а массовый cache miss не перегружает базу.

### Шаг 3

**Что сделать.** Посмотрите hit/miss и отключите кэш на коротком тесте или очистите тестовый ключ.

**Как проверить.** При попадании ответ приходит из кэша, при промахе — из источника.

### Шаг 4

**Что сделать.** Измените исходные тестовые данные и проверьте, когда кэш обновится при конкурентных запросах.

**Как проверить.** Пользователь не видит запрещённые устаревшие данные; недоступный кэш не ломает сервис неожиданно.
