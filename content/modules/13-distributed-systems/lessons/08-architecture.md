# Архитектурные решения и компромиссы

Хорошая архитектура — не «микросервисы» и не «монолит», а решение, которое
подходит контексту и записано так, что его можно пересмотреть.

## Монолит или микросервисы

| Критерий | Монолит | Микросервисы |
| --- | --- | --- |
| Скорость старта | высокая | низкая |
| Сложность эксплуатации | низкая | высокая |
| Независимые релизы | ограничены | да |
| Изоляция сбоев | слабая | сильнее |
| Транзакции | простые | распределённые |
| Команда | одна | несколько |

Микросервисы решают **организационную** проблему: много команд не могут
независимо менять один код. Если команд одна-две, они чаще добавляют сложность,
чем убирают.

## Conway's law

Архитектура системы повторяет структуру коммуникаций организации. Если хотите
независимые сервисы — нужны независимые команды с ясными границами
ответственности. Иначе получите «распределённый монолит»: отдельные сервисы,
которые деплоятся только вместе.

## Границы сервисов

Хорошая граница:

- совпадает с бизнес-возможностью (заказы, оплата, каталог);
- имеет собственные данные;
- меняется по своим причинам;
- может быть переписана без переписывания всего.

Плохая граница — по слоям (`controller-service-repository`): тогда любое
изменение затрагивает все сервисы.

## ADR: Architecture Decision Record

Решение без записи теряется. Шаблон:

```markdown
# ADR-007: Kustomize вместо Helm

## Контекст
Свои манифесты, 2 команды, нет внешних чартов.

## Решение
Используем Kustomize overlays.

## Последствия
+ нет шаблонного языка, diff читается
− нет версионирования пакетов
− при росте зависимостей вернёмся к Helm
```

ADR хранится в репозитории рядом с кодом, имеет дату и статус
(`proposed/accepted/superseded`). Он объясняет «почему», а не только «что».

## Эволюционная архитектура

Не проектируйте на пять лет вперёд. Проектируйте так, чтобы можно было изменить:

- границы модулей и контракты;
- feature flags для поведения;
- обратную совместимость API (versioning);
- возможность отката.

«Самый гибкий» вариант часто самый дорогой. Гибкость нужна там, где ожидаются
изменения, а не везде.

## Оценка решений

Задайте пять вопросов:

1. Какую проблему решаем и как измерим успех?
2. Какие альтернативы рассмотрели?
3. Что станет хуже (цена решения)?
4. Как откатим, если не сработает?
5. Когда пересмотрим решение?

Если ответов нет — это не архитектура, а вкусовщина.

## Стоимость и сложность

Каждый компонент добавляет:

- эксплуатацию (обновления, мониторинг, дежурства);
- когнитивную нагрузку;
- точки отказа;
- расходы.

Простое решение, которое работает, лучше элегантного, которое нужно
сопровождать. «Скучные технологии» — комплимент.

## Как проверить себя

1. Какую проблему решают микросервисы в первую очередь?
2. Что такое распределённый монолит?
3. Зачем нужен ADR и что в нём обязательно?
4. Почему «самый гибкий» вариант может быть плохим?
5. Какие вопросы задать перед архитектурным решением?

!!! tip "Практика"
    Задача «ADR» в практикуме: записать решение с альтернативами и последствиями.

## Подробный разбор темы

Выбор между монолитом и микросервисами — выбор границ развёртывания, данных и ответственности. Модульный монолит может сохранять простую эксплуатацию при чётких внутренних контрактах; микросервисы помогают независимым командам масштабировать и выпускать части системы, но добавляют сеть, discovery, версионирование API и частичные отказы.

Записывайте существенные решения в ADR вместе с контекстом, альтернативами и условиями пересмотра. Для каждой границы оцените latency, нагрузку, владельца данных, безопасность и способ локального тестирования. Архитектуру проверяйте по эволюции: насколько легко добавить функцию, восстановить данные и отключить компонент. Не дробите систему только потому, что это соответствует популярной диаграмме.

## Пошаговый сценарий

![Порядок действий: Архитектурные решения и компромиссы](assets/img/howto/13-distributed-systems--08-architecture.svg)

1. Соберите требования, ограничения, сценарии отказа и SLO заинтересованных сторон.
2. Нарисуйте компоненты, data flow и границы владения.
3. Сравните варианты по надёжности, безопасности, стоимости и сложности эксплуатации.
4. Зафиксируйте решение, допущения и сигналы, при которых архитектуру пересмотреть.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Выпишите пользователей, основные сценарии, SLO, ограничения по цене и данным.

**Как проверить.** Заказчик подтверждает, что список требований соответствует задаче.

### Шаг 2

**Что сделать.** Нарисуйте компоненты, потоки данных и ответственных владельцев.

**Как проверить.** Можно проследить путь запроса и найти систему, в которой живёт каждое данное.

### Шаг 3

**Что сделать.** Сравните два варианта по отказам, безопасности, стоимости и сложности поддержки.

**Как проверить.** Выбор объяснён компромиссами; не существует «лучшей архитектуры» без требований.

### Шаг 4

**Что сделать.** Запишите решение и сигналы для пересмотра: например, нагрузка превысила лимит или изменился SLO.

**Как проверить.** Коллега сможет понять, почему выбран вариант и при каком условии его надо поменять.
