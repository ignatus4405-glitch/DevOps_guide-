# Миграция в облако: стратегии, cutover, DR

Перенос в облако — не «поднять сервер и скопировать файлы». Ошибки в миграции
стоят дороже, чем сама миграция: простой, потеря данных, несовместимость.

## Шесть стратегий (6R)

| Стратегия | Что делаете | Когда |
| --- | --- | --- |
| Rehost | lift-and-shift на ВМ | быстрый переезд, минимум изменений |
| Replatform | managed-сервисы вместо своих | БД, кэш, очереди |
| Repurchase | переход на SaaS | CRM, почта |
| Refactor | переписать под облако | долгосрочная выгода |
| Retire | выключить ненужное | всегда начинайте с этого |
| Retain | оставить on-prem | регуляторика, legacy |

Начинайте с Retire: часто 10–20 % систем не нужны, и их перенос — чистая трата.

## Оценка и планирование

1. Инвентаризация: что есть, кто владелец, зависимости.
2. Классификация: критичность, данные, интеграции.
3. Выбор стратегии для каждого сервиса.
4. Порядок: сначала некритичное, потом критичное.
5. Метрики успеха: стоимость, latency, доступность.

## Cutover: переключение

Варианты:

- **big bang** — всё сразу; рискованно, но просто;
- **постепенно** — часть трафика на новое, часть на старое;
- **canary** — 1–5 % пользователей;
- **parallel run** — оба контура работают, сравниваем результаты.

Для данных:

1. Остановить запись (или включить read-only).
2. Синхронизировать изменения (CDC, логическая репликация).
3. Переключить приложение.
4. Проверить целостность.
5. Оставить старое доступным для отката на N дней.

## Откат

Cutover без плана отката не начинают. Проверьте:

- DNS TTL снижен заранее (за сутки);
- старая система в рабочем состоянии;
- есть способ вернуть данные, записанные в новую;
- ответственные и время решения об откате.

## Disaster recovery

| Модель | RTO | RPO | Стоимость |
| --- | --- | --- | --- |
| Backup & restore | часы | часы | низкая |
| Pilot light | десятки минут | минуты | средняя |
| Warm standby | минуты | секунды | высокая |
| Active-active | секунды | ~0 | очень высокая |

RTO — время восстановления, RPO — допустимая потеря данных. Выбирайте по
бизнес-требованиям, а не «по максимуму».

Проверка DR — учения, а не документ. Раз в квартал поднимайте стенд из бэкапа и
фиксируйте фактический RTO.

## Типичные ошибки

- недооценённые зависимости (лицензии, DNS, IP allowlist);
- забытые cron и интеграции;
- секреты в конфигах, которые «перенесутся»;
- отсутствие мониторинга на новом контуре;
- миграция без baseline производительности;
- отключение старого контура сразу после cutover.

## Как выбрать стратегию под сервис

Стратегия зависит от двух вещей: насколько сервис критичен и сколько у команды
времени. Полезная матрица:

| Ситуация | Стратегия | Риск |
| --- | --- | --- |
| монолит, сроки горят | rehost | низкий сразу, высокий потом |
| есть немного времени | replatform | средний |
| новый сервис | refactor | средний, но нет долга |
| ПО не нужно | retire | нет |
| куплено у вендора | repurchase | зависимость от вендора |

Частая ошибка — обещать refactor везде. Миграция «как есть» быстрее, но
переносит старые проблемы в новую среду; refactor дороже, но убирает долг.

## Миграция данных без простоя

1. Включить репликацию из старой БД в новую.
2. Проверить отставание и целостность.
3. Переключить чтение, затем запись.
4. Оставить обратную репликацию на время отката.
5. Выключить старую БД только после периода наблюдения.

Откат должен быть возможен минимум неделю. «Мы удалили старую базу» — самая
дорогая фраза в миграции.

## Подробный разбор темы

Стратегия миграции выбирается по срокам и цене изменений: rehost переносит почти без изменений, replatform адаптирует часть компонентов, refactor меняет архитектуру; retire и retain тоже валидные решения для отдельных систем. Перед волной миграции зафиксируйте зависимости, владельца, data classification, RTO/RPO и критерий приёмки.

Cutover — управляемое переключение источника трафика или данных. Определите freeze window, проверку целостности, мониторинг и условие отката; синхронизация данных может сделать откат сложнее, чем простое переключение DNS. Проведите репетицию на тестовой волне, проверьте backups и доступы, затем сравните функциональные и финансовые метрики до/после.

## Пошаговый сценарий

![Порядок действий: Миграция в облако: стратегии, cutover, DR](assets/img/howto/09-cloud--06-migration.svg)

1. Составьте карту зависимостей, владельцев, данных и требований к доступности.
2. Выберите стратегию миграции для каждого компонента и задайте критерии готовности.
3. Проверьте копирование, сверку данных и переключение трафика в репетиции.
4. Сохраните проверяемый rollback до подтверждения целевого сервиса.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Составьте таблицу приложений, баз, владельцев и связей; отдельно отметьте данные, которые нельзя потерять.

**Как проверить.** Каждый критичный компонент имеет владельца и известные зависимости.

### Шаг 2

**Что сделать.** Для каждого компонента выберите перенос, замену или переписывание и задайте критерий готовности.

**Как проверить.** Решение принято по компоненту и согласовано с владельцем; миграция не сводится к одной большой дате.

### Шаг 3

**Что сделать.** Повторите копирование и переключение на тестовой копии данных; сверяйте количество и контрольные суммы.

**Как проверить.** Данные совпадают до и после пробного переключения, измерено необходимое время.

### Шаг 4

**Что сделать.** Сохраните старый путь до проверки нового и заранее запишите условие rollback.

**Как проверить.** При ошибке можно вернуть трафик на прежний сервис, не теряя новые записи.
