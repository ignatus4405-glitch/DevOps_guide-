# Финальный проект: сквозной контур end-to-end

Цель проекта: **пройти весь путь изменения** — от кода до эксплуатации — и уметь
защитить каждое решение. Это то, что показывают на собеседовании вместо списка курсов.

## Задание

Соберите небольшой сервис (API со списком задач, сокращатель ссылок, каталог чего-либо)
и проведите его через все этапы:

| Этап | Что должно быть | Как проверяется |
| --- | --- | --- |
| Код | приложение + тесты + /health и /ready | `pytest`, `docker run` |
| Контейнер | Dockerfile (multi-stage, non-root, healthcheck) | `trivy image`, `docker run --read-only` |
| CI | workflow: линтер, тесты, сборка образа, security-скан | зелёные статусы в PR |
| CD | деплой в staging и prod (approval), стратегия выката | `kubectl rollout status`, откат одной командой |
| Kubernetes | Deployment, Service, Ingress, ConfigMap, Secret, probes, HPA, PDB | `kubectl get all`, HPA меняет реплики |
| IaC | Terraform для инфраструктуры, Ansible для настройки узлов | `terraform plan` чистый, плейбуки идемпотентны |
| Облако | VPC, приватные подсети, LB, домен, TLS | приложение доступно по HTTPS |
| Наблюдаемость | метрики, дашборд, 2–3 алерта, SLI/SLO | алерт срабатывает при искусственном сбое |
| Безопасность | секреты в менеджере, сканеры в CI, RBAC минимум | отчёты в Security tab |
| Документация | README, runbook, постмортем учебного инцидента | понятно человеку «с улицы» |

## Структура репозитория (рекомендация)

```text
.
├── app/                      # код приложения
│   ├── __init__.py
│   ├── main.py               # /health, /ready, /metrics, бизнес-логика
│   └── tests/
├── Dockerfile
├── compose.yaml              # локальная разработка
├── .github/workflows/
│   ├── ci.yml                # тесты, линтеры, security
│   ├── build.yml             # сборка и публикация образа
│   ├── release.yml           # релиз по тегу (артефакты + SBOM + подпись)
│   └── terraform.yml         # plan/apply инфраструктуры
├── infra/terraform/          # сеть, кластер, БД
├── infra/ansible/            # роли настройки узлов
├── k8s/                      # манифесты (или helm-чарт)
│   ├── base/
│   └── overlays/{staging,prod}/
├── monitoring/               # prometheus.yml, alerts.yml, дашборды json
├── docs/
│   ├── architecture.md       # схема и решения (ADR)
│   ├── runbooks/api-5xx.md
│   └── postmortems/2025-01-31-5xx.md
└── README.md                 # что это, как запустить, как деплоить
```

## README, который «продаёт» проект

```markdown
# Task API — демонстрационный сервис с полным DevOps-контуром

## Что внутри
Приложение на FastAPI + CI/CD (GitHub Actions) + Kubernetes (EKS/minikube) +
Terraform + Prometheus/Grafana. Деплой — rolling update, откат одной командой.

## Как запустить локально
docker compose up -d && curl localhost:8000/health

## Как деплоится
push в main → тесты и сборка образа → деплой в staging → approval → prod (canary 10 %).
Полное описание — docs/deployment.md.

## Наблюдаемость
SLI: доля успешных запросов. SLO: 99,9 %/30 дней. Дашборд: grafana/d/task-api.
Алерты: HighErrorRate (5xx > 2 % за 10 мин), HighLatency (p95 > 500 мс).

## Разбор инцидента
docs/postmortems/2025-01-31-5xx.md — рост ошибок после миграции, как нашли и что изменили.
```

## Архитектурные решения (ADR) — коротко и по делу

```markdown
# ADR-0003: Rolling update вместо blue/green

## Контекст
Один сервис, нагрузка 200 RPS, бюджет ограничен.

## Решение
Используем RollingUpdate с maxUnavailable: 0 и readinessProbe.
Blue/green отклонён: требует удвоенных ресурсов, преимущество (мгновенный откат)
достигается через rollout undo и канареечный шаг по флагу.

## Последствия
+ нет простоя, ресурсы экономятся
− короткий период смешанных версий (совместимость API обязательна)
```

Такие записи показывают, что вы умеете объяснять решения, а не только выполнять команды.

## Учебный инцидент: обязательная часть проекта

1. Сломайте прод контролируемо: уберите индекс в БД, установите лимит памяти ниже нужного или сломайте зависимость.
2. Зафиксируйте **таймлайн в UTC**: когда заметили (алерт), когда начали митигацию, когда восстановили.
3. Посчитайте MTTD и MTTR.
4. Напишите постмортем и закройте 2–3 action items реальными изменениями (тест, алерт, правка документации).

Это самый ценный артефакт портфолио: он показывает, что вы понимаете эксплуатацию, а не только «умею в Docker».

## Чек-лист готовности проекта

- [ ] Приложение отвечает на `/health`, `/ready`, `/metrics`
- [ ] Образ: multi-stage, non-root, healthcheck, отсканирован
- [ ] CI: тесты, линтер, security-скан, публикация образа по digest
- [ ] CD: staging авто, prod с approval, откат документирован и проверен
- [ ] Kubernetes: манифесты в Git, HPA и PDB настроены
- [ ] IaC: Terraform для инфраструктуры, Ansible для узлов, всё из пайплайна
- [ ] Мониторинг: дашборд, алерты, SLO зафиксирован
- [ ] Секреты вне Git, RBAC по минимуму, сканеры включены
- [ ] README, runbook, ADR, постмортем
- [ ] Релиз v1.0.0 с артефактами и SBOM

## Критерии готовности проекта

Проект считается завершённым, когда выполнены все пункты:

- [ ] приложение поднимается одной командой из чистого клона;
- [ ] CI зелёный на каждом PR;
- [ ] образ собирается по SHA и публикуется;
- [ ] деплой в staging автоматический, в prod — с approval;
- [ ] есть откат, проверенный хотя бы один раз;
- [ ] инфраструктура описана Terraform;
- [ ] настроены метрики, логи и один алерт;
- [ ] README объясняет запуск и решения;
- [ ] есть разбор одного инцидента.

Пустые чекбоксы — это не провал, а список следующих шагов.

## Как оформить результат

1. **Схема архитектуры** — один рисунок, без деталей.
2. **Ссылки** на пайплайн, дашборд (скриншот), образ.
3. **Метрики до/после** — время CI, latency, стоимость.
4. **Раздел «ограничения»** — что сознательно не сделано.

Работа без ограничений выглядит подозрительно: в реальности всегда есть
компромиссы.

## Короткое резюме

- Финальный проект проходит весь путь: код → CI → образ → кластер → IaC → мониторинг.
- Портфолио ценно объяснениями решений (ADR) и разбором инцидента, а не скриншотами.
- README и документация делают проект понятным ревьюеру за 5 минут.
- Чек-лист помогает не забыть критичные пункты прод-готовности.

## Как оценивать проект

Оценка «сделаю за месяц» почти всегда оптимистична. Работающая практика —
декомпозиция и явные допущения:

1. разбейте на шаги по 1–2 дня;
2. для каждого шага укажите результат и зависимость;
3. добавьте буфер 30–50 % на неизвестное;
4. отметьте, что можно вырезать без потери смысла.

Оценка — это диапазон, а не точка. «3–5 дней» честнее, чем «4 дня».

### MVP портфолио

Минимальный жизнеспособный проект:

- приложение и БД;
- Dockerfile и compose;
- CI с тестами;
- деплой в кластер;
- метрики и один алерт;
- README.

Всё остальное — расширения. Сначала доведите MVP до конца, потом добавляйте
Terraform, canary, трейсинг.

### Как выбрать тему

Тема должна:

- быть понятной вам без туториала;
- иметь измеримый результат;
- допускать улучшения;
- не требовать платных ресурсов.

Хороший пример: сервис коротких ссылок, заметки, каталог, трекер задач.
Плохой: «сделаю свой Kubernetes».

### Документирование решений

Ведите `docs/adr/` и `README` с разделами «архитектура», «запуск», «решения»,
«ограничения». Это не бюрократия: именно это читает интервьюер.

### Презентация

3 минуты: проблема → архитектура → что сделали → результат → что улучшили бы.
Схема и цифры сильнее списка технологий.

## Подробный разбор темы

Разбейте capstone на проверяемые этапы: приложение запускается локально, unit tests проходят, CI собирает неизменяемый image, IaC описывает окружение, deploy имеет health checks, а dashboard показывает пользовательский сигнал. На каждом этапе храните артефакт и критерий приёмки. Это облегчает локализацию дефекта и даёт интервьюеру доказательство, что проект не ограничивается красивой схемой.

Подготовьте failure drill: неверная конфигурация, недоступная зависимость или неудачный rollout. Покажите, как обнаружили проблему, приняли решение об откате и проверили восстановление. Финальный README должен содержать архитектуру, команды запуска, ограничения, threat model и стоимость. Не выкладывайте реальные секреты или публичный cloud endpoint без лимитов и плана удаления.
