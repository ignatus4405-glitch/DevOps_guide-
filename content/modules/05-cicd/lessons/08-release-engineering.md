# Релиз-инжиниринг: версии, changelog, артефакты

Релиз — это не «нажать кнопку», а воспроизводимый процесс: версия, артефакт,
подпись, заметки и возможность откатиться. Чем меньше ручных шагов, тем реже
ошибки.

## SemVer: когда какая версия

`MAJOR.MINOR.PATCH`

| Изменение | Версия | Пример |
| --- | --- | --- |
| несовместимое API | major | 1.4.2 → 2.0.0 |
| новая функциональность | minor | 1.4.2 → 1.5.0 |
| исправление | patch | 1.4.2 → 1.4.3 |

Для внутренних сервисов semver часто заменяют монотонным номером сборки, но
контракт API всё равно версионируют. Ломать клиентов «молча» — дороже, чем
поддерживать две версии месяц.

## Conventional Commits

```
feat(api): добавить фильтр по дате
fix(auth): не истекать сессию при обновлении
docs: описать переменные окружения
feat!: удалить v1 endpoint        # breaking change
```

Из сообщений автоматически определяется версия и генерируется changelog. Это
работает только если формат соблюдается — поэтому нужен commit-msg-хук или
squash-merge с правильным заголовком.

## Артефакты релиза

Минимальный набор:

- собранный бинарь/образ/архив;
- контрольные суммы (`SHA256SUMS`);
- подпись (cosign, GPG) для критичных случаев;
- `release notes`;
- манифест версии (для автообновления).

```bash
sha256sum app.tar.gz > SHA256SUMS
cosign sign --key cosign.key ghcr.io/org/app@sha256:...
```

Подпись позволяет потребителю проверить, что артефакт не подменён. Для внутренних
релизов достаточно контрольных сумм, для публичных — подпись.

## Immutable-артефакты

Правило: артефакт нельзя перезаписывать. Тег `1.4.2` должен указывать на один и
тот же образ навсегда.

```bash
docker pull ghcr.io/org/app:1.4.2
# всегда один digest
```

Если нужно исправить — выпускается `1.4.3`, а не перезаписывается `1.4.2`.
Перезапись ломает воспроизводимость и расследование инцидентов.

## Release notes

Хорошие заметки отвечают на три вопроса:

1. Что изменилось для пользователя.
2. Что делать при обновлении (миграции, breaking changes).
3. Как откатиться.

«Разные исправления и улучшения» — бесполезный текст. Группировка по `feat`/`fix`/
`breaking` позволяет быстро оценить риск.

## Процесс выпуска

```
merge в main → тесты → сборка артефакта → подпись → публикация →
обновление changelog → уведомление клиентов
```

Каждый шаг автоматизирован в CI. Ручными остаются только:

- подтверждение релиза (approval environment);
- проверка заметок;
- коммуникация при breaking changes.

Если в процессе больше двух ручных шагов, рано или поздно кто-то забудет один.

## Откат

Релиз без плана отката — не релиз. Варианты:

| Способ | Скорость | Когда |
| --- | --- | --- |
| rollback на предыдущий образ | секунды | всегда должен быть |
| feature flag off | секунды | новая функциональность |
| миграция вниз | минуты | если обратима |
| восстановление БД | часы | крайний случай |

Миграции должны быть обратно совместимыми: сначала добавить колонку, потом писать
в неё, потом удалить старую — а не ломать схему одним релизом.

## Подробный разбор темы

Версия связывает исходный код, артефакт и заметки о релизе. В SemVer major обозначает несовместимое изменение, minor — новую совместимую функциональность, patch — исправление; до `1.0.0` проект может трактовать совместимость иначе, это нужно явно описать. Тег релиза должен ссылаться на тот commit, из которого собран артефакт.

Сохраните checksum, сведения о платформе и точную версию toolchain, чтобы пользователь мог проверить файл и команда могла воспроизвести сборку. Changelog описывает последствия для пользователей, а не просто копирует список commit messages. Перед публикацией проверьте upgrade path, чистую установку и восстановление из предыдущей версии.

## Пошаговый сценарий

![Порядок действий: Релиз-инжиниринг: версии, changelog, артефакты](assets/img/howto/05-cicd--08-release-engineering.svg)

1. Выберите версию и проверьте правила совместимости для пользователей.
2. Создайте тег на проверенном commit и соберите артефакт из него.
3. Сохраните checksum, provenance, платформу и короткие release notes.
4. Проверьте установку, обновление и путь возврата предыдущей версии.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Определите, совместимо ли изменение для пользователя: исправление, новая функция или несовместимый переход.

**Как проверить.** Номер версии объясним, а пользователь понимает, нужно ли менять свою конфигурацию.

### Шаг 2

**Что сделать.** Создайте tag только на проверенном commit и собирайте файл именно из этого tag.

**Как проверить.** У релиза есть постоянная ссылка на исходный commit.

### Шаг 3

**Что сделать.** Сохраните checksum (контрольную сумму), список компонентов и короткое описание изменения рядом с артефактом.

**Как проверить.** Пользователь может проверить целостность файла и понять, что в нём нового.

### Шаг 4

**Что сделать.** Установите релиз в тестовую среду поверх старой версии и проверьте возврат на предыдущий артефакт.

**Как проверить.** Работает обычное обновление и понятен безопасный путь назад.

## Проверьте себя

1. Почему артефакт нельзя перезаписывать?
2. Что должно быть в release notes кроме списка изменений?
3. Какой способ отката должен быть доступен всегда?
4. Почему миграции делают в несколько шагов?
