# Секреты в CI: хранение, OIDC, ротация

CI — самое опасное место для секретов: он запускает чужой код (зависимости,
скрипты, PR из форков) и имеет доступ к продакшену. Ошибка в настройке означает
утечку.

## Где секреты живут

| Способ | Безопасность | Когда использовать |
| --- | --- | --- |
| Переменные в коде | никакой | никогда |
| GitHub Secrets | средняя | базовые случаи |
| Vault / облачный Secrets Manager | высокая | продакшен |
| OIDC + короткоживущие токены | высокая | облачные деплои |
| SOPS + KMS | средняя | GitOps-конфигурация |

GitHub Secrets шифруются и не показываются в логах, но доступны всем job'ам,
которые могут их запросить. Если workflow запускается из PR форка, секреты не
передаются — это защита, которую нельзя обходить.

## Маскирование и его пределы

GitHub маскирует точное значение секрета в логах. Но:

```bash
echo "${TOKEN:0:8}"        # первые 8 символов попадут в лог
echo "$TOKEN" | base64     # закодированное значение не маскируется
env | grep TOKEN           # может вывести целиком
```

Правило: **никогда не печатайте секреты**, даже частично, даже для отладки.

## OIDC: ключи без ключей

Вместо долгоживущего `AWS_SECRET_ACCESS_KEY` CI получает временный токен:

```yaml
permissions:
  id-token: write
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/github-deploy
      aws-region: eu-west-1
```

AWS доверяет конкретному репозиторию и ветке через trust policy:

```json
{
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:sub": "repo:org/repo:ref:refs/heads/main"
    }
  }
}
```

Преимущества: токен живёт минуты, нечего ротировать, утечка менее опасна.
Ограничение условия `sub` критично: без него любой workflow репозитория может
получить роль.

## Секреты в pull request

PR из форка не получает секреты — правильно. Но что если нужны интеграционные
тесты с базой?

- используйте `pull_request_target` **осторожно**: он даёт секреты, но запускает
  код из PR — потенциальная RCE;
- лучше — отдельный workflow по метке (`labeled`) с ревью;
- или тестовая база, доступная без секретов (локальный контейнер).

`pull_request_target` с checkout кода PR — классическая уязвимость: злоумышленник
меняет скрипт и получает секреты.

## Ротация

Секрет должен иметь срок жизни и владельца:

1. Ротация по расписанию (90 дней) или автоматически.
2. Немедленная ротация при подозрении на утечку.
3. Удаление неиспользуемых секретов.
4. Аудит доступа: кто и когда читал.

```bash
gh secret list
gh secret set NEW_TOKEN --body "$(openssl rand -hex 32)"
gh secret delete OLD_TOKEN
```

## Секреты в Docker-образе

Никогда не копируйте `.env` в образ и не пишите `ARG SECRET`. Используйте:

```dockerfile
RUN --mount=type=secret,id=npmrc npm ci
```

BuildKit-секреты не попадают в слои. Для runtime — переменные окружения из
Kubernetes Secret или файл, смонтированный томом.

## Проверка перед коммитом

```bash
gitleaks detect --source . --redact
trufflehog filesystem . --only-verified
```

Эти проверки должны быть и локально (pre-commit), и в CI. Лучше поймать ключ до
первого push: из истории публичного репозитория его удалить почти невозможно.

## Подробный разбор темы

Секрет в CI нужен только конкретному job и минимальное время. Предпочитайте короткоживущие credentials через OIDC и trust policy, привязанную к репозиторию, ветке и среде; статический cloud key сложнее ротировать и опаснее при утечке. Маскирование в логах — последняя линия защиты, а не разрешение печатать токен в stdout.

Проверьте источники утечки: shell trace, debug-логи, artifact, cache, PR из fork и неконтролируемые workflow events. Не выдавайте секреты коду, который автор недоверенного PR может изменить. Ротация должна быть проверяемым процессом: обновить credential, убедиться в успешном использовании нового, отозвать старый и проверить audit log.

## Пошаговый сценарий

![Порядок действий: Секреты в CI: хранение, OIDC, ротация](assets/img/howto/05-cicd--05-secrets-in-ci.svg)

1. Определите job, который действительно нуждается в каждом credential.
2. Настройте OIDC trust policy с ограничением репозитория и среды.
3. Исключите secrets для untrusted pull request и debug-вывода.
4. Проверьте аудит, ротацию и отзыв временного ключа.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** В каждом job спросите: нужен ли ему пароль/ключ? Уберите секреты из jobs, которые только тестируют код.

**Как проверить.** Секрет доступен только на тех шагах, где он действительно требуется.

### Шаг 2

**Что сделать.** Для облака настройте OIDC: GitHub выдаёт короткий identity token, который облако проверяет по репозиторию и среде.

**Как проверить.** Долгоживущий ключ не хранится в репозитории; другой репозиторий не может взять эту роль.

### Шаг 3

**Что сделать.** Проверьте workflow для fork PR: не выводите секреты и не запускайте privileged deployment для непроверенного кода.

**Как проверить.** Ветка из чужого fork может тестироваться без доступа к credentials.

### Шаг 4

**Что сделать.** В тестовом окружении проверьте audit log, rotation и отзыв credential; убедитесь, что старый ключ перестал работать.

**Как проверить.** Есть запись об использовании и проверенный способ быстро лишить credential доступа.
