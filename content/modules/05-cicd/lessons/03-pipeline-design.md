# Проектирование пайплайна: стадии, гейты, артефакты

Пайплайн — это не список команд, а конвейер с контрактом: что считается готовым,
что проверяется и что попадает в продакшен. Плохой пайплайн либо слишком медленный,
либо пропускает ошибки.

## Стадии и их назначение

| Стадия | Время | Что делает | Можно ли пропустить |
| --- | --- | --- | --- |
| lint | секунды | стиль, типы, статический анализ | нет |
| build | минуты | компиляция, сборка образа | нет |
| unit | минуты | быстрые тесты | нет |
| integration | минуты | БД, сети, контракты | нет для сервисов |
| e2e | десятки минут | пользовательские сценарии | только smoke |
| security | минуты | зависимости, секреты, образы | нет |
| deploy | минуты | выкат в окружение | по стратегии |

Правило: **быстрые проверки раньше медленных**. Если линтер падает за 10 секунд,
нет смысла 10 минут собирать образ.

## Артефакт: единственный источник правды

Собрали один раз — доставляем везде одно и то же.

```
build → artifact (docker image / jar / tar.gz) → staging → prod
```

Антипаттерн: пересобирать в каждом окружении. Тогда staging и prod содержат разные
бинары, и «на staging работало» ничего не доказывает.

Для Docker это означает тег по SHA коммита, а не `latest`:

```yaml
- run: docker build -t ghcr.io/org/app:${{ github.sha }} .
- run: docker push ghcr.io/org/app:${{ github.sha }}
```

`latest` — плавающий тег, он не позволяет понять, что именно запущено. Тег по SHA
однозначен и позволяет откатиться на конкретную версию.

## Гейты: где останавливаться

Гейт — обязательное условие перехода. Типичные:

- покрытие не упало ниже порога;
- нет критических уязвимостей;
- обязательное ревью;
- ручное подтверждение для prod;
- успешный smoke-тест после деплоя.

Гейт должен быть **автоматическим и однозначным**. «Посмотреть глазами» — не гейт,
а надежда.

## Кэш и параллелизм

Пайплайн из 30 минут легко сократить до 8:

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements*.txt') }}
```

Кэшируют: зависимости, слои Docker, результаты компиляции, тестовые данные.
Ключ должен зависеть от lock-файла, иначе кэш будет устаревшим.

Независимые job'ы запускают параллельно (`needs` задаёт только зависимости).
Матрица версий — тоже форма параллелизма.

## Идемпотентность и повторяемость

Пайплайн должен давать одинаковый результат при повторном запуске:

- фиксированные версии инструментов (`actions/checkout@v4`, а не `@main`);
- зафиксированные образы (`python:3.12-slim`, а не `python:latest`);
- отсутствие зависимости от локального состояния раннера;
- явные переменные окружения;
- детерминированная сборка (одинаковые входы → одинаковый артефакт).

Проверка: запустите пайплайн дважды подряд. Если результаты различаются — есть
скрытое состояние.

## Структура workflow

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ruff && ruff check .
  test:
    runs-on: ubuntu-latest
    needs: lint
    strategy:
      matrix:
        python: ["3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - run: pip install -r requirements-dev.txt
      - run: pytest -q
```

`concurrency` отменяет устаревшие запуски при новом push в ту же ветку — экономит
минуты и ускоряет обратную связь.

## Секреты и окружения

- секреты — только через хранилище CI (`secrets.*`), не в коде;
- для prod — отдельная среда с обязательным ревью (`environment: production`);
- OIDC вместо долгоживущих ключей облака;
- доступ к секретам не наследуется в PR из форков.

## Метрики пайплайна

| Метрика | Цель |
| --- | --- |
| Время до первого результата | < 5 минут |
| Общее время CI | < 15 минут |
| Доля падений из-за flaky-тестов | < 2 % |
| Время ожидания раннера | < 1 минуты |
| Частота перезапусков | низкая |

Если разработчики перезапускают пайплайн «на удачу», проблема в тестах или
инфраструктуре, а не в людях.

## Чек-лист ревью пайплайна

Перед тем как считать пайплайн готовым:

- [ ] каждый шаг имеет понятное имя и таймаут;
- [ ] секреты не печатаются и не попадают в артефакты;
- [ ] сборка воспроизводима из чистого клона;
- [ ] кэш не влияет на корректность;
- [ ] артефакт имеет неизменяемый идентификатор (SHA/digest);
- [ ] деплой можно откатить одной командой;
- [ ] прод требует подтверждения;
- [ ] упавший шаг останавливает выкатку;
- [ ] логи содержат достаточно контекста без секретов.

## Стоимость пайплайна

Пайплайн — тоже система, у него есть цена:

- минуты раннеров;
- время разработчика в ожидании;
- шумные падения, которые приучают игнорировать красное.

Быстрый фидбек важнее полного покрытия: сначала линтер и unit-тесты (2–3
минуты), затем интеграционные, затем сборка и деплой. Если первый шаг идёт
10 минут, разработчик уходит пить кофе и возвращается к другой задаче.

## Проверьте себя

1. Почему артефакт собирают один раз, а не в каждом окружении?
2. Чем гейт отличается от рекомендации?
3. Что делает `concurrency` и зачем отменять устаревшие запуски?
4. Как проверить, что пайплайн идемпотентен?
