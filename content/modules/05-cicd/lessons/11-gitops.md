# GitOps: Git как источник истины

GitOps — операционная модель, где желаемое состояние кластера хранится в Git,
а агент в кластере приводит реальность к этому состоянию.

## Принципы

1. **Декларативность** — описано состояние, а не шаги.
2. **Версионирование** — каждое изменение в Git.
3. **Автоматическое применение** — агент синхронизирует.
4. **Непрерывное согласование** — дрейф исправляется.

Инженер не делает `kubectl apply` в прод. Он меняет Git, проходит ревью, и
агент применяет.

## Argo CD и Flux

**Argo CD** — UI, приложения, sync waves, health. **Flux** — набор контроллеров,
ближе к «Unix way».

Типовой поток:

```text
app repo → CI (build image, update tag) → manifests repo → Argo CD → cluster
```

Разделение репозиториев даёт независимый аудит и откат.

## Sync и drift

Агент сравнивает Git и кластер. Расхождение — drift. Политика:

- auto-sync с self-heal;
- ручной sync для прода;
- prune — удалять объекты, исчезнувшие из Git.

`prune` опасен: ошибка в манифесте удалит ресурсы. Начните без prune, включите
осознанно.

## Секреты

Секреты не хранят в Git в открытом виде. Варианты:

- Sealed Secrets (шифртекст в Git);
- SOPS + KMS;
- External Secrets Operator (ссылка на vault);
- Secrets Store CSI.

Выбор зависит от того, где живёт источник истины.

## Промоушен окружений

Два подхода:

- **отдельные ветки/папки** на среду;
- **kustomize overlays** с разными values.

Первый проще аудировать, второй — меньше дублирования. В обоих случаях
изменение идёт через PR.

## Ограничения

- GitOps не заменяет CI: сборка и тесты остаются;
- состояние БД не управляется Git;
- секреты требуют отдельного механизма;
- при потере связи с Git кластер живёт по последнему состоянию.

## Подробный разбор темы

GitOps-разделяет желаемое состояние в Git и фактическое состояние кластера. Контроллер периодически сравнивает их и reconciliation loop приводит систему к декларативному описанию. Это удобно для аудита и восстановления, но требует ясного источника истины: ручные изменения в кластере будут возвращены контроллером, если их не зафиксировали в репозитории.

Разделите права на изменение manifest и на чтение runtime-секретов; не помещайте открытые секреты в Git. Для безопасного rollout используйте review, policy checks и продвижение версии между окружениями. Drift сигнализирует о неучтённом изменении, но автоматическое исправление может быть рискованным при инциденте — определите процедуру временного исключения и его возврата в Git.
