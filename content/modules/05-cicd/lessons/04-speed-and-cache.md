# Скорость пайплайна: кэш, параллелизм, инкрементальность

Медленный CI — скрытый налог: разработчик ждёт, переключается на другую задачу и
теряет контекст. Команда из 10 человек при 20 минутах ожидания в день теряет
больше трёх человеко-часов ежедневно.

## Где уходит время

Сначала измерьте, потом оптимизируйте. В GitHub Actions время каждого шага видно
в логе и в summary. Типичное распределение:

| Этап | Доля | Что делать |
| --- | --- | --- |
| установка зависимостей | 30–50 % | кэш |
| сборка | 20–30 % | инкрементальная сборка, кэш слоёв |
| тесты | 20–40 % | параллелизм, разбиение |
| ожидание раннера | 5–20 % | self-hosted или больший раннер |
| публикация артефакта | 5–10 % | сжатие, только нужные файлы |

## Кэш зависимостей

```yaml
- uses: actions/cache@v4
  with:
    path: |
      ~/.cache/pip
      ~/.npm
    key: ${{ runner.os }}-deps-${{ hashFiles('**/requirements*.txt', '**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-deps-
```

Правила:

- ключ зависит от lock-файла — при изменении зависимостей кэш пересоздаётся;
- `restore-keys` даёт частичное попадание (частый кэш, но чуть устаревший);
- не кэшируйте секреты и большие бинарники;
- проверяйте размер: кэш > 2 ГБ замедляет восстановление.

## Кэш Docker-слоёв

```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

Порядок важен: слой с зависимостями переиспользуется, пока не изменился
`requirements.txt`. Если скопировать весь проект до установки, кэш инвалидируется
на каждом коммите.

В CI:

```yaml
- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v6
  with:
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

## Параллелизм

Независимые проверки запускаются одновременно:

```yaml
jobs:
  lint: ...
  unit: ...
  security: ...
  build:
    needs: [lint, unit, security]
```

Разбиение тестов на шарды:

```yaml
strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: pytest --splits 4 --group ${{ matrix.shard }}
```

`pytest-split` делит тесты по времени выполнения, а не по количеству — это важно:
иначе один шард с медленными тестами определяет общее время.

## Инкрементальные проверки

- запускать тесты только для изменённых пакетов (monorepo);
- использовать `--since`/`--affected` (Nx, Turborepo, Bazel);
- пропускать сборку документации, если не менялись docs;
- использовать `paths`/`paths-ignore` в триггерах.

```yaml
on:
  push:
    paths-ignore:
      - 'docs/**'
      - '**.md'
```

Осторожно: пропуск проверок может нарушить branch protection (обязательный статус
не появится). Решение — job, который всегда зелёный, если изменения не касаются кода.

## Ожидание раннера

Бесплатные раннеры GitHub могут ждать в очереди в часы пик. Варианты:

- self-hosted раннеры (нужна безопасность: не запускать непроверенный код);
- большие раннеры (платно);
- уменьшение количества job'ов;
- расписание тяжёлых проверок (ночные прогоны).

## Что не стоит оптимизировать

- **Тесты в ущерб покрытию.** Быстрый CI, пропускающий баги, дороже медленного.
- **Кэш секретов.** Экономия секунд ценой утечки.
- **Отключение security-сканов.** Уязвимость в проде дороже минуты CI.
- **`--no-verify` и force-push.** Скорость, которая ломает доверие к main.

## Измерение результата

До оптимизации зафиксируйте:

- медиану времени CI за две недели;
- p95 (хвост важнее среднего);
- долю перезапусков;
- время до первого результата.

После изменения сравните. «Кажется, стало быстрее» — не аргумент для изменения
процесса.

## Подробный разбор темы

Сначала измерьте, куда уходит время: очередь runner, checkout, установка зависимостей, сборка, тесты или публикация. Параллелизм помогает только независимым задачам; общая база тестов или ограниченный runner могут превратить его в конкуренцию за ресурс. Кэшируйте только повторно используемые и воспроизводимые данные, а ключ кэша связывайте с lock-файлом и платформой.

Кэш — оптимизация, не источник истины. Pipeline должен оставаться корректным при пустом или недоступном кэше; периодически проверяйте cold build. Для монорепозитория используйте граф зависимостей или точные path filters, иначе инкрементальность пропустит нужную проверку. Сравнивайте p50 и p95 времени job, чтобы редкий медленный runner не скрывался за средним.

## Пошаговый сценарий

1. Измерьте очередь runner, checkout, install, tests и build отдельно.
2. Параллелите только независимые стадии и ограничьте конкуренцию за ресурсы.
3. Привяжите cache key к lock-файлам и платформе.
4. Проверьте чистую сборку без cache и сравните p95 времени.
