# Как устроен контейнер: namespaces, cgroups, overlayfs

Контейнер — не «лёгкая виртуальная машина». Это обычный процесс Linux,
которому ядро показывает изолированное представление системы. Понимание
механизмов объясняет и ограничения, и странности вроде «в контейнере 64 ГБ
памяти, хотя лимит 512 МБ».

## Namespaces: что видно

| Namespace | Изолирует |
| --- | --- |
| PID | процессы и их номера |
| NET | интерфейсы, порты, маршруты |
| MNT | точки монтирования |
| UTS | hostname |
| IPC | очереди сообщений, shared memory |
| USER | uid/gid внутри и снаружи |
| CGROUP | дерево cgroup |

Процесс в контейнере может быть PID 1 внутри, но на хосте иметь обычный номер.
`docker exec` попадает в те же namespaces, поэтому «видит» процессы контейнера.

## Cgroups: сколько можно

cgroups ограничивают и учитывают ресурсы: CPU, память, blkio, pids.

```bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/cpu.max
```

В cgroup v2 единая иерархия. Лимит памяти — жёсткий потолок: превышение
приводит к OOM внутри cgroup, а не на хосте.

Важно: `free` внутри контейнера показывает память хоста (в зависимости от
реализации), а лимит — в cgroup. Приложения должны читать cgroup или
поддерживать автоопределение (JVM, Go).

## Overlayfs: слои

Образ состоит из слоёв. Контейнер добавляет тонкий writable-слой сверху:

```text
[rw container layer]
[app layer]
[base layer]
```

Чтение идёт сверху вниз, запись — copy-up: файл копируется в верхний слой.
Поэтому:

- слои образа неизменяемы и разделяются между контейнерами;
- запись в контейнер дороже чтения;
- данные, которые должны жить, выносят в volume.

## Изоляция не равна безопасности

Общее ядро — общая поверхность атаки. Контейнер с `--privileged` почти не
изолирован. Дополнительные барьеры:

- seccomp — фильтр системных вызовов;
- capabilities — урезание прав root;
- AppArmor/SELinux — мандатный доступ;
- user namespaces — root внутри не root снаружи;
- rootless-контейнеры.

## Что такое образ по спецификации

OCI image = манифест + конфигурация + слои (tar+diff). Registry хранит их по
digest. Тег — изменяемая ссылка, digest — неизменяемая.

```bash
docker image inspect app:1.0 --format '{{.RepoDigests}}'
```

Деплой по digest даёт воспроизводимость; по тегу — риск, что «1.0» уже другая.

## Почему контейнер «не запускается»

- entrypoint завершился — контейнер остановился (это не сервис);
- PID 1 не обрабатывает SIGTERM — остановка по таймауту;
- нет динамических библиотек в scratch-образе;
- архитектура образа не совпадает с хостом (`exec format error`);
- права на файл потеряны при копировании.

## Подробный разбор темы

Namespaces изолируют видимость процессов, сети и точек монтирования; cgroups ограничивают ресурсы; overlayfs объединяет слои образа и writable layer. Эта комбинация создаёт ощущение отдельной машины, но процессы всё равно делят ядро хоста. Поэтому уязвимость ядра и слишком широкие права runtime остаются риском общей среды.

При разборе поведения проверьте конкретную границу: namespace процесса, сетевой namespace, монтирования и значения cgroup. Если контейнер видит файл или порт неожиданно, ищите bind mount, shared namespace или capability, а не только Dockerfile. Снимайте диагностику с хоста и контейнера, но помните, что root внутри контейнера не обязан быть root на host при user namespace.
