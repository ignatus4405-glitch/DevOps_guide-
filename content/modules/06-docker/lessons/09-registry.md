# Registry: хранение, теги и жизненный цикл образов

Registry — не «папка с образами». Это распределённая система с манифестами,
слоями, кэшем и политиками. Ошибки здесь приводят к «образ не найден» в проде
и к счетам за хранение.

## Что хранится

- **manifest** — ссылки на слои и конфигурацию;
- **config** — метаданные (env, entrypoint, history);
- **layers** — tar-архивы с diff;
- **tags** — изменяемые указатели на digest.

Digest вычисляется по содержимому. Один и тот же слой в разных образах
хранится один раз (content-addressable storage).

```bash
docker manifest inspect ghcr.io/org/app:1.0
crane digest ghcr.io/org/app:1.0
```

## Теги и digest

Тег — удобство, digest — гарантия. В проде:

```yaml
image: ghcr.io/org/app@sha256:...
```

Тег `latest` не должен использоваться в деплое: он меняется без изменения
манифеста.

## Мультиархитектурные образы

Manifest list указывает на образы для amd64/arm64. `docker buildx build
--platform linux/amd64,linux/arm64 --push` создаёт индекс. Без него на Apple
Silicon или ARM-серверах образ не запустится.

## Кэш и прокси

Registry может быть прокси-кэшем (Harbor, Nexus, registry:2 pull-through).
Это ускоряет сборку и снижает зависимость от внешнего registry.

В CI используйте `--cache-from` и registry cache, но помните: кэш не должен
влиять на корректность.

## Жизненный цикл

- retention policy по тегам (оставлять N последних);
- удаление untagged-манифестов;
- garbage collection слоёв;
- подпись и сканирование при push.

Без политики registry растёт до терабайтов.

## Безопасность

- приватный registry для внутренних образов;
- RBAC на push/pull;
- сканирование при загрузке;
- immutable tags для релизов;
- проверка подписи в admission.

## Отладка

`ImagePullBackOff` — причины:

1. нет образа/тега;
2. нет прав (imagePullSecrets);
3. сеть/DNS до registry;
4. лимит на размер/квоту;
5. несовпадение архитектуры.

`kubectl describe pod` покажет точную ошибку.

## Как проверить себя

1. Чем тег отличается от digest?
2. Зачем manifest list?
3. Что даёт pull-through cache?
4. Какие политики жизненного цикла нужны?
5. Почему ImagePullBackOff нельзя чинить перезапуском?

!!! tip "Практика"
    Задача «Политика registry» в практикуме: настроить retention.

## Подробный разбор темы

Registry хранит слои и манифесты, а тег — изменяемая ссылка на манифест. Digest идентифицирует содержимое; его удобно использовать для точного продвижения одного образа между dev, staging и production. Перед deploy проверьте, что артефакт подписан доверенным ключом, соответствует ожидаемой архитектуре и связан с источником сборки.

Политика retention должна сохранять все образы, на которые ссылаются действующие workloads и rollback-процедуры. Агрессивная очистка registry может удалить единственную версию для восстановления; отсутствие очистки увеличивает стоимость и шум. Ограничьте pull/push credentials, включите аудит и не используйте широкие robot tokens для локального эксперимента.

## Пошаговый сценарий

![Порядок действий: Registry: хранение, теги и жизненный цикл образов](assets/img/howto/06-docker--09-registry.svg)

1. Соберите образ с фиксированной версией и присвойте digest.
2. Опубликуйте его с ограниченным robot credential.
3. Проверьте подпись и provenance перед pull в целевой среде.
4. Настройте retention так, чтобы текущий и rollback-образы не удалялись.

## Пошаговое объяснение для новичка

Сначала выполните упражнение в учебной среде или на примере из урока. Если действие меняет реальные файлы, сервер или облако, сначала проверьте цель и подготовьте откат. После каждого шага сравните результат с проверкой ниже; при неожиданном результате остановитесь.

### Шаг 1

**Что сделать.** Соберите образ с tag версии и запишите его digest; tag — имя, digest — точное содержимое.

**Как проверить.** Есть постоянный идентификатор, по которому можно загрузить именно проверенный образ.

### Шаг 2

**Что сделать.** Войдите в registry с ограниченным robot account; передавайте пароль через stdin или secret manager, не аргументом команды.

**Как проверить.** Пароль не попал в историю shell и учётная запись может только выполнять нужные действия.

### Шаг 3

**Что сделать.** Перед запуском загрузите образ по digest и проверьте подпись/provenance.

**Как проверить.** Подпись соответствует точному digest, а источник образа ожидаемый.

### Шаг 4

**Что сделать.** Настройте retention и убедитесь, что текущий и предыдущий релизы не удаляются автоматически.

**Как проверить.** Для rollback есть доступный образ; устаревший мусор можно чистить по прозрачному правилу.
