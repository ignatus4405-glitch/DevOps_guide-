# Сети Docker: bridge, host, overlay

Контейнеры изолированы, но должны общаться: с другими контейнерами, с хостом и с
внешним миром. Понимание драйверов сети объясняет, почему «контейнер не видит
базу».

## Драйверы

| Драйвер | Назначение | Особенность |
| --- | --- | --- |
| bridge | сеть по умолчанию на одном хосте | NAT, свои IP |
| host | контейнер использует сеть хоста | нет изоляции, порты напрямую |
| overlay | сеть между хостами Swarm | VXLAN-инкапсуляция |
| macvlan | контейнер в физической сети | свой MAC-адрес |
| none | без сети | максимальная изоляция |

По умолчанию Docker создаёт bridge `docker0` и сеть `bridge`. Контейнеры в ней
получают адреса из `172.17.0.0/16`.

## Встроенный DNS

В пользовательской сети (не default bridge) Docker предоставляет DNS по имени
контейнера или сервиса:

```bash
docker network create app-net
docker run -d --name db --network app-net postgres:16
docker run --rm --network app-net postgres:16 psql -h db -U postgres
```

`-h db` работает, потому что Docker DNS резолвит имя контейнера. В сети `bridge`
по умолчанию такой резолвинг недоступен — нужно `--link` (устаревший) или
пользовательская сеть.

## Порты: -p и -P

```bash
docker run -p 8080:80 nginx        # хост:контейнер
docker run -p 127.0.0.1:8080:80 nginx  # только локально
docker run -P nginx                # случайные порты
docker port <container>
```

Публикация порта создаёт правило iptables и обходит `ufw` — это частая причина
«зачем у меня открыт порт». Если нужен доступ только локально, указывайте
`127.0.0.1:` явно.

## Как контейнер ходит наружу

Исходящий трафик проходит через NAT-маскарадинг хоста. Внутри контейнера виден
адрес `172.x.x.x`, а внешний сервис видит IP хоста. Отсюда:

- логи внешнего сервиса показывают IP хоста, а не контейнера;
- rate limit срабатывает на весь хост;
- `X-Forwarded-For` нужно настраивать на прокси.

## Проверка сети

```bash
docker network ls
docker network inspect app-net
docker exec -it app sh -c 'ip addr; ip route; cat /etc/resolv.conf'
docker exec app getent hosts db
```

Типичные проблемы:

| Симптом | Причина |
| --- | --- |
| `could not translate host name "db"` | контейнеры в разных сетях |
| `connection refused` | сервис слушает 127.0.0.1 внутри контейнера |
| `connection timeout` | неверная сеть/фаервол |
| порт занят на хосте | конфликт `-p` |

## Compose и сети

```yaml
services:
  app:
    build: .
    networks: [app-net]
    ports: ["8080:8080"]
  db:
    image: postgres:16
    networks: [app-net]

networks:
  app-net:
```

Compose создаёт сеть с именем проекта и подключает к ней все сервисы. Имя хоста
для подключения — имя сервиса (`db`), а не `localhost`: внутри контейнера
`localhost` — это он сам.

## host и none: когда нужны

`--network host` убирает сетевую изоляцию: контейнер видит все интерфейсы хоста.
Полезно для сетевых утилит и высокопроизводительных сервисов, опасно для
многопользовательских сред.

`--network none` — изоляция: только loopback. Используется для задач, которым сеть
не нужна (обработка файлов, шифрование).

## Как контейнер находит другой контейнер

В пользовательской сети Docker работает встроенный DNS на 127.0.0.11. Имя
сервиса из Compose резолвится в IP контейнера, поэтому `db:5432` работает без
`links` и `/etc/hosts`.

Проверка изнутри:

```bash
docker compose exec api getent hosts db
docker compose exec api nslookup db
```

Если имя не резолвится, причины обычно такие:

1. сервисы в разных сетях;
2. контейнер запущен с `network_mode: host`;
3. используется `container_name` вместо имени сервиса;
4. сеть создана вручную и сервис к ней не подключён.

Важно: DNS Docker не виден с хоста. С хоста обращайтесь через опубликованный
порт (`localhost:8080`), а из контейнера — по имени сервиса и внутреннему
порту.
