# Версии, релизы и автообновление

## Принцип

Никаких ручных сборок: **push в `main` → версия → сборка → релиз → уведомление клиентов**.
Всё делает `.github/workflows/build.yml`.

## Как определяется версия

Источник правды — файл `VERSION` в корне.

1. Если тега `v<VERSION>` ещё нет — выпускается текущая версия как есть.
2. Если тег есть — версия поднимается по истории коммитов с прошлого тега:
   - `BREAKING CHANGE` или `!: ` → **major**
   - `feat:` → **minor**
   - остальные (`fix:`, `docs:`, `chore:`, `ci:`) → **patch**
3. Ручной запуск позволяет выбрать `none/patch/minor/major/auto`.

Решения принимает `tools/next_version.py` (покрыт тестами `tests/test_release_tools.py`),
а `tools/generate_version.py` обновляет `src/devops_academy/version.py`
(`APP_VERSION`, `BUILD_NUMBER`, `BUILD_DATE`) и `content/content_index.json` (хеши контента).

Описание релиза и запись в историю изменений тоже формируются автоматически:
`tools/release_notes.py` группирует коммиты (`feat` → «Добавлено», `fix` → «Исправлено»,
`docs` → «Документация», `chore/ci/build/test` → «Инфраструктура и тесты»,
`BREAKING CHANGE`/`!:` → «Ломающие изменения») и вставляет новую версию в `CHANGELOG.md`.
Merge-коммиты и служебные `chore(release): … [skip ci]` в описание не попадают.
Если в `CHANGELOG.md` есть раздел `## [Не выпущено]`, он заменяется записью релиза
(содержание не дублируется).

## Что попадает в релиз

| Файл | Назначение |
| --- | --- |
| `DevOpsAcademy-Setup-<версия>.exe` | установщик Windows (Inno Setup, поддержка тихой установки) |
| `DevOpsAcademy-<версия>-windows-x64.zip` | портативная сборка |
| `DevOpsAcademy-<версия>-linux-x64.tar.gz` | сборка для Linux |
| `SHA256SUMS.txt` | контрольные суммы (приложение сверяет их перед установкой) |
| `update.json` | метаданные для автообновления (версия, канал, файлы, ссылка на notes) |
| `RELEASE_NOTES.md` | список изменений |

Перед публикацией обязательны: линтер, 139 тестов, проверка контента и
`--self-test` собранного приложения.

## Как клиент узнаёт о новой версии

1. При каждом запуске (через 2,5 секунды после открытия окна) приложение в фоне запрашивает
   `https://api.github.com/repos/ignatus4405-glitch/DevOps_guide-/releases/latest`.
   Автопроверку можно отключить в настройках.
2. Если версия тега новее `APP_VERSION`, приложение сразу открывает диалог с release notes,
   ссылкой и списком файлов и спрашивает, устанавливать ли обновление. Баннер также остаётся
   в окне, если пользователь отложил решение или закрыл диалог.
3. Пользователь может:
   - **скачать и установить** — файл загружается, сверяется SHA-256 из `SHA256SUMS.txt`,
     затем запускается установщик в тихом режиме, приложение закрывается;
   - **отложить** («Позже») — закрыть диалог; в текущем окне его можно открыть снова через баннер;
   - **пропустить эту версию** — версия запоминается в настройках и автоматически больше не предлагается.
4. При отсутствии обновления или проблемах с сетью приложение продолжает запуск без всплывающих ошибок;
   при ручной проверке результат отображается пользователю.

## Уведомления на уровне команды

Job `notify` после релиза:

- пишет сводку в Summary workflow (со ссылкой на релиз и списком файлов);
- при заданном секрете `RELEASE_WEBHOOK_URL` отправляет POST-сообщение
  (Slack/Discord/Teams/Mattermost);
- подписчики репозитория получают письмо по Watch → Releases.

Чтобы включить вебхук: Settings → Secrets and variables → Actions → New secret
`RELEASE_WEBHOOK_URL` со ссылкой на входящий вебхук канала.

## Ручной выпуск и откат

```bash
# Ручной релиз конкретной версии (через CLI GitHub):
gh workflow run build.yml -f bump=minor

# Откат релиза: переиздать предыдущую версию
git tag -a v0.1.2 <commit> -m "Откат к 0.1.2" && git push origin v0.1.2
```

Поскольку приложение сравнивает версии численно, откат оформляется **новым** релизом
с большим номером (например, 0.1.3 с исправлением), а не понижением тега: иначе
клиенты не увидят изменения.

## Диагностика сборок

| Что нужно | Как посмотреть |
| --- | --- |
| Список запусков | `gh run list` или вкладка Actions |
| Какие job'ы упали | `gh run view <run-id>` |
| Текст ошибки без скачивания логов | аннотации проверки (`gh api repos/<owner>/<repo>/check-runs/<id>/annotations`) — имена упавших тестов и хвост вывода публикует `tools/run_tests.py` |
| Полный лог pytest | артефакт `reports-<os>-<python>` (`reports/pytest.log`, `reports/pytest.xml`) |
| Самотест приложения | шаги «Проверка режима --self-test» (из исходников) и «Проверить собранный exe» (готовая сборка) |
| Журнал собранного приложения | `dist/self-test.log` (переменная `DEVOPS_ACADEMY_LOG`) — в GUI-сборке ошибку иначе не увидеть; шаг печатает журнал в лог workflow |

Особенность Windows: PowerShell **не ждёт** GUI-приложение (`console=False`), поэтому
самотест запускается через `Start-Process -Wait -PassThru` и проверяется `ExitCode`
процесса (иначе `$LASTEXITCODE` остаётся пустым и шаг падает без причины).

Тесты в CI запускает `tools/run_tests.py` (а не `pytest` напрямую): он пишет
`reports/pytest.log` и `reports/pytest.xml`, печатает вывод в лог шага и добавляет
аннотацию с именами упавших тестов. Это важно, потому что GitHub запускает bash
с `-e` (обработчик провала просто не успевает выполниться), а логи workflow
скачиваются отдельным сервисом, который может быть недоступен.
`tools/ci_annotate.py` делает то же самое для произвольного лога.

## Секреты

| Секрет | Обязателен | Для чего |
| --- | --- | --- |
| `GITHUB_TOKEN` | выдаётся автоматически | публикация релиза, теги |
| `RELEASE_WEBHOOK_URL` | нет | уведомления в командный чат |

Других секретов сборке не требуется: репозиторий публичный, образам и обновлениям
токен не нужен.

## Обновление зависимостей

`dependabot.yml` каждую неделю предлагает обновления pip-пакетов и actions;
каждый PR автоматически проходит CI (линтер, тесты, проверка контента).
Обновления, влияющие на пользователя, попадают в следующий релиз и CHANGELOG.
