# Как добавлять контент

Весь курс — это данные в `content/`. Код приложения трогать не нужно.

## Структура модуля

```
content/modules/NN-slug/
├── module.json      описание модуля (id, order, title, level, summary, objectives, tags)
├── lessons/         уроки, порядок = имя файла (01-*.md, 02-*.md ...)
│   └── 01-name.md
├── quiz.json        тест модуля и банк вопросов
├── lesson_quizzes.json  необязательные тесты по 3 вопроса после уроков
└── practice.json    практические задачи
```

`NN` (например `06-docker`) задаёт папку, а порядок в приложении — поле `order`
в `module.json`. Требования проверяет `tools/validate_content.py` и CI.

## module.json

```json
{
  "id": "docker",
  "order": 7,
  "title": "Docker и контейнеры",
  "level": "intermediate",
  "summary": "Одно-два предложения для дашборда.",
  "estimated_minutes": 220,
  "objectives": ["Чему научится студент — 3–5 пунктов"],
  "tags": ["docker", "контейнеры"]
}
```

## Урок

```markdown
---
id: unique-lesson-id
title: Заголовок урока
minutes: 40
---

# Заголовок

Текст с `командами`, таблицами, списками.

![Подпись](assets/img/docker-layers.svg)

!!! warning "Важно"
    Врезки: note / tip / warning / danger. Внутри поддерживается markdown и код.

```bash
docker build -t api:local .
```

## Проверьте себя

1. Вопрос для самопроверки.
```

Правила:
- минимум 1800 символов основного текста (проверяется CI);
- каждая картинка обязана существовать в `content/assets/img`, и каждая
  картинка должна быть подключена хотя бы к одному уроку;
- термины можно оборачивать в `[[docker]]` — они получат подсказку из глоссария;
- ключевые команды даются в блоках с указанием языка (`bash`, `yaml`, `json`, `ini`, `dockerfile`, `powershell`, `python`).

### Структура «глубокого» урока

С 0.4.0 уроки строятся по единому каркасу — он даёт и теорию, и практику:

1. зачем тема и где она встречается в реальной работе;
2. **как это работает внутри** — модель, границы и основные термины, а не набор команд;
3. раздел **«Подробный разбор темы»** — объяснение компромиссов, типичных отказов и способа проверки;
4. **разбор реального сценария** — симптом → гипотезы → проверка → вывод;
5. команды с настоящим выводом (сокращённым, но правдоподобным);
6. ошибки и антипаттерны — таблицей «симптом / причина / лечение»;
7. чек-лист или критерии готовности;
8. **связка с практикой** — ссылка на конкретную задачу;
9. «Проверьте себя» — 3–5 вопросов без ответов в тексте.

Такой урок обычно занимает 20–35 минут и 700–1000 слов. Дублировать один и
тот же текст в разных уроках не нужно: лучше сослаться на соседний урок.

## Учебная нагрузка и структура

Курс рассчитан на последовательное прохождение: модули 1–12 дают базу и
практику, модуль 13 — теорию распределённых систем, модуль 14 — финальный
проект и выход на работу.

Ориентиры на модуль:

- 6–13 уроков по 25–40 минут;
- 18–33 вопроса в тесте;
- 6–12 практических задач;
- 250–500 минут суммарно с практикой.

При добавлении урока проверяйте, что у него есть:

1. front matter (`id`, `title`, `minutes`);
2. минимум 1800 символов текста;
3. 3–5 вопросов «Проверьте себя»;
4. ссылка на практическую задачу;
5. при необходимости — иллюстрация из `content/assets/img`.

Новый материал не должен дублировать существующий: лучше сослаться на соседний
урок и добавить только то, чего там нет.

## quiz.json

```json
{
  "title": "Тест модуля 7: Docker",
  "pass_score": 75,
  "questions": [
    {
      "id": "q1",
      "type": "single",
      "question": "Текст вопроса",
      "options": ["A", "B", "C"],
      "answer": [1],
      "explanation": "Почему это верно и что не так с остальными.",
      "tags": ["containers"]
    },
    {
      "id": "q2",
      "type": "text",
      "question": "Введите ответ одним словом",
      "answer": ["sbom", "software bill of materials"],
      "explanation": "Пояснение."
    }
  ]
}
```

- `type`: `single` (ровно один ответ), `multiple` (несколько), `text` (текстовый).
- Ответы для `single`/`multiple` — **индексы** вариантов, начиная с нуля.
- Для `text` перечисляйте все допустимые формы ответа (регистр и лишние пробелы не важны).
- Пояснение обязательно: без него тест не проверяется в CI.

## lesson_quizzes.json

После каждого урока приложение показывает кнопку короткого автопроверяемого теста.
Тест необязательный: его можно закрыть и сразу перейти к следующему уроку.
Для каждого урока задаются ровно три вопроса; по умолчанию для зачёта нужны два
правильных ответа (`pass_score: 67`). Вопросы можно брать из `quiz.json` модуля
по ID и дополнять отдельными вопросами:

```json
{
  "schema_version": 1,
  "pass_score": 67,
  "lessons": {
    "first-lesson": {
      "question_ids": ["q1", "q7"],
      "questions": [
        {
          "id": "lesson-q1",
          "type": "single",
          "question": "Какой вариант верен?",
          "options": ["Неверно", "Верно", "Тоже неверно"],
          "answer": [1],
          "explanation": "Пояснение к правильному ответу.",
          "tags": ["lesson-check"]
        }
      ]
    }
  }
}
```

- `lessons` должен содержать запись для каждого ID урока этого модуля — без пропусков и лишних ID.
- Сумма `question_ids` и `questions` должна быть ровно три; ссылки разрешаются только на вопросы из `quiz.json` этого модуля.
- Дополнительные вопросы используют ту же схему `single`/`multiple`/`text`, что и вопросы модуля; объяснение и допустимые ответы обязательны.
- `pass_score` можно задать для всего файла или переопределить для конкретного урока; значение должно быть от 1 до 100.
- Результаты мини-тестов сохраняются отдельно от теста модуля и не блокируют отметку урока, навигацию или итоговый экзамен.

## practice.json

```json
{
  "title": "Практика модуля 7",
  "tasks": [
    {
      "id": "first-dockerfile",
      "title": "Написать безопасный Dockerfile",
      "level": "medium",
      "goal": "Что должно получиться и зачем это нужно.",
      "instructions": ["Шаг 1", "Шаг 2"],
      "hints": ["Подсказка, которая не выдаёт решение сразу"],
      "solution": "FROM python:3.12-slim\n...",
      "check": {
        "type": "regex_all",
        "patterns": ["FROM python", "USER\\s+app"],
        "feedback": "Что именно проверялось и почему это важно."
      },
      "validation_hint": "Как студент сам проверит результат: docker run --rm id"
    }
  ]
}
```

Задачи запускаются с дашборда или из урока в безопасном встроенном тренажёре. Кнопка
«Запустить в тренажёре» сохраняет введённый текст в памяти виртуального стенда, а
«Проверить результат» применяет критерии `check`. Shell-команды не выполняются и не
могут изменить файлы или настройки компьютера. Укажите в `instructions` порядок действий,
а в `validation_hint` — конкретный признак успешного результата, который студент сможет
сверить на реальном учебном стенде. Для задач `manual` тренажёр просит явно подтвердить
самостоятельную проверку.

Типы проверки:
- `regex_all` — в ответе должны встретиться все шаблоны (регистр не учитывается);
- `regex_any` — достаточно одного из шаблонов;
- `equals` — ответ совпадает с одним из шаблонов (например `/etc`);
- `commands` — проверяются отдельные shell-команды и обязательные argv-токены; команды не исполняются, комментарии и строки-аргументы не засчитываются;
- `manual` — задача на самопроверку, обязательно заполните `validation_hint`.

Для `commands` используйте объект вместо `patterns`, например:

```json
"check": {
  "type": "commands",
  "commands": [
    {"name": "chmod", "args": ["640", "/opt/app/secrets.env"]}
  ],
  "feedback": "Права выставлены для правильного файла."
}
```

Аргументы должны идти в указанном порядке, но могут быть разделены дополнительными
параметрами; поддерживаются несколько строк, `;`, `&&`, `||`, пайпы и префикс
`sudo`. Проверка намеренно не запускает shell и не заменяет полноценную проверку
инфраструктуры.

**Главное требование:** эталонное решение должно проходить собственную проверку
(`tests/test_content.py::test_solution_passes_own_checker`), в том числе для
`commands`; контент дополнительно валидируется в CI. Проверяйте локально:

```bash
python tools/validate_content.py
pytest tests/test_content.py -q
```

## Иллюстрации

Схемы рисуются кодом, а не «руками», — так их проще править:

```bash
python tools/make_diagrams.py            # перегенерировать все SVG
```

Добавляя новую схему, используйте хелперы класса `Svg` (`box`, `label`, `arrow`, `path`),
затем проверьте результат: `pytest tests/test_diagrams.py` (валидность XML, размеры,
использование в уроках) и **обязательно посмотрите на картинку глазами** — тест
не увидит «линии проходят сквозь текст». Быстрый способ отрисовать SVG в PNG тем же
движком, что в приложении:

```python
from PySide6.QtCore import Qt
from PySide6.QtGui import QImage, QPainter
from PySide6.QtSvg import QSvgRenderer
from PySide6.QtWidgets import QApplication

app = QApplication([])
renderer = QSvgRenderer("content/assets/img/devops-lifecycle.svg")
image = QImage(renderer.defaultSize(), QImage.Format_ARGB32)
image.fill(Qt.black)
painter = QPainter(image)
renderer.render(painter)
painter.end()
image.save("/tmp/preview.png")
```

Правила компоновки схем (проверены на практике):

- блоки не должны пересекаться, а стрелки — проходить через текст и панели;
- подпись должна помещаться в свою панель с запасом (шрифт в Qt шире, чем в браузере);
- цикл рисуйте кольцевой трассой: наконечники по касательной читаются лучше,
  чем дуги «через центр» (именно так ломалась схема жизненного цикла).

## Чек-лист добавления контента

- [ ] `module.json` заполнен (порядок, цели, теги)
- [ ] уроки: front matter, 1800+ символов, картинки существуют
- [ ] вопросы: объяснение у каждого, ответы в диапазоне, 8+ вопросов
- [ ] задачи: решение, шаблоны проверки, подсказки, `validation_hint`, 3+ задач
- [ ] решение проходит автопроверку
- [ ] `python tools/generate_version.py --version "$(cat VERSION)"` (обновить index)
- [ ] `python tools/validate_content.py` и `pytest -q` — зелёные
